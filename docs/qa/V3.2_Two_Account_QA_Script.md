# SnuffleStudy Two-Account QA Script

**Purpose:** the canonical, reusable manual QA pass for every social/accountability feature that
can only really be proven with two real, independent, signed-in accounts clicking through the
actual extension — not just at the data/authorization layer. This is `docs/implementation_plans/
V3.2_Implementation_Plan.md`'s Task 9. It is a **human step**: no agent session should attempt to
execute this script, sign into anything, or apply the prerequisite migrations/deployments below —
those require live write access this sandbox deliberately doesn't have.

**This document is meant to be reused on every future release**, not thrown away after V3.2. Don't
fork a new copy per release — append a new row to the Run Log below and re-walk the same numbered
items, updating a step's copy/instructions only if the underlying UI actually changed since the
last run.

committed on `v3.2`, but **have not been applied/deployed to the live Supabase project**. Every
implementation session that touched them was blocked by this sandbox's write-safety restrictions
on mutating a live database — see `docs/reports/v3.2/task-5-report.md`, `task-6-report.md`, and
`task-8-report.md`'s "What's still open" sections. Running this script before these land will
produce **false failures** on items 6, 7, and 9 below (not real regressions) — do this first.

## 1. Onboarding sign-in flow, end to end (Tasks 1–4)

Covers the shared `<SignInForm />`'s full behavior via `OnboardingWizard.tsx`'s "Sign in" step
(the first screen after the welcome screen, before "Meet Snuffles").

**Use Account A's profile**, fresh install (uninstall/reinstall the extension, or clear its storage,
if onboarding was already completed in this profile before).

1. Open the extension. Dismiss the welcome screen. The "Sign in" step appears, with the framing
   copy: *"Sign in to use friends, rooms, nudges, approvals, and synced accountability features."*
2. Enter Account A's email, click **Send sign-in code**. Confirm a real email with a 6-digit code
   arrives in that inbox within a couple of minutes.
3. **Wrong code:** enter an obviously incorrect 6-digit code (e.g. `000000`), click **Verify code**.
   Confirm an inline error appears (`role="alert"`, text like *"Couldn't sign in: Incorrect or
   expired code."*) and the step does **not** advance — you're still looking at the code-entry form.
4. **Request a new code:** click **Request a new code**. Confirm the email field's value is
   unchanged (still Account A's address, not cleared), the previously entered wrong code is cleared,
   and a **second** email with a new code arrives.
5. Enter the new (correct) code, click **Verify code**. Confirm the wizard advances to "Meet
   Snuffles".
6. Continue through the rest of onboarding (pressure style, duration, tracking tier, passcode —
   any values) to "Ready to go" and finish.

## 6. Daily digest visibility — Task 5's fix specifically

This is the one item that most directly needs the Prerequisites' migration `20260815000030`
(`daily_digests_visible`) actually live — if it isn't applied yet, `digestApi.ts` will 404/error
against a view that doesn't exist, which is a **setup gap**, not a Task 5 regression; go back and
apply it first.

Accounts A and B should already share a group (item 3). This needs at least one full day boundary
to pass with real session activity, or direct seeding — see the note below.

1. On Account A's Options → Account page (or wherever friend-privacy toggles live in the shipped
   UI), confirm **`share_distraction_attempts` is OFF** toward Account B specifically (this is the
   default/unset state for a newly-joined friendship per `friendship_settings`' schema — don't
   explicitly grant it yet).
2. Confirm Account B has `receive_daily_digest` **ON** toward Account A (so B is opted in to seeing
   A's digest at all — otherwise B won't see a digest row for A regardless of the distraction
   toggle, and the test proves nothing).
3. Get at least one real digest row computed for Account A covering a day with a nonzero
   distraction count (a study session with at least one blocked-site attempt, then either wait for
   the real daily aggregation to run, or — faster — ask an engineer to invoke
   `compute_daily_digests('<that date>')` via the service-role client for that date, the same
   mechanism `scripts/verify-digest.mjs` uses).
4. On Account B's Friends tab → "Daily digest" section, find Account A's digest card. Confirm the
   rendered distraction count is **0** (*"…, 0 distractions, …"*), while the completed/abandoned

5. On Account A's own Friends tab → "Daily digest" section (A viewing their own digest, if the UI
   surfaces a self-row — otherwise skip to step 6 and treat step 4 alone as sufficient), confirm A's

6. Now have Account A explicitly turn **ON** `share_distraction_attempts` toward Account B. On
   Account B's next digest refresh (Friends tab → Refresh, or a poll cycle), confirm the same digest

## 9. Account deletion (Task 8) — run LAST, throwaway account only

**Irreversible. Never run this against Account A or Account B — use the disposable third account
from Prerequisites step 3.** Requires the `delete-account` Edge Function actually deployed and
migration `20260815000032` applied (Prerequisites steps 1–2) — otherwise `AUTH_DELETE_ACCOUNT` will
fail outright, which is a setup gap, not a Task 8 regression.

1. Sign in as the throwaway account (a fresh browser profile, or reuse A/B's profile after signing
   out of it first — just don't do this step signed in as A or B).
2. Give it something real to delete: create a friend group, join A's or B's group with a fresh
   invite code, send at least one nudge, record and send at least one Producer Tag (so a Storage
   object actually exists under its account), and let at least one `session_status_events` row and
   one `daily_digests` row get created for it if practical.
3. **Before deleting**, as a service-role query (Supabase SQL Editor, or a throwaway script), note
   this account's `auth.uid()` and confirm it currently has at least one row in several of the
   tables below — otherwise step 5 would trivially "pass" by having nothing to check in the first
   place.
4. In the extension's Options → Account page, click **Delete account**. Confirm the browser's
   confirm dialog appears with the expected warning text before anything is sent. Confirm it.
5. Confirm the UI returns to the signed-out `SignInForm` (no lingering signed-in state, no error).
6. **Via the Supabase Dashboard or a service-role query**, confirm **zero** rows remain referencing
   that account's `auth.uid()` across every one of these tables (the same fourteen this migration's
   own header documents — not just the plan's original twelve):

   ```sql
   -- replace '<uid>' with the deleted account's auth.uid(), noted in step 3
   select 'friend_groups (owner)'      as check_name, count(*) from friend_groups        where owner_user_id = '<uid>'
   union all select 'group_memberships',            count(*) from group_memberships      where user_id = '<uid>'
   union all select 'invite_codes (created/used)',  count(*) from invite_codes           where created_by = '<uid>' or used_by = '<uid>'
   union all select 'friendship_settings',          count(*) from friendship_settings    where user_id = '<uid>' or friend_user_id = '<uid>'
   union all select 'session_status_events',        count(*) from session_status_events  where user_id = '<uid>'
   union all select 'unlock_requests (requester)',  count(*) from unlock_requests        where requester_user_id = '<uid>'
   union all select 'unlock_requests (resolved_by)',count(*) from unlock_requests        where resolved_by = '<uid>'
   union all select 'temp_passcode_requests',       count(*) from temp_passcode_requests where requester_user_id = '<uid>' or friend_user_id = '<uid>'
   union all select 'study_rooms (owner)',          count(*) from study_rooms            where owner_user_id = '<uid>'
   union all select 'study_room_participants',      count(*) from study_room_participants where user_id = '<uid>'
   union all select 'producer_tags',                count(*) from producer_tags          where user_id = '<uid>'
   union all select 'producer_tag_sends',           count(*) from producer_tag_sends     where sender_user_id = '<uid>' or recipient_user_id = '<uid>'
   union all select 'daily_digests',                count(*) from daily_digests          where subject_user_id = '<uid>'
   union all select 'nudges',                       count(*) from nudges                 where sender_user_id = '<uid>' or recipient_user_id = '<uid>'
   union all select 'coaching_message_requests',    count(*) from coaching_message_requests where user_id = '<uid>'
   union all select 'auth.users row itself',        count(*) from auth.users             where id = '<uid>';
   ```

   Every row's `count` must be `0`. (`friend_groups`/`study_rooms` intentionally check only the
   `owner_user_id` = the deleted account's case — a group it *joined* but didn't own should show the
   group still existing, just without the deleted account as a member, which
   `group_memberships` — correctly `0` — already confirms.)
7. Confirm the Producer Tag audio object(s) recorded in step 2 are gone from the `producer-tags`
   Storage bucket (Dashboard → Storage → `producer-tags`, browse to the tag id path(s) noted in step
   2 — should 404/not list).
8. If this account had been the **sole member** of a friend group it owned, confirm that group row
   is also gone (`select * from friend_groups where id = '<group id>'` returns nothing). If it
   shared that group with another member, confirm the group **still exists** with ownership
   reassigned to the longest-standing remaining member instead (`owner_user_id` now points at
   someone else, not a dangling reference).
