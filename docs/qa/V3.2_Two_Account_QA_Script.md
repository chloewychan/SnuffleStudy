# SnuffleStudy Two-Account QA Script

**Purpose:** the canonical, reusable manual QA pass for every social/accountability feature that
can only really be proven with two real, independent, signed-in accounts clicking through the
actual extension — not just at the data/authorization layer. Originally `docs/implementation_plans/
V3.2_Implementation_Plan.md`'s Task 9, and now also covers `docs/implementation_plans/
V3.3_Implementation_Plan.md`'s Task 15: items 10–20 below are V3.3's additions, and items 1, 2, 3,
5, 7, and 9 were updated in place where V3.3 changed the underlying UI those items already walk
through (items 4, 6, 8 are untouched — nothing in V3.3 touched nudges, daily digests, or Producer
Tags). It is a **human step**: no agent session should attempt to execute this script, sign into
anything, or apply the prerequisite migrations/deployments below — those require live write access
this sandbox deliberately doesn't have.

**This document is meant to be reused on every future release**, not thrown away after V3.2 or
V3.3. Don't fork a new copy per release — append a new row to the Run Log below and re-walk the
same numbered items, updating a step's copy/instructions only if the underlying UI actually changed
since the last run.

## 1. Onboarding sign-in flow, end to end (Tasks 1–4; updated for V3.3 Tasks 2, 14)

Covers the shared `<SignInForm />`'s full behavior via `OnboardingWizard.tsx`'s "Sign in" step
(the first screen after the welcome screen, before "Meet Snuffles"). **Updated for V3.3:** Task 14
replaced the old single email/code flow with a Create-account/Sign-in choice, and made a mandatory
password step part of account creation; Task 2 fixed the code-entry copy from "6-digit" to

onboarding install is, definitionally, creating a new account.

**Use Account A's profile**, fresh install (uninstall/reinstall the extension, or clear its storage,
if onboarding was already completed in this profile before).

1. Open the extension. Dismiss the welcome screen. The "Sign in" step appears, with the framing
   copy: *"Sign in to use friends, rooms, nudges, approvals, and synced accountability features."*
   Confirm it now shows an entry-state choice of two buttons, **Create account** and **Sign in**
   (plus **Skip for now**, still present at this first screen) — not a bare email field.
2. Click **Create account**. An email field appears. Enter Account A's email, click **Send sign-in
   code**. Confirm a real email with an **8-digit** code arrives in that inbox within a couple of
   minutes, and that the on-screen copy reads *"Check {email} for an 8-digit code."* (not 6-digit).
3. **Wrong code:** enter an obviously incorrect 8-digit code (e.g. `00000000`), click **Verify
   code**. Confirm an inline error appears (`role="alert"`, text like *"Couldn't sign in: Incorrect
   or expired code."*) and the step does **not** advance — you're still looking at the code-entry
   form.
4. **Request a new code:** click **Request a new code**. Confirm the email field's value is
   unchanged (still Account A's address, not cleared), the previously entered wrong code is cleared,
   and a **second** email with a new code arrives.
5. Enter the new (correct) code, click **Verify code**. Confirm the wizard does **NOT** yet advance
   to "Meet Snuffles" — instead a mandatory password step appears: *"Almost done - set a password to
   finish creating your account."* with **Password** and **Confirm password** fields.
6. Leave the two password fields empty or mismatched. Confirm the **Set password** button is
   genuinely disabled (check the DOM `disabled` attribute, not just its visual dimming). Enter two
   matching passwords, click **Set password**. Confirm *now* the wizard advances to "Meet Snuffles"

7. Continue through the rest of onboarding (pressure style, duration, tracking tier, passcode —
   any values) to "Ready to go" and finish.
