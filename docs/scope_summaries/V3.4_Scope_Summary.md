# SnuffleStudy V3.4 Scope Summary — Friend-Model Foundation, Nudge Unification, Account-Setup Consolidation, Task Vault Simplification

**Purpose of this document:** the definite v3.4 scope, following the decisions made in conversation against a grounded read of the current (post-V3.3) codebase. This document states what gets built, not why — drawbacks and alternatives were discussed and resolved before this was written.

This version adds a foundation pass (Section 0) on top of the originally-requested items: rather than adding a third near-duplicate "friend approves a request" table for the session-end temporary pass, the underlying friend model gets rebuilt first — a real pairwise friendship replacing the group mechanic everything currently routes through — so this and every future "ask a friend for X" feature share one mechanism instead of each inventing its own. Per your explicit go-ahead, none of the current data is preserved through this — every migration below is a clean cutover, not a careful backfill, since the accounts on this today are test accounts.

One item from the original ask — keeping the user connected to a Study Room while they're on a different sidepanel tab — is explicitly **out of scope for v3.4** at your request, pending a separate pass on how the Study Room should be displayed generally. `StudyRoomPanel.tsx`'s unmount-triggers-leaveCall behavior is unchanged this version.

---

## Section 0 — Foundation: real friendships, one request mechanism, one auth helper

Build this first. Every other item in this document either touches friend-permission checks directly or benefits from the codebase being settled before it's built, rather than being built against the old group model and re-migrated again immediately after.

### 1. Replace the group mechanic with real pairwise friendships

Today, "friending" (the V3.3 rename) is cosmetic: `AccountPage.tsx`'s "Invite a friend" auto-creates a hidden group and an invite code for it; "Add a friend" joins that group via the code; "Your friends" lists that group's other members. Underneath, `friend_groups`/`group_memberships`/`invite_codes` and the `users_share_a_group(uuid, uuid)` SECURITY DEFINER helper back nearly every friend-permission check in the app — `friendship_settings`'s auto-creation trigger, `profiles`, `nudges`, `producer_tag_sends`, `study_rooms`/`study_room_participants`/`study_room_invitees`'s eligibility, `unlock_requests`, `temp_passcode_requests`. This version replaces the group underneath with a direct connection between two users:

- New `friendships` table: `user_id_a`, `user_id_b` (stored in a canonical order, e.g. `user_id_a < user_id_b`, so each pair has exactly one row), `created_at`. RLS: a user can read/insert rows where they're one of the two ids.
- New `are_friends(uuid, uuid) returns boolean` SECURITY DEFINER helper, replacing `users_share_a_group()`. Every policy or trigger currently calling `users_share_a_group()` is rewritten to call `are_friends()` instead — this is the single largest mechanical change in this item, touching most of the RLS surface in the project.
- `invite_codes` keeps its exact current shape and redemption model — generate a code, redeem a code, connected instantly, no accept/decline step. Decided explicitly, not left implicit: possessing the code already represents two deliberate actions (the generator chose to share it with this specific person; the redeemer chose to enter it), the code is already single-use and time-limited (today's "unused, unexpired" redemption policy, unchanged), and a per-friend removal action (below) makes an unwanted connection a one-click fix after the fact rather than something that has to be prevented up front — an approval step would add friction without a clear safety gap it's closing. Redemption now inserts a `friendships` row directly between the two users instead of adding both to a shared group.
- `friendship_settings` needs no schema change — it's already keyed by `(user_id, friend_user_id)` pairs directly, not by group. Only its auto-creation trigger's firing condition changes, from "the moment two users share a group" to "the moment a `friendships` row is created."
- `AccountPage.tsx`'s "Your friends" section changes from today's group-shaped UI (a manually-entered "Friend list ID," "List members" scoped to one group at a time, "Leave" scoped to one group at a time) to one flat list of every friend the signed-in user has — this can't actually stay "as-is" once groups are gone, since today's UI only works the way it does because a user can hold membership in several separate groups. Each row gets its own **"Remove friend"** action (deletes that one `friendships` row), replacing group-scoped "Leave." "Invite a friend" and "Add a friend" keep their current copy and flow — generate a code, redeem a code — unchanged other than what gets written on redemption.
- **Quick confirmation when a code is redeemed.** `friendships` gains one more column, `initiated_by uuid references auth.users(id)` — set at creation time to whichever of the two users generated the invite code being redeemed (the other side is implicitly whoever redeemed it). Informational only — no permission check depends on it. A new `pollFriendConnectionUpdates(userId)` joins `alarmHandlers.ts`'s existing friend-poll alarm cycle (mirroring its established `poll*Updates` pattern, with its own persisted cursor in `friendPollState.ts`), finds `friendships` rows where `initiated_by = userId` created since the last poll, and shows one `chrome.notifications` toast per new connection: *"{friend's name} just connected using your invite"* — using the same human-name-with-raw-id-fallback resolution every other friend-facing notification in this codebase already uses.
- `study_room_invitees` (added in V3.3, already friend-specific) is unchanged in shape — only the definition of "eligible to invite" changes, from "shares a group with the room owner" to "is friends with the room owner," via `are_friends()`.
- `friend_groups`, `group_memberships`, and `users_share_a_group()` are dropped once every call site is migrated. No data backfill from the old tables — a clean cutover, per your note that the current accounts are disposable test data.

### 2. One shared backend auth helper

`nudgeApi.ts`'s `checkAuth()` and `friendGroupApi.ts`/`profileApi.ts`'s `requireUserId()` (and other `infrastructure/backend/*Api.ts` files following the same shape) each independently reimplement "get the current authenticated user or fail" — several with comments noting they're deliberately mirroring another file's version rather than sharing one. Consolidate into one `infrastructure/backend/authHelpers.ts` exporting both shapes used today — `requireUserId(): Promise<string>` (throws when signed out) and `checkAuth(): Promise<{ ok: true; userId: string | null } | { ok: false }>` (for callers that need to tell a failed check apart from a clean signed-out state) — every `*Api.ts` file imports from here instead of defining its own copy.

### 3. One generalized friend-request mechanism, covering unlock, temporary passcode, session-end, and future kinds

Today `unlock_requests`, `temp_passcode_requests`, and the session-end feature this version was going to add as `session_end_requests` are three separate tables, each hand-copying the previous one's shape — separate RLS pairs, separate `*Api.ts` files, separate approver panels (`UnlockRequestPanel.tsx`, `TempPasscodePanel.tsx`, and a `SessionEndRequestPanel.tsx` that — found while grounding this — already exists and is tested but isn't mounted anywhere in the shipped app). This version replaces all three with one mechanism:

- New `friend_requests` table: `id`, `kind` (`'site_unlock' | 'site_temp_pass' | 'session_end'`, open to future values), `requester_user_id`, `friend_user_id` (nullable — null means "any of the requester's friends can resolve it," matching `unlock_requests`' current group-wide/first-responder-wins behavior, now scoped to `are_friends()` instead of a group; set means "only this friend," matching `temp_passcode_requests`' current behavior), `message` (nullable text), `status` (`'pending' | 'approved' | 'denied'`), `requested_at`, `resolved_at`, `resolved_by`. Plus kind-specific nullable columns, each used by exactly one kind today: `hostname` (`site_unlock`/`site_temp_pass`), `session_id` (`session_end`), `expires_at` (`site_temp_pass`'s TTL, for its relock-alarm behavior). A future kind that needs its own bit of context adds one more nullable column the same way — this mirrors how `TempPasscodeRequest`/`SessionEndRequest` already each carry their own shape-specific fields today, just consolidated onto one table instead of split across three.
- One RLS policy set: SELECT `requester_user_id = auth.uid() or friend_user_id = auth.uid() or (friend_user_id is null and status = 'pending' and are_friends(requester_user_id, auth.uid()))`; INSERT `requester_user_id = auth.uid()`; UPDATE (resolve) mirrors the SELECT visibility, with the same "must still be pending" first-responder-wins race guard `unlock_requests` already has today.
- One `friendRequestApi.ts`, replacing `unlockRequestApi.ts` and `tempPasscodeApi.ts`'s request/resolve/fetch/poll functions, parameterized by `kind`. `approve-temp-passcode`'s Edge Function (TTL/relock generation) stays scoped to `kind = 'site_temp_pass'` only — not something every kind has to know about.
- One `FriendRequestPanel.tsx`, replacing `UnlockRequestPanel.tsx`, `TempPasscodePanel.tsx`, and the never-mounted `SessionEndRequestPanel.tsx` — the approver-side "Requests from friends" list, rendering a kind-specific detail line ("wants to unlock {hostname}," "wants a temporary pass for {hostname}," "wants to end their session early") and the optional `message`, with identical Approve/Deny handling across all three. Mounted once, in `SettingsTab.tsx`, replacing all three of today's separate mounts there and in `SidePanelApp.tsx`'s active-session view.
- Requester-side UI stays feature-specific — `LockedPage.tsx`'s existing unlock/temp-pass requests, and a new small form on `EndSessionControl.tsx`'s hard-mode prompt (a friend picker sourced the same way `LockedPage.tsx`'s is, plus an optional message field, matching that screen's "Why do you need this? (optional)" pattern) — since each is embedded in a different moment in the app. All three now call the same shared `createRequest(kind, friendUserId, message, context)` instead of separate implementations.
- `unlock_requests` and `temp_passcode_requests` are dropped once their call sites migrate to `friend_requests`. No data migration — a clean cutover, same as item 1 above.

## Section 1 — Everything else

### 1. Unify nudges and Producer Tags into one "nudge" concept — written and audio, each with its own cooldown

Nudges (`nudges` table, `nudgeApi.ts`) and Producer Tags (`producer_tag_sends`/`producer_tags`, `producerTagApi.ts`) stay as separate backing tables this version — audio needs a Storage-bucket reference and a duration cap that text doesn't, and splitting the schema apart now isn't worth it for what's fundamentally a UI/vocabulary and rate-limit change. No dependency on Section 0: `friendship_settings` is already pairwise-keyed, and Section 0 item 1 preserves its creation trigger, just retargeted to fire off `friendships` instead of `group_memberships`.

- **Presentation:** `NudgeSendForm.tsx` and `ProducerTagSection.tsx` (both already inside `FriendGroupPanel.tsx`, already sharing the same `effectiveFriendId` target picker) merge into one "Send a nudge" section with a **Written / Audio** segmented toggle. Written shows today's `NUDGE_MESSAGES` catalog; Audio shows today's `ProducerTagRecorder`. One friend picker, one section, two modes — not two separate UI blocks anymore.
- **Cooldowns, independent per type, ~1 minute default each.** `friendship_settings.nudge_cooldown_seconds` (currently one column, default 300) splits into `nudge_cooldown_seconds_written` and `nudge_cooldown_seconds_audio`, each defaulting to **60**. A backfill migration sets both columns to 60 on every existing `friendship_settings` row too — this is a real behavior change for existing friend pairs, not just new ones, so it needs to actually take effect immediately rather than only for pairs connecting from now on.
- **Rate-limit gate, extended to cover audio for the first time.** Today, `can_send_nudge()` (the SECURITY DEFINER function backing the `nudges` INSERT policy) is the only cooldown/toggle enforcement in this feature — `producer_tag_sends` has no equivalent gate at all; a friend can currently send unlimited audio tags. This version extends that same enforcement to `producer_tag_sends` inserts, keyed off the same `receive_live_nudges`/`send_live_nudges` toggle columns (both types share one on/off toggle — only the cooldown timers are separate) and the new `nudge_cooldown_seconds_audio` column.
- **Copy:** every place "Producer Tag(s)" appears in user-facing text (`ProducerTagSection.tsx`'s heading, `AccountPage.tsx`'s delete-account warning list, etc.) becomes "audio nudge(s)." Internal file/table/type names (`ProducerTag`, `producerTagApi.ts`, `producer_tag_sends`) are unchanged this version — a naming-only rename of the backend isn't required to ship the unified UI and shared rate limit, and can follow later if wanted.

### 2. Require the current password before changing it

`AccountPage.tsx`'s "set/change your password" section only asks for a new password today (twice) and calls `AUTH_SET_PASSWORD` → `supabase.auth.updateUser({ password })`, which succeeds for anyone holding a valid session — no re-proof of the existing password. This version adds that proof, but only when there's an existing password to prove:

- New nullable `password_set_at timestamptz` column on `profiles`, set whenever `AUTH_SET_PASSWORD` succeeds (both from `SignInForm.tsx`'s create-account step and from `AccountPage.tsx`'s change-password action). This is the durable, server-side signal for "does this account already have a password" — the client can't infer that reliably from the Supabase session object alone.
- `AccountPage.tsx` loads its own `password_set_at` via `PROFILE_GET_MINE` alongside the rest of its account state. If it's set, the password section shows a **"Current password"** field above "New password"/"Confirm new password," required to submit. If it's null (an account that predates this feature, or was created OTP-only before ever setting one), the section renders exactly as it does today — no current-password field, since there isn't one yet.
- `AUTH_SET_PASSWORD`'s payload gains an optional `currentPassword` field. When the signed-in user's profile has `password_set_at` set, `messageRouter.ts`'s handler verifies `currentPassword` via `supabase.auth.signInWithPassword({ email, password: currentPassword })` **before** calling `updateUser({ password })`, returning `{ ok: false, error: "Current password is incorrect." }` on a mismatch instead of changing anything. When `password_set_at` is null, `currentPassword` is ignored (there's nothing to verify against) and behavior is unchanged from today.

### 3. Consolidate account creation onto one screen — name, bunny name, email, password (×2) — verification code is the only remaining step after

Email verification is **kept**, not dropped — it still has to happen before an account is usable, same as today. What changes is that every other field moves earlier, onto the same screen, and account creation completes automatically the moment the code is verified — no separate password step or profile step afterward.

- `SignInForm.tsx`'s create-account branch: the current `"create-email"` step is replaced by a `"create-details"` step collecting **Name, Bunny name, Email, Password, Confirm password** all on one form. Bunny name is optional (left blank, it falls back to the existing "Snuffles" stub default `BunnyTab.tsx` already shows for an unset profile) — everything else is required. Submit is disabled until password and confirm-password match, mirroring the exact disabled-until-matching contract the current `"create-password"` step already uses. Submitting requests the OTP code (`AUTH_REQUEST_OTP`) and advances to `"create-code"`, exactly as today.
- Name/bunny name/password are held in local component state (alongside the already-existing `pendingCreateSession` pattern) while the code step is pending — nothing is saved to the backend yet, since the email isn't verified yet.
- On successful `AUTH_VERIFY_OTP`, the account-creation completion step fires automatically and immediately: `AUTH_SET_PASSWORD` (with the collected password) and `PROFILE_SAVE_MINE` (with the collected humanName/bunnyName) both run before `onSignedIn` is called. The standalone `"create-password"` mode is removed entirely — there is no step after code verification anymore.
- If either call fails (e.g. the password doesn't meet Supabase's project-level policy), the error surfaces inline on the code-verification screen with a way to retry the completion step, without forcing the user to re-verify a fresh code — the email is already proven at that point.
- `AccountPage.tsx`'s existing "set/change your password" section (Section 1 item 2 above) and `BunnyTab.tsx`'s existing name fields are both unchanged as ongoing edit surfaces — this item only changes how they're first collected at signup, not how they're edited later.
- Onboarding's sign-in step renders the same `SignInForm`, so it gets this consolidated flow automatically, same as every prior `SignInForm` change has.

### 4. Remove "Back"/"Close" buttons that don't lead anywhere

Confirmed dead: `StudyRoomPanel.tsx` and `FriendGroupPanel.tsx` each render an internal `<button onClick={onClose}>Close</button>`, and `FriendsTab.tsx` (their only mount point) passes `onClose={() => {}}` — a no-op left over from when these were routed pages with somewhere to close *to*, now permanently embedded side by side with nowhere to go. (The equivalent dead `onClose` on `TempPasscodePanel.tsx`/`UnlockRequestPanel.tsx` in `SettingsTab.tsx` is moot after Section 0 item 3 replaces both components entirely. `SignInForm.tsx`'s "Back" buttons were checked too — those all navigate between real modes within that form and are not dead; nothing changes there.)

- `onClose` becomes optional (`onClose?: () => void`) on `StudyRoomPanel`/`FriendGroupPanel`; each renders its Close button only when a real handler is passed: `{onClose && <button type="button" onClick={onClose}>Close</button>}`.
- `FriendsTab.tsx` stops passing `onClose` to either — the button disappears there.
- The new `FriendRequestPanel.tsx` (Section 0 item 3) is built without a dead Close button in the first place, rather than inheriting one from its three predecessors.

### 5. Remove the Task Vault breakdown-item feature

Confirmed real: a Task Vault task can have `TaskBreakdownItem`s (subtasks like "Chapter 6 of STAT231"), each independently checkable, and each with a "Start a session from this" button that threads `taskBreakdownItemId` through `SESSION_CREATE` onto the resulting `StudySession`. The mismatch is in how that item gets marked done afterward: `alarmHandlers.ts`'s natural-completion branch (the timer running out) silently auto-completes the linked breakdown item, but ending that same session any other way — the everyday "End session" button, a hard-mode passcode/temporary-pass end, anything routed through `messageRouter.ts`'s `SESSION_END` — deliberately does **not** (`messageRouter.ts`'s own comment: "a manually/early-ended session should not mark its linked TaskBreakdownItem done"). So a student who finishes the chapter early and clicks "End session" satisfied gets no credit, while a student who got distracted but let the timer run out gets auto-checked off with no confirmation either way. Removing it rather than patching it, per your call:

- `taskTypes.ts`: `TaskBreakdownItem` interface removed; `Task.breakdown` field removed. `Task` becomes just `id`, `userId`, `title`, `createdAt`, `completedAt` (that last field is already unused by any current UI — worth knowing, but left as-is; not part of this removal).
- `taskRepository.ts`: `TaskRepository.addBreakdownItem()` removed from the interface and `IndexedDbTaskRepository`. No IndexedDB version bump/migration needed — existing local rows that still have a stored `breakdown` array on disk are simply never read or written again by the new code; the leftover field is harmless.
- `shared/messages.ts`: `TASK_ADD_BREAKDOWN_ITEM` removed. `SESSION_CREATE`'s payload type drops `& { taskBreakdownItemId?: string }`, back to plain `CreateSessionInput`.
- `messageRouter.ts`: the `TASK_ADD_BREAKDOWN_ITEM` case removed; `SESSION_CREATE`'s handler no longer merges a `taskBreakdownItemId` onto the session it creates.
- `alarmHandlers.ts`: `markBreakdownItemCompleted()` and its call site in the natural-completion branch removed entirely.
- `sessionTypes.ts`: `StudySession.taskBreakdownItemId` field removed.
- `TaskVaultPage.tsx`: the breakdown-item list, the "Add breakdown item" form, `breakdownDrafts` state, `handleAddBreakdownItem`, `handleToggleBreakdownItem`, and the "Start a session from this" button all removed. `onStartSessionFromBreakdownItem` removed from `TaskVaultPageProps`. What remains: create a task, see the list, delete a task — flat, no nesting.
- `StudyTab.tsx`: the `prefill` state, the `onStartSessionFromBreakdownItem` wiring, and the `key={prefill?.taskBreakdownItemId ?? "default"}` remount trick on `SessionSetupForm` all removed — there's no external prefill event to remount for anymore.
- `SessionSetupForm.tsx`: `initialGoal`/`taskBreakdownItemId` props removed; `goal` state goes back to a plain `useState("")`; `taskBreakdownItemId` dropped from the `SESSION_CREATE` payload. The Goal dropdown itself is untouched — picking a flat task by title to prefill the goal field never depended on breakdown items and keeps working exactly as it does today.

## Suggested execution order

1. **Section 0, item 2** (shared auth helper) — free-standing, do first; every `*Api.ts` file the rest of this release touches should import from it rather than gain a fresh independent copy.
2. **Section 0, item 1** (pairwise friendships) — the foundation. Do this before anything else that touches a friend-permission check.
3. **Section 0, item 3** (generalized `friend_requests`) — depends on item 1's `are_friends()` helper.
4. **Section 1, item 4** (dead Close buttons) and **item 5** (Task Vault breakdown removal) — free-standing, no dependency on Section 0; can run in parallel with it if you want, listed here for a single linear read.
5. **Section 1, item 2** (current-password check) — independent.
6. **Section 1, item 3** (consolidated signup) — after item 2, since it's the other writer of `password_set_at`/`PROFILE_SAVE_MINE`.
7. **Section 1, item 1** (nudge/Producer Tag unification) — last; the largest remaining item, and by this point `friendship_settings`' creation path is already settled by Section 0.
8. **Manual two-account QA pass**, last — now also exercising Section 0 directly (two test accounts connect via invite code and are confirmed friends everywhere: nudges, Study Rooms, digests, the new `FriendRequestPanel`; "Remove friend" actually revokes access everywhere `are_friends()` gates something, not just from the list view), alongside item 1's new audio cooldown and Section 0 item 3's friend-only request visibility (a friend who isn't the assigned one, and isn't the requester, can't see or resolve a `friend_user_id`-scoped request).

## Definition of done for V3.4

Two accounts connect as friends directly (no group underneath) via the existing invite-code flow — instant on redemption, no accept/decline step, by deliberate choice — and "Your friends" shows one flat list of every connection with a working per-friend "Remove friend" action, instead of today's manually-entered group id. Every friend-permission check in the app — profiles, nudges, Producer Tags, Study Rooms and their invitees, and friend-approval requests — runs through the new pairwise `are_friends()` check, not group membership. Unlock requests, temporary-passcode requests, and session-end requests are one mechanism (`friend_requests`, one table, one panel) instead of three separate ones, and a friend has one real screen to approve or deny any of them from. Sending a nudge to a friend offers Written or Audio from one unified section with one friend picker; each has its own ~1-minute default cooldown, both toggled by the existing shared on/off setting, and audio nudges are rate-limited for the first time. Changing your account password requires the current password first, except for an account that has never had one, which still sets its first password with no prior proof required. Creating an account collects name, bunny name, email, and a confirmed password on one screen, with email verification as the one remaining step after — the account, its password, and its profile are all live the moment the code is verified. Every "Close" button that used to do nothing now either works or isn't shown. Task Vault tasks are flat — no breakdown items, no linked-session auto-completion, no "Start a session from this" — just create, list, and delete a task, with a task's title still usable as a session goal. Study Room persistence across sidepanel tabs remains untouched, deliberately deferred to a future version.
