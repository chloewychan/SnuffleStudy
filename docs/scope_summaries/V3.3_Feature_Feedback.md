# SnuffleStudy V3.3 — Feature Feedback & Scoping Notes

**Purpose of this document:** a grounded review of the 12 items proposed for v3.3, checked against the actual v3.2 codebase rather than assumed. Organized in your own four groups. Each item gets: what's actually there today (with file references), a feasibility read, the real drawbacks and a concrete solution, and — where it applies — a flag for something that isn't a v3.3-sized change as stated.

Two items turned out to be much cheaper than they look (the temp-passcode flow, the video sizing bug) because the codebase already solves an adjacent problem the same way. One item (renaming "friend group") is much bigger than it looks, because the group model isn't cosmetic — it's the backbone of almost every RLS policy in the app. That one gets flagged rather than scoped.

---

## Section 1 — Rearranging locations of things

### 1.1 Move Temporary passcode requests + Unlock requests from Settings tab to Friends tab

**Today:** `SettingsTab.tsx` renders `<TempPasscodePanel>` then `<UnlockRequestPanel session={null}>`. `FriendsTab.tsx` renders `<StudyRoomPanel>` then `<FriendGroupPanel>`. Both tab files are pure composition — literally just two JSX blocks each, no logic of their own.

**Feasibility:** trivial. This is a cut-and-paste between two files.

**Drawbacks / gotchas:**
- `UnlockRequestPanel` is currently passed `session={null}` in `SettingsTab.tsx`, which is *why* only its "Requests from friends" half renders there (its "Request an unlock" section is gated on `session !== null`). If the goal is just to relocate the approver view, keep passing `null`. If you also want the *requester* side reachable from the Friends tab (asking to unlock a site for the active session), `FriendsTab.tsx` would need the real active session threaded in — that's a small but real prop-plumbing change, not a pure move.
- Both panels still render a visible "Close" button wired to a no-op `onClose` (a known, already-accepted leftover from when these were routed pages — see the comments in both tab files). Moving them doesn't fix or worsen that; worth deciding once, separately, whether to just remove those buttons everywhere.

**Recommendation:** do this first — it's free, and it clears space in Settings for 1.2 below.

### 1.2 Add Settings / Account / Friends / History as boxes in the sidepanel's Settings tab, linking to the extension's Options page

**Today:** the sidepanel only has four tabs (Bunny/Study/Friends/Settings — `TabBar.tsx`), all rendered inline with no navigation. The richer "Settings / History / Account / Friends / Privacy" surface already exists, but as a *separate* full-tab page (`OptionsApp.tsx`), only reachable via `chrome://extensions` or the manifest's options entry — not linked from the sidepanel anywhere today.

**Feasibility:** straightforward. This is four buttons that call `chrome.runtime.openOptionsPage()` (the standard MV3 API for this — no message-passing needed, it's a direct browser API), landing on the Options page's `settings`/`account`/`friends`/`history` view respectively. `OptionsApp.tsx`'s `view` state already supports being told which view to open; you'd want to extend `openOptionsPage()`'s target with a `#hash` or query param (`options.html#account`) and read it once on mount to set the initial `view`, since `chrome.runtime.openOptionsPage()` doesn't take a "start on this tab" argument itself.

**Drawbacks / gotchas:**
- This *doesn't* embed the options content in the sidepanel — it opens a new full browser tab. That's consistent with how this codebase already treats the Options page elsewhere (the "grant camera/microphone access" flow in `OptionsApp.tsx` explicitly requires a real full tab, because a Chrome side panel can never show a `getUserMedia` permission prompt). Worth setting that expectation: these are launcher buttons, not an embedded view.
- "Privacy" exists as a fifth Options view but isn't in your requested order of four — leaving it unlinked from the sidepanel is fine (it's not a page most users need to jump to routinely), just flagging that it stays reachable only via the Options page's own nav once you're there.

**Recommendation:** do this second, once 1.1 has freed up the Settings tab. Low effort, no backend involved.

## Section 2 — Friends flow

### 2.1 Add/remove study rooms if you created the room

**Today:** "add" (create) already exists — `STUDY_ROOM_CREATE` → `studyRoomApi.createRoom()`. "Remove" doesn't exist at all: there's no delete/archive path in `studyRoomApi.ts`, no RLS policy for it, and no button for it anywhere in `StudyRoomPanel.tsx`.

**Feasibility:** straightforward, self-contained.

**Drawbacks / gotchas:**
- `producer_tag_sends.recipient_room_id` has a foreign-key reference to `study_rooms.id` (see the v2 accountability schema migration). A hard `DELETE` on a room with any producer-tag history would either fail on the FK constraint or (if you added `ON DELETE CASCADE`) silently erase real activity history that had nothing wrong with it.
- **Solution:** don't hard-delete. Add an `archived_at timestamptz` column to `study_rooms`, an RLS `UPDATE` policy scoped to `owner_user_id = auth.uid()`, and filter `listRooms()` to `archived_at is null`. This sidesteps the FK problem entirely, keeps history intact, and is the same pattern this codebase already uses elsewhere for "soft" state changes (`left_at` on participants, `resolved_at` on requests) rather than deletes.
- Decide what happens to anyone currently *in* an archived room — recommend: archiving doesn't force-disconnect an active call, it just removes the room from the joinable list going forward (mirrors how leaving a group doesn't retroactively yank you out of a room you already joined).

### 2.2 Per-room friend visibility (instead of automatic group-wide access)

**Today:** any study room is visible and joinable by *anyone who shares a group with the owner* — full stop. This is enforced entirely in RLS (`study_rooms`' SELECT policy and `study_room_participants`' INSERT policy, both rewritten together in migration `20260815000019` specifically to close a "room is discoverable but not joinable" gap). There is no concept of "invite specific friends to this room" anywhere in the schema.

**Feasibility:** real backend work, but contained — this is exactly the kind of access-control change this codebase already has a clean pattern for (see 20260815000019's own header comment on how carefully the read-vs-write halves of a visibility change have to move together, or you reopen the same bug three separate features already hit: unlock requests, daily digests, friendship settings, temp passcodes).

**What it actually takes:**
- A new `study_room_invitees` table (`room_id`, `user_id`, `invited_by`, `invited_at`).
- Rewrite `study_rooms`' SELECT policy and `study_room_participants`' INSERT policy to also accept "is in `study_room_invitees` for this room," alongside (not necessarily instead of) the existing group-sharing check.
- Owner-only UI: an "add/remove friends" list on a room you own, sourced from your existing friend/group list.
- A decision on default behavior (see below).

**Drawback worth flagging explicitly:** if this *replaces* today's "any group-mate can see it" behavior outright, every room becomes invite-only by default — meaning a user has to explicitly add friends to every room they create before anyone else can find it. That's a real behavior change, not just an added option, and it will make rooms feel emptier/harder to discover unless the invite step is fast and low-friction.

**Recommendation:** make it additive, not a replacement — a room defaults to "visible to anyone in your group(s)" exactly as it does today (zero behavior change for anyone who doesn't touch the new control), with an owner-only toggle to restrict a specific room to an explicit allow-list. This gets you the control you're asking for without silently breaking the "just works" default the app has today. Also decide: does restricting a room retroactively remove participants who are already in it but not on the new list? Recommend no — restriction only affects who can *newly* join, not who's already there, mirroring how leaving a group doesn't retroactively evict you from a room.

### 2.3 Rename "friend group" → "friending" ⚠️ needs a decision before scoping

**This is the one item in your list that isn't sized like the others — flagging it clearly rather than quietly scoping it small.**

**Today:** "friend group" isn't a UI label sitting on top of a pairwise-friend backend — it *is* the backend. `friend_groups` / `group_memberships` / `invite_codes` are the actual tables. A SECURITY DEFINER helper, `users_share_a_group(a, b)`, is what almost every other feature's RLS policy calls to decide "can these two people see each other's stuff at all": study room visibility, unlock-request visibility, temp-passcode eligibility (who you're even allowed to ask), daily-digest visibility, nudge permissions, friendship-settings inserts. `FriendsPage.tsx`'s own comment states the current definition outright: *"who is a friend has the same definition everywhere in this codebase: anyone sharing a group."*

There's no `profiles` table, no `friendships` table, no accepted/pending pairwise relationship concept anywhere — a "friend" today is 100% "someone in at least one of my groups."

**Two genuinely different things could satisfy this request, at very different costs:**

- **(A) Cosmetic relabel only** — keep the group mechanic exactly as it is, but stop showing "group" language in the UI. E.g., "Create a friend group" → "Add a friend"; a person who accepts your invite code just becomes a friend, with the 2-person group underneath entirely invisible. This works fine for the common case (inviting one person at a time) and touches only `AccountPage.tsx`'s copy/labels plus maybe auto-naming a new group after the person who joins it — no schema change, no RLS change, low risk. The rough edge: it still *behaves* like a group under the hood (a 3rd person could theoretically be invited into that same "friendship," which a pure 1:1 model wouldn't allow) — fine to leave as-is if nobody's actually hit that, but worth knowing it's there.
- **(B) A real pairwise friendship model** — a `friendships` table, friend requests, accept/decline, and `users_share_a_group()` replaced everywhere it's called (study rooms, unlock requests, temp passcodes, digests, nudges, friendship-settings — every one of those RLS policies would need to be rewritten and re-verified). This is not a v3.3-sized task by this codebase's own established rigor (every prior RLS change here has needed a dedicated migration, a fix round, and often a second fix round after that — see the `temp_passcode_requests`/`unlock_requests`/`daily_digests` history called out directly in migration 20260815000019's own comments). This is closer to a new major-version scope than a feature addition to v3.3.

**Recommendation:** ship (A) in v3.3 — it gets you the "this feels like friending, not group admin" outcome for near-zero risk. Treat (B) the way your own `V4_Scope_Summary.md` treats the aggregate-analytics dashboard: worth doing once real usage shows it's actually needed (e.g., once someone's hit the "wait, my friend and I are stuck sharing a group with a third person" edge case for real), not preemptively.

### 2.4 Add backend to "bunny name" and "human name"

**Today:** `BunnyTab.tsx` already has both fields, fully built — but they're `useState` calls with a code comment confirming it outright: *"Stub data - no backend exists for bunny stats yet... nothing here is persisted or sent via sendMessage."* This isn't a half-built feature, it's a placeholder UI with nothing behind it at all. Separately, three different files (`friendGroupApi.ts`, `LockedPage.tsx`, and by extension everywhere a friend is listed) independently note the same underlying gap: *"There is no `profiles` table in this schema... A future task that wants friend-facing display names would need a `profiles` table."* Every friend-facing surface in the app today shows a raw user UUID.

**Feasibility:** solid v3.3 candidate — well-scoped, and explicitly anticipated in the existing code's own comments.

**What it takes:**
- A new `profiles` table (`user_id` PK/FK → `auth.users`, `human_name text`, `bunny_name text`, `updated_at`).
- RLS: a user can read/write their own row; a group-mate can read it (reuse the existing `users_share_a_group()` helper — same pattern `study_rooms`' own visibility policy already uses, so this isn't a new security primitive, just a new consumer of one that already exists).
- A `profileApi.ts` + `PROFILE_GET`/`PROFILE_SAVE` message pair, following this codebase's existing convention exactly.
- Wire `BunnyTab.tsx`'s two existing inputs to actually save (small change, since the fields are already built).
- Replace raw-userId display with resolved `human_name` (falling back to the id when no profile exists yet — new users won't have set one) at every friend-facing call site: `NudgeSendForm`'s friend picker, `StudyRoomPanel`'s participant list, `TempPasscodePanel`/`UnlockRequestPanel`'s requester lines, `LockedPage.tsx`'s friend picker, `AccountPage.tsx`'s member list. That's roughly 6-8 call sites — each is a small, mechanical swap once a shared `useProfileNames()`-style lookup exists, but it is genuinely spread across most of the "friends" surface, so budget it as breadth, not depth.

**Drawback:** none structural — this is exactly the shape of change this codebase already has three separate load-bearing comments anticipating. The only real judgment call is whether a `human_name` should be unique/validated (recommend: no uniqueness constraint, it's a display label, not an identifier — the id remains canonical everywhere it matters for security).

### 2.5 Own video is too large in the study room

**Today, confirmed by reading the CSS, not guessed:** there is no styling at all for `.study-room-panel__grid` / `.study-room-panel__tile` / `.study-room-panel__media` anywhere in `sidepanel.css` or `global.css` — grepped both files directly. Every video/audio tile in a study room renders completely unstyled, at whatever size the browser gives an unconstrained `<video>` element: its own native/intrinsic resolution.

**Why this actually explains the reported bug, not just correlates with it:** your own camera's local preview and a remote peer's video aren't symmetric under the hood. `videoCallClient.ts` connects with `adaptiveStream: true` — LiveKit's adaptive-simulcast feature, which requests a *lower*-resolution stream layer for a remote peer's video based on how it's actually being displayed. Your own local camera preview isn't subject to that at all (there's no "layer" to adapt — it's your raw local capture). So with zero sizing CSS in place, a remote tile can end up rendering noticeably smaller than your own simply because LiveKit already scaled it down server-side, while your own camera stream renders at full native size. It's not a local-vs-remote CSS bug so much as a missing-CSS bug that happens to show up asymmetrically because of how adaptive streaming works.

**Feasibility:** trivial, pure CSS. Add real rules for the grid/tile/media classes — a responsive grid (`display: grid`, fixed tile aspect-ratio via `aspect-ratio: 16/9` or similar, `object-fit: cover` on the video/audio elements, a sensible `max-width`/`max-height`). This fixes both today's symptom and prevents the same class of "why does this participant's video look different" surprise from recurring for anyone else's resolution in the future — right now sizing is accidental, not designed.

**Recommendation:** bundle with 2.6 below — both are the same file, same `<style>` change plus one small handler edit.

### 2.6 Mirror the user's own video

**Today:** no mirroring anywhere — `event.element` (the local `<video>`) gets `.muted = true` set in the `track-added` handler in `StudyRoomPanel.tsx`, but nothing touches its transform.

**Feasibility:** trivial. Add `event.element.style.transform = "scaleX(-1)"` in the exact same `if (event.isLocal && event.element instanceof HTMLVideoElement)` branch that already sets `.muted`.

**Drawback to get right, not a blocker:** this must be a *display-only* mirror — applied to the local `<video>` element's own CSS transform, never to the outbound published track. LiveKit publishes and streams your camera's true (unmirrored) orientation to everyone else in the room; only your own self-preview element should be flipped. The existing code structure makes this easy to get right, since the local-only branch already exists for the mute logic — just extend it, don't touch anything that affects what's actually published.

### 2.7 Camera/microphone on/off toggle in the study room box, including before joining

**Today:** `videoCallClient.ts`'s `joinCall()` unconditionally calls `setCameraEnabled(true)` and `setMicrophoneEnabled(true)` the moment you connect — there's no way to join muted/camera-off, and no toggle once you're in the room either. The underlying LiveKit calls this would build on (`room.localParticipant.setCameraEnabled()`/`setMicrophoneEnabled()`) already exist and are already used — they're just not exposed as a live toggle.

**Feasibility:** two separate, both straightforward pieces:
- **In-room toggle:** export a small `setCameraEnabled(bool)`/`setMicrophoneEnabled(bool)` pair from `videoCallClient.ts` (the `Room` instance is already held module-scope), and add two buttons to `StudyRoomPanel.tsx`'s joined-room view.
- **Pre-join toggle:** thread optional `initialCameraEnabled`/`initialMicEnabled` params through `joinCall()`, driven by two toggles in the room-list view (before "Join" is pressed) rather than the hardcoded `true`/`true` today.

**Drawback / real nuance worth flagging:** the pre-join "camera off" case interacts with the Chrome side-panel `getUserMedia` limitation this codebase already has a documented workaround for (`OptionsApp.tsx`'s "Grant camera & microphone access" section, needed because a side panel can never itself show the permission prompt). Toggling camera *on* mid-room for the first time will still need that one-time grant if the user hasn't done it yet — pre-toggling to "off" doesn't remove that requirement, it just delays when it's hit. Not a blocker, just worth surfacing the same "open a tab to grant access" affordance `StudyRoomPanel.tsx` already has for the join-time media error, on the in-room toggle too.

## Section 3 — Other changes

### 3.1 Email verification is actually an 8-digit code, not 6

**Today:** `SignInForm.tsx` hardcodes the copy *"Check {email} for a 6-digit code."* — this is display text only; the actual OTP is generated and validated entirely by Supabase Auth's own email-OTP flow (`AUTH_REQUEST_OTP`/`AUTH_VERIFY_OTP`), not by any code in this repo. There's no `supabase/config.toml` in this project (confirmed — the `supabase/` directory only has `functions/` and `migrations/`), which means OTP length isn't managed as versioned config here at all; it's a Supabase project (dashboard) setting.

**Feasibility:** the code fix itself is a one-line copy change. The thing worth verifying before shipping it: confirm in the Supabase dashboard that the project's email-OTP length is actually set to 8 (not just that you'd like it to be) — since this repo has no record of that setting one way or the other, "6" being wrong in the copy is either stale copy that needs updating to match a config change already made, or a signal the dashboard setting itself needs to be changed too. Either way, the copy and the real backend setting need to agree; fixing only the string without confirming the dashboard value would just move the mismatch instead of closing it.

**Recommendation:** quick — verify the dashboard setting, then update the one string.

### 3.2 Password login instead of email verification every time

**Today:** sign-in is 100% OTP-only, via Supabase Auth's `signInWithOtp`/`verifyOtp`, hoisted into the shared `SignInForm.tsx` component used by both onboarding and `AccountPage.tsx`.

**Feasibility:** moderate, and genuinely additive rather than a replacement — Supabase Auth supports email+password on the same `auth.users` backing store, so this isn't a new auth system, it's a second credential type on the existing one.

**What it takes:**
- A "set a password" action (`supabase.auth.updateUser({ password })`) — most naturally offered on `AccountPage.tsx` once already signed in via OTP, since an account has no password until the user sets one.
- A password sign-in path (`supabase.auth.signInWithPassword({ email, password })`) alongside the existing OTP path in `SignInForm.tsx` — likely a toggle ("sign in with a code" vs. "sign in with a password") rather than replacing OTP outright, since first-ever sign-in for anyone who hasn't set a password yet still has to go through OTP (or a full password-based signup with its own email-confirmation step, which is more machinery for the same practical outcome).
- A forgot-password path — worth noting this one is nearly free: the existing OTP flow *is* a working password-reset mechanism (prove you own the email, then let them set/reset a password), so this doesn't need new infrastructure, just a slightly different entry point into what already exists.

**Drawback worth naming, not a blocker:** a password is a weaker per-sign-in guarantee than "just proved you own this email address right now" (OTP re-proves email ownership every time; a password doesn't). For this product's threat model — a personal study/accountability tool, not something holding financial or highly sensitive data — that trade-off is almost certainly fine, but it's worth being a deliberate choice rather than an assumed one.

## Section 4 — Permissions and passcodes

### 4.1 Temporary passcode → "request, accept, refresh, access granted" (no more code relay)

**This one is cheaper than it looks, because a sibling feature in this exact codebase already does precisely what you're describing.**

**Today, side by side:**
- **Unlock requests** (a *different*, already-shipped feature, for a permanent-for-the-session unlock): request → friend approves → done. No code. The requester's own client just re-reads the request's status; once it's `approved`, they're unlocked. `UnlockRequestPanel.tsx`/`unlockRequestApi.ts` — no code generation, no relay, nothing to type.
- **Temp passcodes** (the one you're asking to change, for a time-boxed unlock that auto re-locks): request → friend approves → server generates a 6-digit code and hands it *only* to the approving friend → the friend has to manually relay it (text, shout through a wall — literally the copy in `TempPasscodePanel.tsx`) → the requester pastes it into `LockedPage.tsx`'s redeem form.

`LockedPage.tsx` **already has a "Check status" refresh button** for a pending temp-passcode request (`handleRefreshTempRequestStatus`) — the refresh-and-see-it-resolve interaction you're asking for already exists as UI. The only thing standing between today's flow and your requested one is that when the status flips to `approved`, the current UI shows a code-entry form instead of just... unlocking.

**What it actually takes:** skip code generation in `approve-temp-passcode`'s Edge Function (or keep it server-side-only and simply never surface it to the friend), and when the requester's client sees their own request flip to `approved` (via the same refresh they already have, or — nicer — a live Realtime subscription instead of manual refresh, following the same pattern `study_room_participants`' presence already uses), call the unlock directly (`unlockHardBlockRuleForHostname` + `scheduleTempUnlockRelockAlarm` — both already exist and already get called today, just currently gated behind a successful code redemption instead of a status check). The re-lock/expiry behavior that makes this "temporary" rather than permanent (`TTL_MS`, the relock alarm) doesn't change at all — you're removing the human-relay step, not the time-boxing.

**Drawback worth naming honestly:** the code never actually added *access-control* security beyond what the approval step already provides — both `approve-temp-passcode` and `redeem-temp-passcode` already verify server-side that the caller really is the assigned friend / the real requester (via their JWT), which is the actual security boundary in both designs. What the code added was *friction* — a deliberate "hard mode" cost, consistent with hard-restricted sites being supposed to have some. Removing it makes the flow faster and less annoying, which is the whole point of the ask — just confirm that's an intentional trade-off for this specific feature (friction was arguably part of "hard mode" working as designed) rather than an accidental side effect of chasing convenience.

**Recommendation:** genuinely good value for the effort — reuses an existing, already-shipped pattern almost verbatim. One of the cheaper items on this whole list despite sounding like a flow redesign.

### 4.2 Add an option to request a temporary pass for ending a study session early

**Today:** `EndSessionControl.tsx` already gates early-ending on a *permanent* hard-block passcode when `session.restrictionMode === "hard"` — the same passcode set in the Options page's "Hard-block passcode" section, explicitly meant to be shared with a friend, not held by yourself. There's no *temporary*, per-request path for this at all — only the standing passcode.

**Feasibility:** good v3.3 candidate, but worth scoping accurately: this is closer in shape to an **unlock request** than to a **temp passcode**. A temp passcode is time-boxed and auto-relocks because it's granting access to something ongoing (a site, for the rest of a session); ending a session is a one-time, one-way action — there's nothing to "re-lock" afterward. Modeling it on the simpler `unlock_requests` pattern (a pending/approved/denied row, no code, no expiry machinery) is a better fit than dragging in the hashing/TTL/lockout infrastructure `temp_passcode_requests` needs for a genuinely re-lockable grant.

**What it takes:** a new request type — either a small dedicated table (`session_end_requests`: `session_id`, `requester_user_id`, `friend_user_id`, `status`), or a `purpose` column added to the existing `unlock_requests` shape if you'd rather not introduce a fourth accountability table — plus wiring `EndSessionControl.tsx`'s hard-mode gate to accept "an approved end-session request exists" as an alternative to "the permanent passcode was entered." Recommend making this opt-in via a settings toggle (`userSettings.ts` already has this exact pattern for other social features, e.g. `friendSyncEnabled`) rather than mandatory for every hard-restricted session — some users may genuinely want the permanent-passcode-only flow to stay as the *only* way out, precisely because it can't be requested from inside the session itself.

### 4.3 Add a message field when requesting a temp pass, so the friend can judge the excuse

**Today:** `temp_passcode_requests` carries no free-text field at all — `TempPasscodePanel.tsx`'s friend-facing view shows only *"{requesterUserId} wants a temporary passcode for {hostname}"*, nothing else to go on.

**Feasibility:** small and low-risk — the most contained item in this whole list.

**What it takes:** one new nullable `message text` column on `temp_passcode_requests`, a text input added to the request-creation flow in `LockedPage.tsx` (next to the existing friend picker), passed through `TEMP_PASSCODE_CREATE`'s payload, and displayed alongside the hostname in `TempPasscodePanel.tsx`'s request list. No RLS changes needed beyond making sure the column is included in the same explicit column allowlist `tempPasscodeApi.ts` already uses everywhere (this codebase is already disciplined about that — see `TEMP_PASSCODE_COLUMNS`'s comment on why it's a literal list, not a bare `select()`).

**Worth considering, not required:** the same small addition would fit `unlock_requests` too, for consistency — a friend deciding whether to approve an unlock request has exactly the same "why do you need this" question today, with even less context than the temp-passcode flow currently gives.

## Suggested grouping for v3.3

Roughly cheapest-and-lowest-risk to most involved, based on what's actually in the codebase today rather than how the ask reads on paper:

1. **Free/trivial, no backend:** 1.1 (move panels), 2.5 + 2.6 (video sizing + mirroring, same file), 3.1 (copy fix, pending a dashboard check).
2. **Small, contained backend additions:** 1.2 (options-page launcher buttons), 4.3 (message field), 2.1 (archive a room), 2.7 (camera/mic toggle).
3. **Real features, well-precedented by existing patterns:** 4.1 (temp passcode refresh-to-unlock — cheaper than it sounds, reuses `unlock_requests`' shape), 4.2 (temp pass to end early — same reuse), 2.4 (bunny/human name backend — three separate comments in the existing code already anticipate exactly this).
4. **Real backend + RLS work, budget accordingly:** 2.2 (per-room friend visibility) — genuine new access-control surface, but a contained one.
5. **Needs a product decision before it gets scoped at all:** 2.3 (friend-group rename) — ship the cosmetic version (2.3-A) in this bucket; treat the real pairwise-friendship model as its own future scope, not a v3.3 line item.

## Open questions worth deciding before implementation starts

- **2.3:** cosmetic relabel now, or is a real pairwise-friendship rebuild actually wanted sooner rather than later? (Recommend: cosmetic now.)
- **2.2:** does restricting a room's visibility retroactively affect people already in it, or only future joins? (Recommend: future joins only.)
- **4.2:** should the temporary end-session-early pass be opt-in per user, or does it replace the permanent-passcode gate outright once available? (Recommend: opt-in toggle, permanent passcode stays available as the non-requestable fallback.)
- **3.1:** is 8 digits already live in the Supabase dashboard, or does the dashboard setting need to change too? (Can't be answered from the codebase — needs a look at the actual project config.)
