# SnuffleStudy V3.3 Scope Summary — Sidepanel Consolidation, Friend-Scoped Rooms, Passcode Simplification

**Purpose of this document:** the definite v3.3 scope, following the decisions made against `docs/scope_summaries/V3.3_Feature_Feedback.md` (that document has the full reasoning, drawbacks, and file-level grounding behind each call below — it isn't repeated here). This document states what gets built, not why.

---

## Section 1 — Rearranging locations of things

1. **Move Temporary passcode requests + Unlock requests into the Friends tab.** `FriendsTab.tsx` renders `<StudyRoomPanel>` and `<FriendGroupPanel>` today; add `<TempPasscodePanel onClose={() => {}} />` and `<UnlockRequestPanel session={null} onClose={() => {}} />` below them, in that order. `SettingsTab.tsx` loses both — its content is fully replaced by item 2 below.

2. **Rebuild the sidepanel's Settings tab as a real embedded surface for Settings / Account / Friends / History, in that order — except camera/microphone access, which stays a full-tab-only action.**
   - Extract `OptionsApp.tsx`'s inline "Settings" view into its own component (`SettingsPage.tsx`) — everything currently in that view (Tracking, Friends/share-activity checkbox, Notifications, Default restricted sites, Hard-block passcode) **except** the "Camera & microphone access" section. Same `SETTINGS_GET`/`SETTINGS_SAVE`/`HARD_BLOCK_SET_PASSCODE` messages, no behavior change.
   - `OptionsApp.tsx`'s own "settings" nav view becomes `<SettingsPage />` followed by the camera/microphone section (unchanged in place, still requiring a real full tab per Chrome's `getUserMedia` limitation) — so Options itself is functionally identical to today.
   - Add a small in-tab sub-nav to the sidepanel's `SettingsTab.tsx`, mirroring `OptionsApp.tsx`'s own nav-button/`view`-state pattern: **Settings** (default), **Account**, **Friends**, **History**.
     - **Settings** renders `<SettingsPage />` plus one callout button, "Grant camera & microphone access →", which calls `chrome.runtime.openOptionsPage()`.
     - **Account** renders `<AccountPage />` directly — already fully self-contained (sign-in/out, delete account, friending — see Section 2 item 4 — no full-tab dependency).
     - **Friends** renders `<FriendsPage onSignInClick={...} />` directly.
     - **History** renders `<HistoryPage />` directly.
   - `AccountPage.tsx`/`FriendsPage.tsx`/`HistoryPage.tsx` are reused as-is from `src/options/pages/` (imported into the sidepanel, not duplicated).

## Section 2 — Friends flow

1. **Add/remove study rooms you created (archive, not delete).** Add `archived_at timestamptz` to `study_rooms`, an RLS `UPDATE` policy scoped to `owner_user_id = auth.uid()`, and filter `listRooms()` to `archived_at is null`. Add an owner-only "Archive this room" action in `StudyRoomPanel.tsx`'s room list. No hard delete — `producer_tag_sends.recipient_room_id` references `study_rooms.id`, and archiving preserves that history instead of fighting the foreign key.

2. **Study rooms become invite-only — no more automatic access for anyone who shares a group with the owner.**
   - New `study_room_invitees` table: `room_id`, `user_id`, `invited_by`, `invited_at`, primary key `(room_id, user_id)`.
   - `study_rooms`' SELECT policy and `study_room_participants`' INSERT policy (both from migration `20260815000019`) drop their `users_share_a_group(owner_user_id, auth.uid())` clause entirely and instead check `study_room_invitees` — owner, already-a-participant, or explicitly invited; nothing else.
   - Migration for existing rooms: backfill `study_room_invitees` from each room's current `study_room_participants` rows, so nobody already active in a room loses access when this ships. Nothing else changes retroactively — restricting a room going forward only affects future joins.
   - Owner-only "manage room access" UI on a room you created: add/remove specific friends, sourced from your current friend list (i.e. group members — see item 4 below on why that's still the source of truth this version). New messages: `STUDY_ROOM_INVITEE_ADD`, `STUDY_ROOM_INVITEE_REMOVE`, `STUDY_ROOM_INVITEES_LIST`, all authorized to `owner_user_id = auth.uid()` only.
   - Room creation itself is unchanged (doesn't block on picking invitees first) — a freshly created room simply has no invitees until the owner adds some.

3. **Rename "friend group" to friending — cosmetic only this version; the underlying group mechanic is unchanged.** The rest of the friending rebuild (a real pairwise-friendship model replacing `friend_groups`/`group_memberships`) is out of scope for v3.3 and picked up in a future version.
   - `AccountPage.tsx`: "Create a friend group" + "Generate invite code" collapse into one "Invite a friend" action — drop the visible group-name field (auto-name the underlying group), one click creates the group and immediately generates the invite code. "Join a friend group" → "Add a friend" (same invite-code entry form, relabeled). "Group members" → "Your friends" (same list, relabeled; still keyed by the underlying group id under the hood).
   - Relabel every other user-facing "group" string to "friend" language: `UnlockRequestPanel.tsx`'s "Ask a friend in your group to unlock a site" → "Ask a friend to unlock a site"; `LockedPage.tsx`'s "join a group first" → "add a friend first"; and equivalents anywhere else "group" appears in copy (`FriendsPage.tsx`, `FriendGroupPanel.tsx`, `TempPasscodePanel.tsx`).
   - No schema or RLS change — `users_share_a_group()` keeps backing every permission check exactly as it does today.

4. **Backend for "bunny name" and "human name."** `BunnyTab.tsx`'s two fields already exist as pure local stub state — wire them to a real backend and use `human_name` everywhere a raw user id is shown today.
   - New `profiles` table: `user_id` (PK, FK → `auth.users`), `human_name text`, `bunny_name text`, `updated_at`. RLS: a user can read/write their own row; a group-mate can read it (reuse `users_share_a_group()`).
   - New `profileApi.ts` + `PROFILE_GET`/`PROFILE_SAVE` messages, following this codebase's existing `*Api.ts`/message-pair convention.
   - Wire `BunnyTab.tsx`'s existing `bunnyName`/`humanName` inputs to save via `PROFILE_SAVE` and load via `PROFILE_GET` on mount.
   - Replace raw-userId display with resolved `human_name` (falling back to the id when no profile row exists yet) at: `NudgeSendForm`'s friend picker, `StudyRoomPanel`'s participant list, `TempPasscodePanel`/`UnlockRequestPanel`'s requester lines, `LockedPage.tsx`'s friend picker, `AccountPage.tsx`'s friend list (item 3 above), and Section 2 item 2's room-invitee picker/list. `bunny_name` is stored only — no display surface anywhere this version, per the original ask.

5. **Fix study-room video sizing.** Add real CSS for `.study-room-panel__grid` / `.study-room-panel__tile` / `.study-room-panel__media` (currently entirely unstyled in both `sidepanel.css` and `global.css`) — a responsive grid, a fixed aspect-ratio per tile (e.g. `aspect-ratio: 16/9`), `object-fit: cover` on the video/audio element, and a sensible max size. Applies uniformly to every tile, local and remote alike.

6. **Mirror the user's own video.** In `StudyRoomPanel.tsx`'s `track-added` handler, in the existing `event.isLocal && event.element instanceof HTMLVideoElement` branch (where `.muted = true` is already set), also set `event.element.style.transform = "scaleX(-1)"`. Display-only — the outbound published track (what everyone else sees) is untouched.

7. **Camera/microphone on/off toggle, in-room and before joining.**
   - Export `setCameraEnabled(enabled: boolean)` / `setMicrophoneEnabled(enabled: boolean)` from `videoCallClient.ts`, wrapping the already-used `room.localParticipant.setCameraEnabled`/`setMicrophoneEnabled` LiveKit calls.
   - Add two toggle buttons to `StudyRoomPanel.tsx`'s joined-room view, wired to the new exports.
   - Add `initialCameraEnabled`/`initialMicEnabled` params to `joinCall()` (default `true`/`true`, preserving today's behavior), driven by two toggles in the room-list view (before "Join" is pressed).
   - The joined-room view's existing "open a tab to grant access" affordance (for the Chrome side-panel `getUserMedia` limitation) also covers turning a toggle on mid-room for the first time, not just the join-time case.

## Section 3 — Other changes

1. **Email verification copy: 8-digit code, not 6.** One-line change in `SignInForm.tsx`: *"Check {email} for a 6-digit code."* → *"Check {email} for an 8-digit code."* Nothing else in this flow changes.

2. **Password login, alongside OTP — separate account-creation and sign-in flows, matching a regular sign-up/log-in.**
   - `SignInForm.tsx` gets an explicit top-level choice — **"Create account"** or **"Sign in"** — since the two flows below genuinely diverge, rather than one unified email-and-code form.
   - **Create account:** email → request code → verify code (`AUTH_REQUEST_OTP`/`AUTH_VERIFY_OTP`, unchanged) → **then, before the account is considered set up,** a required password step: two password fields ("Password" / "Confirm password"), submit disabled until they match, saved via a new `AUTH_SET_PASSWORD` message (`supabase.auth.updateUser({ password })`). Signup isn't complete until this step succeeds — there is no "skip the password" option here. Password strength itself (minimum length, etc.) is enforced by Supabase Auth's own project-level password policy, not by this codebase beyond the two-field match check.
   - **Sign in:** an existing user is offered both options as equal peers, not a fallback path — **"Sign in with a password"** (email + password, `supabase.auth.signInWithPassword`) and **"Email me a code"** (today's OTP request/verify flow, unchanged), with no password step tacked onto the end of the OTP path here — signing in via a code for an account that already has a password just signs them in, exactly like the code-based flow already works today.
   - `AccountPage.tsx` keeps a "set/change your password" action for an already-signed-in user — this becomes the recovery path for any account created before this feature shipped (no password yet) and the normal way to change one later, not the primary way a password gets set going forward.
   - Forgot-password: use the "Email me a code" sign-in path to get back in, then set a new password from `AccountPage.tsx` — proving email ownership via OTP is already a working reset mechanism, so no separate "forgot password" infrastructure is needed.
   - Onboarding's sign-in step (`OnboardingWizard.tsx`) renders the same `SignInForm`, so it gets both the Create-account/Sign-in choice and the mandatory password step automatically — "Skip for now" stays available at every step exactly as it is today.

## Section 4 — Permissions and passcodes

1. **Temporary passcode: approve → refresh → unlocked. No code generated, none relayed, none typed.**
   - `approve-temp-passcode`'s Edge Function stops generating/hashing a code entirely — it just flips the request to `approved` (with the existing `expires_at`/TTL fields, unchanged).
   - The requester's client (already polling via `handleRefreshTempRequestStatus` in `LockedPage.tsx`) detects `status === "approved"` and calls the unlock directly — `unlockHardBlockRuleForHostname` + `scheduleTempUnlockRelockAlarm`, both already used today, just no longer gated behind a code-redemption round trip.
   - `LockedPage.tsx`'s code-entry form for temp passcodes is removed; the "approved" state shows the unlock happening immediately instead.
   - `redeem-temp-passcode` and the PBKDF2 hashing machinery (`code_hash`/`code_salt`, `hashCode`/`randomSalt` in both Edge Functions and `hardBlockCredential.ts`'s port) are no longer needed for this flow and can be removed once this ships. Re-lock/expiry behavior (`TTL_MS`, the relock alarm) is unchanged — this only removes the human-relay step, not the time-boxing.

2. **A "request a temporary pass" button on the end-session passcode screen — does not replace the permanent passcode.**
   - New `session_end_requests` table, modeled directly on `unlock_requests` (no assigned friend — any group-mate can resolve it, first-responder-wins): `id`, `session_id`, `requester_user_id`, `status` (`pending`/`approved`/`denied`), `requested_at`, `resolved_at`, `resolved_by`. RLS mirrors `unlock_requests`' policies exactly.
   - New messages: `SESSION_END_REQUEST_CREATE`, `SESSION_END_REQUEST_RESOLVE`, `SESSION_END_REQUESTS_FETCH`.
   - New `SessionEndRequestPanel.tsx` (one small component per friend-feature, matching this codebase's existing convention), composed into `FriendsTab.tsx` alongside the panels moved in Section 1 item 1 — shows pending requests from friends with Approve/Deny.
   - `EndSessionControl.tsx`'s hard-mode prompt (the passcode-entry form shown on ending a hard-restricted session early) gets a second button, **"Request a temporary pass from a friend,"** alongside the existing passcode input/submit/cancel. Clicking it fires `SESSION_END_REQUEST_CREATE` and shows an inline pending/approved status (mirroring `LockedPage.tsx`'s existing inline request-status block) with a refresh action.
   - Once approved, the same prompt shows an "End session now" button that calls `SESSION_END` with the approved request's id instead of a passcode (`payload: { sessionId, endRequestId }`) — `messageRouter.ts`'s `SESSION_END` handler accepts either a valid passcode **or** a valid approved `session_end_requests` row for that session/requester, verified server-side. The permanent hard-block passcode path is completely unchanged and stays available side by side.

3. **A message field on temporary passcode requests, so the friend can judge the excuse.**
   - New nullable `message text` column on `temp_passcode_requests`, added to `TEMP_PASSCODE_COLUMNS`'s explicit column list in `tempPasscodeApi.ts`.
   - A text input added to the request-creation flow in `LockedPage.tsx` (next to the existing friend picker), passed through `TEMP_PASSCODE_CREATE`'s payload.
   - Displayed in `TempPasscodePanel.tsx`'s request list, alongside the existing hostname line.

## Definition of done for V3.3

The sidepanel's Settings tab hosts Settings/Account/Friends/History directly, with only the camera/microphone grant still requiring a trip to the full Options tab; Temporary passcode requests and Unlock requests live in the Friends tab. A study room is visible and joinable only by its owner, current participants, and explicitly invited friends — not by default to an entire shared group — and no one already active in a room loses access when this ships. "Friend group" language is gone from the UI; the invite/join/member flow reads as friending, on the same underlying mechanic. Bunny name and human name persist to a real backend, and every friend-facing surface shows a human name instead of a raw id wherever one has been set. Study-room video tiles render at a consistent, deliberate size for every participant, the local preview is mirrored, and camera/microphone can be toggled both before and during a call. The sign-in code prompt correctly says 8 digits. Creating a new account requires verifying a code and setting a matching password before it's usable; signing into an existing account offers a password or a fresh code as equal options. A temporary passcode request goes from approved to unlocked with a refresh — no code is generated, relayed, or typed. Ending a hard-restricted session early can be done with the permanent passcode (unchanged) or by requesting and receiving a temporary pass from a friend, without leaving that same screen. A temporary passcode request can carry a short message explaining why it's needed.
