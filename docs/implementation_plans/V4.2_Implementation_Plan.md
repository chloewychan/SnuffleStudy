# SnuffleStudy V4.2 Implementation Plan — New Frontend Integration

**Source:** `frontend-backup/` (a Vite + React 19 + CSS-modules UI, confirmed 100% static — zero `chrome.*`/`fetch`/`supabase`/`sendMessage` references anywhere, only one file with any interactivity at all) and this session's mapping conversation. There is no separate scope-summary document for this version — the mapping below **is** the scope, confirmed directly against both trees rather than assumed.

**Method:** for every screen, the *logic* already exists and is correct — it shipped in v4.1. The *markup* is what changes. Per component: keep every hook call, `sendMessage()` call, and handler from the current file; delete its JSX; graft in the matching `frontend-backup` component's JSX/CSS module, bound to that same state and those same handlers instead of hardcoded placeholder text. Never re-derive data-layer behavior from scratch — every task below names the exact current file whose logic survives unchanged.

**Not in scope:** `frontend-backup`'s own routing (`App.tsx`'s one-route-per-screen model). Confirmed by you: it was scaffolding to preview screens in isolation, not the intended composition. The real composition is `SidePanelApp.tsx`'s existing state-driven shell (`activeTab` picks one tab; `AppFooter` is always mounted and shows/hides itself based on real state) — every task below slots a re-skinned component into that shell, none of them re-introduce routing.

---

## Goal

Replace every hand-rolled presentation component in the v4.1 sidebar with its `frontend-backup` equivalent, keeping 100% of the existing data layer intact: `StudyRoomSessionProvider`, `RefreshRegistryProvider`, `useIncomingActivity`, `useNudgeVaultItems`, `useDisplayNames`, `SignInForm`, `ProducerTagRecorder`, and every `sendMessage()` call in every current component, unchanged. When finished, the extension looks like `frontend-backup`'s design and behaves exactly as it does today — no new features, no new messages, no new backend, except where a Decision below explicitly says otherwise.

## Architecture

Unchanged. Still a WXT Chrome MV3 extension; still one `messageRouter.ts` switch as the sole backend entry point; still the v4.1 app-shell contexts (`StudyRoomSessionContext.tsx`, `RefreshRegistryContext.tsx`) mounted once in `SidePanelApp.tsx`. This version touches only `snufflestudy/src/sidepanel/components/*`, `snufflestudy/src/options/pages/*`'s JSX, and the WXT entrypoints' asset/build wiring — never `background/`, `infrastructure/backend/*Api.ts`, or `shared/messages.ts`.

## Tech Stack addition

CSS Modules (frontend-backup's styling mechanism) **replace** the old global-CSS rules for every re-skinned component — this is a removal, not an addition alongside the old system. `@mui/x-date-pickers` is retained for exactly one component (`HistoryPage.tsx`'s date-range filter, Decision 8) — no other MUI package is used anywhere else in the app.

## Global Constraints

- Every screen keeps calling the exact same `sendMessage()` types it calls today. If a task below can't find a real data source for a piece of `frontend-backup` markup, it says so as an open item — it never invents a new message to fill the gap.
- **No old-frontend styling or markup survives anywhere this plan touches — including surfaces with no Figma-built equivalent.** Per your direction: everything either matches a real `frontend-backup` screen, or, where none exists (Decision 5's `RequestUnlockForm`, Task 12's delete-account confirmation, Task 13's expanded event log), is built fresh from the new design system's own components, colors, spacing, and tokens — never left in its pre-v4.2 plain-CSS form. Each task deletes the old CSS selectors/classnames it replaces (named in that task's Steps) once its replacement is verified working, not left dead-but-loaded. Task 14 grep-checks that no old classname survives anywhere in the final build.
- `frontend-backup`'s images are referenced as absolute paths (`/icon-refresh.svg`, `/Bunny-and-Book@2x.png`, etc., under its own `public/`). These do not resolve inside a packed extension page. Every task that touches an `<img src="/...">` replaces it with a WXT-resolvable asset (mirroring `Header.tsx`'s existing `chrome.runtime.getURL("sidepanel/bunny-and-book.png")` pattern) as part of that same task — not deferred to a cleanup pass.
- `frontend-backup` renders `HeaderBar`/`NavigationBar` inside every one of its own page components (`BunnyPage.tsx`, `StudyPage.tsx`, `FriendsPage.tsx`, `SettingsPage.tsx` each import and mount both). Do not carry that forward — see Decision 1. Only the *content* below the header/nav in each of those page files maps onto its current-frontend tab; the header/nav themselves map onto the shell-level `Header.tsx`/`TabBar.tsx`, once.
- Accessibility attributes already present on current components (`TabBar.tsx`'s `role="tablist"`/`role="tab"`/`aria-selected`/`aria-controls`, `HistoryPage.tsx`'s `aria-expanded`, various `role="alert"`) carry forward onto the new markup. `frontend-backup`'s own markup has none of these — each task adds them, it doesn't just copy the skin as-is.
- **Study rooms are joined only by owner-granted access.** Per your confirmation: there is no code-based join mechanism, now or planned — `STUDY_ROOM_INVITEE_ADD` (via the Friends box) is the only way a friend gains access to a room. Nothing in this plan builds, stubs, or leaves room for a join-by-code path.

## Decisions

Judgment calls made once here so no task improvises one independently. Each flagged **(overridable)**.

1. **`HeaderBar`/`NavigationBar` render once, at the shell level — not once per tab page, as `frontend-backup`'s own files structure it.** Every `frontend-backup` page (`BunnyPage.tsx`, `StudyPage.tsx`, `FriendsPage.tsx`, `SettingsPage.tsx`) imports and mounts both itself. Following that literally would duplicate the header/nav on every tab switch (a fresh mount, fresh `AUTH_GET_SESSION` fetch, fresh refresh-registry churn each time) instead of the one persistent instance `SidePanelApp.tsx` already maintains. Task 2 re-skins `Header.tsx`/`TabBar.tsx` once; every other task's re-skinned tab component starts from `frontend-backup`'s page file *minus* its `HeaderBar`/`NavigationBar` import and JSX. **(overridable — say so if per-tab remounting is actually wanted for some reason; not recommended.)**

2. **`FriendDetailsPopup`'s checkbox list drops "Receive a daily digest about this friend."** The static design shows all eight of the pre-v4.1 checkboxes — it was built before the daily-digest checkbox was removed from `FriendSettingsFields`. Task 9 renders the popup with the current, already-reduced seven-field list, not an eight-field one — reusing the existing component is what makes this automatic, but it's called out since it means Task 9 does not copy this file's JSX 1:1. **(not overridable without reintroducing a field the current data model no longer has — `FriendshipSettingsPatch` has no `receiveDailyDigest` key to bind an eighth checkbox to.)**

3. **`StudyRoomPopup` shows only currently-invited friends, each with a remove-only action — no add-toggle.** The design shows a flat list of already-in-the-room friends with a trash icon each, and nothing resembling "invite someone not yet added." Granting access already has a home: the Friends box's existing bulk "Add to room" action (`STUDY_ROOM_INVITEE_ADD`, v4.1 Task 9). This popup becomes a thinner view than today's `ManageAccessSection` (which lists every friend with an add/remove toggle) — a real behavior narrowing, not just a re-skin: it reads `STUDY_ROOM_INVITEES_LIST` and offers only `STUDY_ROOM_INVITEE_REMOVE` per row. **(overridable — say so if the popup should keep the full add/remove toggle instead, rendered in this new visual shell.)**

4. **Settled — no join-by-code feature, anywhere, ever: rooms are joined only when the owner adds you.** Confirmed directly, not a guess: the second `InputCreateStudyRoom` instance in `StudyRoomsPanel.tsx` ("Join Study Room" / "E.g., Room code") is removed from the frontend entirely, not merely left unwired. Task 5 ports only the "Create Study Room" input; the "Join Study Room" one is never built, never referenced, and never appears in the shipped component. Access continues to work exactly as it does today — the owner grants it via `STUDY_ROOM_INVITEE_ADD` (Friends box), and that stays the *only* path in. **(settled, not overridable — this is a confirmed product decision, not a placeholder pending confirmation.)**

5. **`RequestUnlockForm` (the mid-session "ask a friend to unlock a site" form) is rebuilt from the new design system, not carried forward in its old visual form.** Nothing in `frontend-backup` corresponds to it — `ActiveStudySessionPage.tsx` composes only `HeaderBar` + a goal heading + `ActiveSession`. Per the "no visible evidence of the old frontend" constraint, Task 7 composes it fresh out of the same building blocks the rest of the design already uses — `ButtonLarge` for its actions, `TextInput` for the hostname field, the same card/section shell `ActiveSession` itself uses for structure and spacing — rather than mounting the old plain-HTML version unchanged. There is no dedicated Figma frame for this specific form, so its exact layout (which fields go where, how the blocked-hostname suggestion buttons are arranged) is composed using the design system's existing patterns, not invented arbitrarily. **(overridable — flag if you'd rather wait for a dedicated frame instead of composing one from existing primitives now.)**

6. **Static checkbox-like elements are re-skinned as real, independently-toggleable controls; the one genuinely mutually-exclusive pair (tracking tier) is wired as a real radio pair.** Several "checkbox" and "radio" inputs across the design are either plain `<img>`s with no input element at all (`ButtonBoolIcon`-based ones — `FriendDetailsPopup`'s permission list, `TaskVaultPanel`'s "check" submit icon) or `<input type="radio">` with no shared `name` (Task Vault's per-task toggle, `TrackingSettings`' Activity-only/Detailed pair) — meaning none of them are functionally grouped today regardless of the `type` attribute used. Each task wires real semantics to match the *actual* underlying choice: independent toggles stay independent (Task Vault's per-task done state, the seven friend-permission checkboxes, `activityTrackingEnabled`), and the one real either/or choice (`trackingTier`) is wired as `checked`/`onChange` against one shared value, matching `SettingsPage.tsx`'s current, already-correct radio pair. **(overridable per-field if you want the visual literally unchanged; not recommended for the tracking-tier pair specifically, since that one is a real constraint, not a style choice.)**

7. **"Grant Camera & Microphone Access" opens the full Options tab; it does not call `getUserMedia()` inline.** A hard, previously-documented platform constraint: Chrome cannot show that permission prompt from the side panel at all. Task 11 wires this button to the exact same `chrome.runtime.openOptionsPage()` call `SettingsTab.tsx`'s current callout already uses. **(not overridable — this is a Chrome limitation, not a design choice.)**

8. **`HistoryPage.tsx`'s date-range filter keeps the MUI `DatePicker` — the one deliberate MUI dependency in the whole app.** Per "follow the design perfectly where possible": this is what the design specifies for this one field, and it's the one place `frontend-backup` actually uses `@mui/x-date-pickers` for something real (everywhere else, MUI's `ThemeProvider`/`CssBaseline` from `index.tsx` is unused scaffolding — see Task 1). `LocalizationProvider` wraps only this component's own subtree, not the whole app. Its `onChange` converts the picked `Date | null` into the `YYYY-MM-DD` strings `sinceDate`/`untilDate` already expect — no change to `HistoryPage.tsx`'s own query logic. **(overridable — drop MUI entirely and use plain `<input type="date">`, matching every other date-ish field in the app, if you'd rather not carry the one MUI dependency forward.)**

9. **`HistoryPage.tsx`'s expanded per-session event log has no design to follow — it's built fresh from the new design system's own components and tokens, not copied from the old plain-CSS version at all.** The design only shows the collapsed row (goal, date, an "options" icon). Per the "no visible evidence of the old frontend" constraint: the expanded state uses the same colors, spacing scale, and component choices (e.g. `TextSmall` for the distraction-attempts/recoveries summary, list styling matching the collapsed rows above it) as the rest of `SessionHistory.module.css` — none of `HistoryPage.tsx`'s current `history-page__event-*` classnames survive. This is the one place this version does original layout work rather than pure transplantation, since there's nothing to transplant. **(overridable — flag if the collapsed-only view is fine and expansion should just go away.)**

## Scope

**In scope:** re-skinning all fourteen surfaces listed in Build order below, using `frontend-backup`'s design pixel-for-pixel within each screen, composed via the current shell's state-driven model (not `frontend-backup`'s routes).

**Explicitly out of scope:**
- Any new backend message, table, or column. If a piece of `frontend-backup` markup has no current data source, it's logged as an open item (see Decision 9), never quietly backed by an invented endpoint.
- A join-study-room-by-code feature of any kind (Decision 4) — confirmed **not wanted**, not merely deferred. Rooms are owner-invite-only; nothing in this plan builds, stubs, or leaves an opening for a code-based join path.
- Any behavior change beyond the two narrow, explicitly-called-out ones in Decisions 3 and 6.
