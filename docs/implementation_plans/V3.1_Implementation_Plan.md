# SnuffleStudy V3.1 Implementation Plan

**Goal:** Add a skippable sign-in step to onboarding, and gate the one social entry point `docs/V3.1_Scope_Summary.md` scopes for this pass (the Friends tab in Settings) behind it — the smallest slice of `docs/V3_Scope_Summary.md`'s auth-in-onboarding item that's demoable and buildable in one session, for hackathon submission.

**Architecture:** No changes. This plan touches only existing presentation-layer components (`OnboardingWizard.tsx`, `FriendsPage.tsx`, `OptionsApp.tsx`) and calls message types that already exist, are already implemented in `messageRouter.ts`, and are already proven working end-to-end in `AccountPage.tsx` (`AUTH_REQUEST_OTP`, `AUTH_VERIFY_OTP`, `AUTH_GET_SESSION`). No new domain types, no new backend endpoints, no new dependencies, no new files.

**Tech Stack:** Unchanged from v2 — Supabase Auth via the existing extension-side message contract. Nothing here talks to Supabase directly; both tasks below go through the same `sendMessage` → `messageRouter.ts` → `supabaseClient.ts` path `AccountPage.tsx` already uses.

Per `docs/Implementation_Plan_Guidelines.md`: this plan is deliberately light, not as a corner cut but because the work genuinely is well-scoped and low-risk — every message contract involved is pre-existing, already tested, and already live in `AccountPage.tsx`. There's no unresolved third-party API surface and no new security boundary; this is UI relocation and duplication, not new logic. Exact call syntax is given only where it's a straight copy of what `AccountPage.tsx` already does correctly.

## Global Constraints

Everything from `docs/V2_Implementation_Plan.md`'s Global Constraints still applies unchanged (no API key ships client-side, friend-visible data stays field-gated, etc. — none of it is touched by this plan). New, and explicitly temporary, for V3.1 only, per `docs/V3.1_Scope_Summary.md`'s own stated rigor cut:

- No new automated tests are required for either task below. Every other `OnboardingWizard` step has a test; this one won't, for now — `docs/V3.2_Scope_Summary.md` closes that gap.
- Duplicating OTP form logic between `OnboardingWizard.tsx` and `AccountPage.tsx`, rather than extracting a shared component, is accepted for this pass. Do not spend session budget on that extraction here — `docs/V3.2_Scope_Summary.md` owns it.
- Manual, by-hand verification (click through both paths once) is the bar for "done" on this plan. No live/scripted two-account verification is in scope here.

## Decisions

Both already made in `docs/V3.1_Scope_Summary.md`; restated here so they're not re-litigated mid-build:

1. **Step position:** the new sign-in step goes immediately after `WelcomeScreen`, before the existing `"name"` step — first thing onboarding asks, after the purpose framing.
2. **Copy is fixed, not a placeholder:** *"Sign in to use friends, rooms, nudges, approvals, and synced accountability features."* Use it verbatim.
3. **Skippable, unconditionally.** "Skip for now" always continues onboarding exactly as it does today; a signed-out user completes onboarding with no degraded experience for the local-only product.
4. **Exactly one gated entry point for this pass: the Friends tab in Settings** (`OptionsApp`'s `view === "friends"`, rendering `FriendsPage.tsx`). Nudge-send, Study Room join, digest view, and temp-passcode request are explicitly *not* gated in this plan — they already work fine for a signed-in user and are left alone for a signed-out one. `docs/V3.2_Scope_Summary.md` finishes those.

## Scope

**In scope:**
- Task 1: a skippable sign-in step in `OnboardingWizard.tsx`.
- Task 2: an actionable sign-in prompt on `FriendsPage.tsx` when signed out.

**Explicitly out of scope, deferred to `docs/V3.2_Scope_Summary.md`:**
- Extracting a shared `<SignInForm />` (or equivalent) used by both `AccountPage.tsx` and the new onboarding step.
- Gating any entry point other than the Friends settings tab (nudge-send, Study Room join, digest view, temp-passcode request).
- Automated test coverage for the new onboarding step.
- Live/scripted two-account verification of any of this.
- Handling a user closing the tab mid-OTP-verification beyond what "Skip for now" already covers (no new "resume later" state).
- Anything else in `docs/V3_Scope_Summary.md`'s six items (items 1–4 and 6) — untouched by this plan, on purpose.

No phases — the two tasks are independent (both call only pre-existing, already-shipped `AUTH_*` messages) and can be built in either order or in parallel. Suggested order: Task 1 first, since it's the actual flow a demo walks through; Task 2 second, a five-minute follow-up.

## Task 1: Skippable sign-in step in onboarding

**Goal:** Insert a sign-in step into `OnboardingWizard.tsx`, positioned right after the Welcome screen, using the fixed copy from the Decisions section above, reusing `AUTH_REQUEST_OTP`/`AUTH_VERIFY_OTP` directly with duplicated local logic (no shared component, per this plan's accepted V3.1 shortcut).

**Depends on:** nothing. `AUTH_REQUEST_OTP`, `AUTH_VERIFY_OTP`, and their handlers in `messageRouter.ts` already exist and are already proven live via `AccountPage.tsx`.

**Interfaces:**
- Consumes: `{ type: "AUTH_REQUEST_OTP"; payload: { email: string } }` and `{ type: "AUTH_VERIFY_OTP"; payload: { email: string; token: string } }` (`shared/messages.ts`) — same two messages `AccountPage.tsx`'s `handleRequestOtp`/`handleVerifyOtp` already call, same response shapes (`{ ok: boolean; error?: string }` and `{ ok: boolean; session?: AuthSession; error?: string }`). `WelcomeScreen`'s existing `onContinue` prop (unchanged).
- Produces: `OnboardingWizard`'s `Step` union extended with a new first member: `type Step = "account" | "name" | "pressure" | "duration" | "tracking" | "sites" | "passcode" | "review";`. Nothing produced here is consumed by Task 2 or by anything outside this file — self-contained.

**Deliverables:**
- Extend `Step` as above; change `const [step, setStep] = useState<Step>("name")` to `useState<Step>("account")`, so `showWelcome` still gates first, then `step === "account"` is what's shown next.
- New local state, namespaced to avoid colliding with this file's existing `passcode*` state for the later hard-block-passcode step: `accountEmail`, `accountOtpRequested`, `accountOtpCode`, `accountAuthError`, `accountAuthBusy`.
- New render block for `step === "account"`, modeled directly on `AccountPage.tsx`'s `!session` branch:
  - Heading and the fixed copy: *"Sign in to use friends, rooms, nudges, approvals, and synced accountability features."*
  - Not yet requested: an email input plus a "Send sign-in code" button calling `AUTH_REQUEST_OTP` with `{ email: accountEmail }`; on success, set `accountOtpRequested = true`.
  - Requested: a 6-digit code input plus a "Verify code" button calling `AUTH_VERIFY_OTP` with `{ email: accountEmail, token: accountOtpCode }`; on success, call `setStep("name")` to continue onboarding exactly as today.
  - A "Skip for now" button, visible in both states, that unconditionally calls `setStep("name")` — no side effects, no partial state to clean up.
  - `accountAuthError` rendered as `role="alert"` on failure, mirroring this file's existing `passcodeError`/`finishError` pattern.
- No change to `finish()` or the `SETTINGS_SAVE` payload — signing in or skipping has no bearing on local settings; onboarding's completion behavior is identical either way.

**Definition of done:** Fresh install → Welcome screen → "Get started" → the new step renders the exact stated copy. Path A: "Skip for now" → lands on "Meet Snuffles" exactly as today's flow does, onboarding completes normally. Path B: enter a real email → "Send sign-in code" → enter the real received code → "Verify code" → also lands on "Meet Snuffles" → after finishing onboarding, `AUTH_GET_SESSION` confirms a real signed-in session exists. Both paths verified once, by hand — no automated test required for this task.

## Task 2: Gate the Friends settings tab behind sign-in

**Goal:** `FriendsPage.tsx` already detects a signed-out user (`selfUserId === null`, via the `AUTH_GET_SESSION` call its existing `load()` already makes) and renders a static sentence — *"Sign in on the Account page to manage friend settings."* Replace that with a real, one-click action, so opening Friends while signed out visibly prompts sign-in rather than just describing where to go.

**Depends on:** nothing new. Reuses `FriendsPage.tsx`'s existing `AUTH_GET_SESSION` call and `AccountPage.tsx`'s already-working sign-in form as the destination.

**Interfaces:**
- Consumes: `OptionsApp`'s existing `view`/`setView` state (`type OptionsView = "settings" | "history" | "account" | "friends"`), currently local to `OptionsApp.tsx`.
- Produces: `FriendsPage` gains a new optional prop `onSignInClick?: () => void`.

**Deliverables:**
- `FriendsPage.tsx`: add `onSignInClick` to `FriendsPageProps`; in the existing `{!selfUserId && !error && ...}` branch, render a `<button type="button" onClick={onSignInClick}>Sign in</button>` alongside the existing sentence (keep the sentence — it still adds context; the button is what makes it actionable).
- `OptionsApp.tsx`: at the `<FriendsPage />` call site, pass `onSignInClick={() => setView("account")}`.

**Definition of done:** Signed out, open Settings → Friends tab → see a clickable "Sign in" button, not just static text. Click it → lands on the Account tab, which already has a fully working sign-in form (unchanged by this task). Nothing else changes: `FriendGroupPanel.tsx` in the side panel, nudge-send, Study Room join, digest view, and temp-passcode request are all untouched, exactly as `docs/V3.1_Scope_Summary.md` scopes.
