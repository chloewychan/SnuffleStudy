# SnuffleStudy V3.4 Implementation Plan — Friend-Model Foundation, Nudge Unification, Account-Setup Consolidation, Task Vault Simplification

**Source scope document:** `docs/scope_summaries/V3.4_Scope_Summary.md`. This plan maps that document's Section 0 (items 1–3) and Section 1 (items 1–5) into buildable tasks, in the order Section 0 must ship first (it touches almost every RLS policy in the schema, and every later task either depends on `are_friends()`/`friend_requests` directly or benefits from the codebase being settled before it's built against the old group model).

## Goal

Replace the group-shaped friend mechanic (`friend_groups`/`group_memberships`/`invite_codes`/`users_share_a_group()`) with a real pairwise `friendships` model; consolidate `unlock_requests`/`temp_passcode_requests`/`session_end_requests` into one generalized, kind-discriminated `friend_requests` table and one `FriendRequestPanel.tsx`; consolidate 16 duplicated `requireUserId()`/`checkAuth()` bodies into one `authHelpers.ts`; then, on that settled foundation, unify nudges and Producer Tags into one "nudge: written, audio" concept with independent per-type cooldowns; require the current password before changing it; consolidate account creation onto one screen ahead of the existing OTP step; remove dead Close/Back buttons; and remove the Task Vault breakdown-item feature entirely.

## Architecture

Unchanged from V3.1–V3.3: WXT-based Chrome MV3 extension. Background service worker (`background/messageRouter.ts`'s single `switch (message.type)`, dispatched via `handleMessage()`) is the sole entry point for all UI→backend communication, with the two documented direct-call exceptions (`studyRoomApi.joinRoom`/`subscribeToPresence`, `producerTagApi.subscribeToRoomProducerTags`/`downloadTagAudio` — DOM/live-callback/Blob reasons, unaffected by this version). Domain layer (`src/domain/`) stays free of browser/Supabase APIs. Infrastructure layer (`src/infrastructure/backend/*Api.ts`) wraps every Supabase call; Supabase Postgres RLS is the actual security boundary everywhere, never client-side filtering alone. `background/alarmHandlers.ts`'s friend-poll alarm (`chrome.alarms`) drives all background-delivered friend notifications via independent `poll*Updates()` streams, each with its own persisted cursor in `infrastructure/storage/friendPollState.ts`.

## Tech Stack

Unchanged: WXT, React, TypeScript, Supabase (Postgres + RLS + Edge Functions + Realtime + Storage), `idb` (IndexedDB) for local task/session storage, LiveKit for Study Room video/audio.

## Global Constraints

- Every UI→backend call goes through `sendMessage()`/`messageRouter.ts`'s switch, except the two documented direct-call exceptions above (unchanged this version).
- RLS is the real security boundary. A client-side check is a convenience/data-integrity nicety, never the actual gate — every new/changed policy below is written and reasoned about as if a malicious client can and will call the underlying REST/RPC surface directly with any input.
- Migrations in `supabase/migrations/` are strictly cumulative/additive — never edit a shipped migration file. A later migration can `drop policy`/`create or replace function`/`alter table` to change an earlier one's effective behavior, which is how every "swap `users_share_a_group()` for `are_friends()`" change below is expressed.
- Per your explicit go-ahead (scope doc's Purpose section): every table drop in Section 0 is a clean cutover with **no data migration** — `friend_groups`, `group_memberships`, `invite_codes`' `group_id` column's old semantics, `unlock_requests`, `temp_passcode_requests`, and `session_end_requests` are dropped/emptied outright, since the accounts on this database today are disposable test accounts. This is not the default policy for a future version with real user data.
- A background poll (`alarmHandlers.ts`) never silently applies a disruptive action. Unlocking an already-approved hostname/site is "silently extend what the user is already allowed to do" and stays safe to auto-apply; ending a session is disruptive and is never auto-applied — this asymmetry is unchanged and every new poll/apply function below preserves it exactly.
- Study Room persistence across sidepanel tabs is explicitly **out of scope** for v3.4 (per your request, pending a separate pass on how Study Rooms are displayed generally). `StudyRoomPanel.tsx`'s unmount-triggers-`leaveCall` behavior, and everything else about Study Rooms, is untouched by this plan except the one `are_friends()`-vs-group-sharing note in Task 2 (which doesn't apply — Study Rooms already migrated off group-sharing in V3.3).

## Decisions

Judgment calls made once here, up front, so no task improvises one independently. Each is flagged **(overridable)** — say so and it changes; otherwise this plan proceeds on the stated basis.

1. **Instant friend-connect, no accept/decline step.** Already decided and reasoned through in conversation before the scope doc was written (code-possession already implies two deliberate actions; codes are already single-use/time-limited; "Remove friend" is the escape hatch) — restated here because Task 2 depends on it. **(Settled, not overridable within this plan — revisit as its own future decision if ever reconsidered.)**

2. **`invite_codes.group_id` is dropped, not repointed at `friendships`.** Under the group model, redeeming a code added the redeemer to the generator's *group*. Under the pairwise model there is no group to join — redemption creates one `friendships` row directly between the two users. `invite_codes` therefore no longer needs to reference anything beyond `created_by` (already present) to know who generated a given code; `group_id` becomes dead weight and is dropped in the same migration that creates `friendships`. This also means "Invite a friend" collapses from today's two-step **create a group, then generate a code for it** into one step, **generate a code** — `AccountPage.tsx`'s `handleInviteAFriend()` loses its `GROUP_CREATE` call entirely, not just its `GROUP_GENERATE_INVITE_CODE` call. **(overridable — the alternative is keeping `group_id` nullable and unused for a softer diff; not recommended, since a dead NOT-NULL-turned-nullable FK column with no purpose is worse than removing it.)**

3. **`site_temp_pass` approval is the one `friend_requests` mutation that does NOT go through the shared plain-client `resolveRequest()` — it stays exclusively behind the `approve-temp-passcode` Edge Function.** This is a real security boundary, not a style choice: the Edge Function is what generates `expires_at`'s TTL server-side. If the consolidated table's UPDATE policy allowed any authenticated resolver to set `status = 'approved'` on *any* kind via a plain client update, a malicious client could approve their own (or anyone's) `site_temp_pass` request directly, setting `expires_at` to whatever they want or leaving it null (breaking the relock-alarm mechanism entirely). Task 3's UPDATE policy's `WITH CHECK` clause therefore explicitly excludes `status = 'approved' and kind = 'site_temp_pass'` from the plain-client path — see Task 3 for the exact policy and the negative-case test this needs. **Denial**, for all three kinds including `site_temp_pass`, *does* go through the shared `resolveRequest()` — today's `deny_temp_passcode_request()` RPC becomes redundant and is dropped. This is a small, deliberate behavior harmonization (today's temp-passcode denial leaves `resolved_by` null; under the shared path it gets set, matching how `unlock_requests`/`session_end_requests` already behave on denial) — not a preserved quirk, since nothing security-relevant depends on `resolved_by` being null on a denied request. **(overridable.)**

4. **A preserved existing quirk, not a new one: the requester of a `site_unlock`/`session_end` request can resolve (approve OR deny) their own pending request.** Verified directly in the currently-shipped `unlock_requests`/`session_end_requests` UPDATE policies (`requester_user_id = auth.uid()` is one of the USING branches, and the WITH CHECK only requires `resolved_by = auth.uid() and status in ('approved','denied')` — nothing excludes the requester from being their own resolver). This looks like it lets a user self-approve their own unlock request, which reads as a gap — but it is **pre-existing, shipped behavior**, not something this version introduces, and self-approval fixing is not part of the v3.4 ask. Task 3's consolidated UPDATE policy mirrors this exact shape for `site_unlock`/`session_end` (not `site_temp_pass`, which never had a requester-resolves-self branch to begin with — `temp_passcode_requests`' policies never gave the requester an update path at all). Flagging this explicitly rather than silently carrying it forward unremarked. **(overridable — if you want this closed, it's a small, separate WITH CHECK tightening (`resolved_by <> requester_user_id`) that Task 3 can absorb; say so and it's a one-line change to that task's policy.)**

5. **The mid-session "Request an unlock" requester form (today: the top half of `UnlockRequestPanel.tsx`, gated on an active session) relocates to a new small `RequestUnlockForm.tsx`, not into `FriendRequestPanel.tsx`.** The scope doc states the general principle ("requester-side UI stays feature-specific... since each is embedded in a different moment in the app") for `LockedPage.tsx`'s temp-pass request and `EndSessionControl.tsx`'s new session-end request, but doesn't explicitly place this third, pre-existing requester flow (which is a different feature from both: proactively asking to unlock a hostname mid-session, before ever hitting a hard block, versus `LockedPage.tsx`'s reactive "I already hit a wall" flow). Applying the same stated principle consistently: it becomes its own small component, carrying exactly its current logic (blocked-hostname suggestions via `SESSION_LIST_EVENTS`, a hostname field, "my requests for this session"), calling the new shared `createRequest("site_unlock", ...)`. `SidePanelApp.tsx`'s active-session view composes `RequestUnlockForm` (session-aware) and `FriendRequestPanel` (approver-only, no session prop) side by side — the same "compose two focused components at one call site" pattern `FriendsTab.tsx`/`SettingsTab.tsx` already established for `StudyRoomPanel`+`FriendGroupPanel` and `TempPasscodePanel`+`UnlockRequestPanel`. `SettingsTab.tsx` mounts only `FriendRequestPanel` (no `RequestUnlockForm` — matches today's `UnlockRequestPanel session={null}` there, which already suppresses the requester section when no session exists). **(overridable — flag if you'd rather fold this into `FriendRequestPanel.tsx` as an optional `session` prop instead of a sibling component; the plain-component split was chosen to match the existing panel-composition precedent exactly.)**

6. **One additional dead button found during grounding, added to Task 4's scope: `TaskVaultPage.tsx`'s own "Back" button.** The scope doc's Section 1 item 4 names only `StudyRoomPanel.tsx`/`FriendGroupPanel.tsx`. Direct inspection of `TaskVaultPage.tsx` (`app/routes/TaskVaultPage.tsx`) found the identical pattern: an internal `<button onClick={onClose}>Back</button>`, with its only mount point (`StudyTab.tsx`) passing `onClose={() => {}}` — a no-op, for the exact same "used to be a routed page, now permanently embedded" reason as the other two. This matches the user's original, general request ("removing the buttons that say 'back' or 'close' that don't lead anywhere") and the identical fix pattern already planned for the other two components, so it's folded into Task 4 rather than raised as a separate ask. **(overridable — flag if you'd rather leave this one out of v3.4.)**

7. **A generalized immutable-columns trigger is added to `friend_requests`, mirroring `unlock_requests`' existing one, even though only `unlock_requests` has one today.** The consolidated table now backs three previously-separate concerns behind one UPDATE policy; protecting `kind`/`requester_user_id`/`friend_user_id`/`hostname`/`session_id`/`message` from being altered post-creation (while still allowing `status`/`resolved_at`/`resolved_by`/`expires_at` to change, which is the entire point of an UPDATE) is a small, low-cost defense-in-depth measure consistent with the one precedent that already exists in this schema. Not requested explicitly; added because the consolidation itself increases what one shared UPDATE policy has to get right. **(overridable — drop it if you'd rather keep this table's migration smaller and lean entirely on the WITH CHECK clause.)**

8. **`background/friendSync.ts` and `sidepanel/components/ActiveSessionView.tsx` could not be read directly this session** — the device bridge to your machine returned `session_stale_relogin` partway through grounding. Both files are referenced (by `messageRouter.ts`/`alarmHandlers.ts` and by `SidePanelApp.tsx` respectively) but their exact current bodies aren't reproduced verbatim below. Task 2 and Task 3 describe the required change to each (`isInAnyGroup()` → `hasAnyFriend()`; consolidating `onShowUnlockPanel`/`onShowTempPasscodePanel` into one `onShowFriendRequestPanel`) at the goal-and-contract level and flag that the exact current body should be confirmed against the live file before editing, rather than presenting invented syntax as verified. ## Task 1 — Shared backend auth helper

### Goal

Consolidate the 16 duplicated `requireUserId()`/`checkAuth()` function bodies (8 files each, byte-identical within each shape — confirmed by direct grep of every `infrastructure/backend/*.ts` file) into one `infrastructure/backend/authHelpers.ts`, imported everywhere instead of redefined.

### Depends on

Nothing. Do first.

### Scope

**In:** one new file, exporting both shapes verbatim (no behavior change — this is a pure extraction). Every existing `infrastructure/backend/*.ts` file that currently defines its own copy switches to importing from here instead. `messageRouter.ts`'s own `currentUserId()` (lines 46–50: `string | null` return, no throw, used only for local IndexedDB task scoping) is a **third, differently-shaped** helper and is explicitly **not** part of this consolidation — it serves a different (non-throwing) contract and has exactly one call site (this file itself).

**Out:** any behavior change to either helper. Any change to which files call `getUser()` vs. `getSession()` — that distinction (hot-path lifecycle transition vs. explicit user-initiated action) is preserved exactly as each file already uses it.

### Interfaces

**Produces** (`infrastructure/backend/authHelpers.ts`):
```typescript
import { supabase } from "./supabaseClient";

// Verbatim from friendGroupApi.ts/friendshipSettingsApi.ts/producerTagApi.ts/studyRoomApi.ts/
// tempPasscodeApi.ts/unlockRequestApi.ts/sessionEndRequestApi.ts/profileApi.ts - all 8 copies are
// byte-identical, confirmed by direct comparison. For explicit, infrequent user-initiated actions
// (a button press) where a verified identity is worth the extra round trip .getUser() costs over
// .getSession().
export async function requireUserId(): Promise<string> {
  const { data, error } = await supabase.auth.getUser();
  if (error || !data.user) {
    throw new Error("Not signed in.");
  }
  return data.user.id;
}

// Verbatim from producerTagApi.ts/tempPasscodeApi.ts/unlockRequestApi.ts/sessionEndRequestApi.ts/
// sessionStatusSyncApi.ts/nudgeApi.ts/digestApi.ts/coachingApi.ts - all 8 copies are byte-identical.
// For poll-side callers that must distinguish "the auth check itself failed" (ok: false - a real
// failure, must not advance a persisted poll cursor) from "cleanly signed out" (ok: true,
// userId: null - not a failure, just nothing to fetch).
export async function checkAuth(): Promise<{ ok: true; userId: string | null } | { ok: false }> {
  try {
    const { data, error } = await supabase.auth.getSession();
    if (error) {
      console.error("Failed to read Supabase auth session", error);
      return { ok: false };
    }
    return { ok: true, userId: data.session?.user.id ?? null };
  } catch (err) {
    console.error("Failed to read Supabase auth session", err);
    return { ok: false };
  }
}
```

**Consumes:** nothing new — `supabaseClient.ts`'s existing `supabase` singleton, exactly as every one of the 16 removed copies already did.

Every file in this list deletes its own local copy and adds `import { requireUserId, checkAuth } from "./authHelpers";` (only the shape(s) it actually uses): `friendGroupApi.ts` (→ `friendshipApi.ts`, Task 2), `friendshipSettingsApi.ts`, `producerTagApi.ts`, `studyRoomApi.ts`, `tempPasscodeApi.ts`/`unlockRequestApi.ts`/`sessionEndRequestApi.ts` (all three deleted outright in Task 3 — their copies simply disappear, not migrated), `profileApi.ts` (Task 6 also edits this file — do the import swap first so Task 6 isn't touching a stale copy), `sessionStatusSyncApi.ts`, `nudgeApi.ts` (Task 8 also edits this file), `digestApi.ts`, `coachingApi.ts`.

### Deliverables

- 10 existing files edited to import instead of redefine (the count above minus the 3 files Task 3 deletes wholesale, since editing them here just to delete them next is wasted motion — Task 3's new `friendRequestApi.ts` imports from `authHelpers.ts` directly from the start instead).

### Depends on

### Scope

### Decisions specific to this task

Already covered above as Decisions 2 and 8 — restated here for locality: `invite_codes.group_id` is dropped (Decision 2); `friendSync.ts`'s exact current `isInAnyGroup()` body wasn't directly readable this session (Decision 8) — the replacement `hasAnyFriend()` is specified by contract below; confirm the exact current file before editing.

### Interfaces

**Produces (SQL — migration `20260815000041_v3.4_friendships.sql`):**

```sql
-- === New friendships table ===
create table friendships (
  user_id_a     uuid not null references auth.users(id),
  user_id_b     uuid not null references auth.users(id),
  initiated_by  uuid not null references auth.users(id),
  created_at    timestamptz not null default now(),
  primary key (user_id_a, user_id_b),
  -- Canonical ordering means each pair has exactly one row regardless of who redeemed whose
  -- code, and are_friends() below never has to check both orderings.
  constraint friendships_canonical_order check (user_id_a < user_id_b),
  constraint friendships_initiated_by_is_a_party
    check (initiated_by = user_id_a or initiated_by = user_id_b)
);

alter table friendships enable row level security;

create policy "either party can read their friendship"
  on friendships for select
  using (user_id_a = auth.uid() or user_id_b = auth.uid());

create policy "either party can remove their friendship"
  on friendships for delete
  using (user_id_a = auth.uid() or user_id_b = auth.uid());

-- No client-reachable INSERT path at all, by design - mirrors invite_codes' own fully-revoked-
-- UPDATE precedent (20260815000025) and group_memberships' redeem-only INSERT gate. The ONLY way
-- a friendships row is ever created is through redeem_invite_code() below (SECURITY DEFINER,
-- bypasses RLS entirely), so there is deliberately no INSERT policy and no grant of INSERT to
-- authenticated.
grant select, delete on friendships to authenticated;
grant select, insert, update, delete on friendships to service_role;

-- === are_friends() - replaces users_share_a_group() ===
create or replace function public.are_friends(p_user_a uuid, p_user_b uuid)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1 from friendships
    where user_id_a = least(p_user_a, p_user_b)
      and user_id_b = greatest(p_user_a, p_user_b)
  );
$$;

revoke all on function public.are_friends(uuid, uuid) from public;
grant execute on function public.are_friends(uuid, uuid) to authenticated, service_role;

-- === invite_codes: drop group_id, simplify INSERT policy (Decision 2) ===
alter table invite_codes drop column group_id;

drop policy "group members can create invite codes for their group" on invite_codes;
create policy "signed-in users can create invite codes for themselves"
  on invite_codes for insert
```

```typescript
export async function removeFriend(friendUserId: string): Promise<void> {

  const a = userId < friendUserId ? userId : friendUserId;
  const b = userId < friendUserId ? friendUserId : userId;

    .eq("user_id_b", b)
    .select();

    throw new Error(error.message);

    throw new Error("You aren't friends with this user.");
```

```sql
create table friend_requests (
  id                 uuid primary key default gen_random_uuid(),
  kind               text not null check (kind in ('site_unlock', 'site_temp_pass', 'session_end')),
  requester_user_id  uuid not null references auth.users(id),
  friend_user_id     uuid references auth.users(id),  -- null = any friend, first-responder-wins
  message            text,
  status             text not null check (status in ('pending', 'approved', 'denied')),
  requested_at       timestamptz not null default now(),
  resolved_at        timestamptz,
  resolved_by        uuid references auth.users(id),
  hostname           text,       -- site_unlock/site_temp_pass only
  session_id         text not null,  -- required by all three kinds (matches all 3 source tables today)
  expires_at         timestamptz,     -- site_temp_pass only - set exclusively by the Edge Function below
  constraint friend_requests_requester_ne_friend
    check (friend_user_id is null or friend_user_id <> requester_user_id),
  constraint friend_requests_hostname_by_kind check (
    (kind in ('site_unlock', 'site_temp_pass') and hostname is not null)
    or (kind = 'session_end' and hostname is null)
  ),
  constraint friend_requests_expires_at_by_kind
    check (kind = 'site_temp_pass' or expires_at is null)
);

alter table friend_requests enable row level security;

create policy "users can create their own pending friend requests"
  on friend_requests for insert
  with check (
    requester_user_id = auth.uid()
    and status = 'pending'
    and (friend_user_id is null or are_friends(requester_user_id, friend_user_id))
  );

create policy "requester assigned friend or pending-friend can read friend requests"
  on friend_requests for select
  using (
    requester_user_id = auth.uid()
    or friend_user_id = auth.uid()
    or (
      friend_user_id is null
      and status = 'pending'
      and are_friends(requester_user_id, auth.uid())
    )
  );

-- SECURITY-CRITICAL - see Decision 3 for the full reasoning this comment summarizes. This policy
-- deliberately does NOT let a plain client UPDATE set status='approved' when kind='site_temp_pass'
-- - that transition must go through the approve-temp-passcode Edge Function (service_role,
-- bypasses RLS entirely), which is what generates expires_at's TTL server-side. Without this
-- exclusion, any authenticated user visible to a pending site_temp_pass request (the assigned
-- friend, per the USING clause) could plain-UPDATE it to approved with expires_at left null
-- (breaking the relock-alarm mechanism - the request would read as "approved" but never
-- auto-relock) or, if expires_at weren't excluded from client writes at all, set an arbitrary far-
-- future expiry themselves. Denial has no such server-generated side effect, so it's allowed
-- through this same plain path for all three kinds (Decision 3's "denial harmonization").
--
-- Also preserves the existing requester-can-resolve-their-own-pending-request USING branch for
-- site_unlock/session_end, per Decision 4 (a pre-existing, unmodified shipped behavior - NOT
-- something newly introduced by this consolidation).
create policy "requester assigned friend or pending-friend can resolve friend requests"
  on friend_requests for update
  using (
    requester_user_id = auth.uid()
    or friend_user_id = auth.uid()
    or (
      friend_user_id is null
      and status = 'pending'
      and are_friends(requester_user_id, auth.uid())
    )
  )
  with check (
    resolved_by = auth.uid()
    and (
      status = 'denied'
      or (status = 'approved' and kind <> 'site_temp_pass')
    )
  );

grant select, insert, update on friend_requests to authenticated;
grant select, insert, update, delete on friend_requests to service_role;

-- Immutable-columns trigger (Decision 7) - protects identity/context columns from being altered
-- post-creation via the same UPDATE path used to resolve a request. status/resolved_at/
-- resolved_by/expires_at are deliberately NOT included - mutating those is the entire point of
-- resolving a request (and expires_at must remain writable by the service_role Edge Function).
create or replace function public.friend_requests_prevent_immutable_column_changes()
returns trigger language plpgsql as $$
begin
  if new.kind <> old.kind
    or new.requester_user_id <> old.requester_user_id
    or new.friend_user_id is distinct from old.friend_user_id
    or new.hostname is distinct from old.hostname
    or new.session_id <> old.session_id
    or coalesce(new.message, '') <> coalesce(old.message, '')
  then
    raise exception 'kind, requester_user_id, friend_user_id, hostname, session_id, and message cannot be changed on a friend request';
  end if;
  return new;
end;
$$;
```

```typescript
import { requireUserId, checkAuth } from "./authHelpers";
import type { FriendRequest, FriendRequestKind } from "../../domain/accountability/friendRequest";
import { unlockHardBlockRuleForHostname } from "../browser/declarativeNetRequestApi";
import { scheduleTempUnlockRelockAlarm } from "../browser/alarmsApi";

const COLUMNS =
  "id, kind, requester_user_id, friend_user_id, message, status, requested_at, resolved_at, resolved_by, hostname, session_id, expires_at";

function toFriendRequest(row: any): FriendRequest {
  return {
    id: row.id,
    kind: row.kind,
    requesterUserId: row.requester_user_id,
    friendUserId: row.friend_user_id,
    message: row.message,
    status: row.status,
    requestedAt: new Date(row.requested_at).getTime(),
    resolvedAt: row.resolved_at ? new Date(row.resolved_at).getTime() : null,
    resolvedBy: row.resolved_by,
    hostname: row.hostname,
    sessionId: row.session_id,
    expiresAt: row.expires_at ? new Date(row.expires_at).getTime() : null,
  };

// One creation function for all three kinds, parameterized by kind + a context object holding
// exactly the fields that kind needs - mirrors LockedPage.tsx's/EndSessionControl.tsx's/
// RequestUnlockForm.tsx's shared call shape (Decision 5 / scope doc's "all three now call the
// same shared createRequest").
export async function createRequest(
  kind: FriendRequestKind,
  context: { sessionId: string; friendUserId?: string; message?: string; hostname?: string }
): Promise<FriendRequest> {
  const userId = await requireUserId();
  const { data, error } = await supabase
    .from("friend_requests")
    .insert({
      kind,
      session_id: context.sessionId,
      requester_user_id: userId,
      friend_user_id: context.friendUserId ?? null,
      hostname: context.hostname ?? null,
      status: "pending",
      ...(context.message ? { message: context.message } : {}),
    })
    .select(COLUMNS)
    .single();
  if (error || !data) {
    throw new Error(error?.message ?? "Failed to create that request.");
  }
  return toFriendRequest(data);
}

// Plain client UPDATE - valid for: denying ANY kind, or approving site_unlock/session_end.
// Approving a site_temp_pass request must go through approveTempPass() below instead - RLS's
// WITH CHECK clause enforces this server-side regardless of what this function is called with
// (see the migration's own comment), so this is a client-side guard for a clear error message,
// not the actual security boundary.
export async function resolveRequest(
  requestId: string,
  decision: "approved" | "denied"
): Promise<void> {
  const userId = await requireUserId();
  const { data, error } = await supabase
    .from("friend_requests")
    .update({ status: decision, resolved_at: new Date().toISOString(), resolved_by: userId })
    .eq("id", requestId)
    .select()
    .single();
  if (error || !data) {
    throw new Error(
      error?.message ?? "Could not resolve this request — it may already have been resolved, or (if approving a temporary pass) needs Approve, not this path."
    );
  }
}

export async function approveTempPass(
  requestId: string
): Promise<{ hostname: string; expiresAt: number }> {
  const { data, error } = await supabase.functions.invoke<{
    hostname?: string;
    expiresAt?: number;
    error?: string;
  }>("approve-temp-passcode", { body: { requestId } });
  if (error || !data?.hostname || typeof data.expiresAt !== "number") {
    throw new Error(data?.error ?? error?.message ?? "Failed to approve temp passcode request.");
  }
  return { hostname: data.hostname, expiresAt: data.expiresAt };
}

// site_temp_pass only - unchanged behavior from tempPasscodeApi.ts's current claimApproval().
export async function claimApproval(requestId: string): Promise<{ ok: boolean }> {
  try {
    const { data, error } = await supabase
      .from("friend_requests")
      .select("hostname, status, expires_at")
      .eq("id", requestId)
      .eq("kind", "site_temp_pass")
      .eq("status", "approved")
      .single();
    if (error || !data || !data.hostname) return { ok: false };
    if (data.expires_at && new Date(data.expires_at).getTime() <= Date.now()) return { ok: false };
    await unlockHardBlockRuleForHostname(data.hostname);
    if (data.expires_at) {
      scheduleTempUnlockRelockAlarm(data.hostname, new Date(data.expires_at).getTime());
    }
    return { ok: true };
  } catch (err) {
    console.error("Failed to claim an approved temp passcode request", err);
    return { ok: false };
  }
}

// SECURITY-CRITICAL - generalizes sessionEndRequestApi.ts's isApprovedForSelf exactly (see that
// function's own comment for the full reasoning this preserves verbatim): does its own fresh
// read, never trusts a client-supplied status, and explicitly compares requester_user_id against
// the CALLER's own freshly-verified identity - RLS's "friend_user_id = auth.uid()" SELECT branch
// deliberately lets the resolving friend read this row too, which is not the same thing as it
// being THEIR pass to use. Kind-scoped (only ever called for "session_end" today, but takes kind
// as a param rather than hardcoding it, in case a future kind needs the same guard).
export async function isApprovedForSelf(
  requestId: string,
  kind: FriendRequestKind,
  sessionId: string
): Promise<boolean> {
  const userId = await requireUserId();
  const { data, error } = await supabase
    .from("friend_requests")
    .select("kind, session_id, status, requester_user_id")
    .eq("id", requestId)
    .single();
  if (error || !data) return false;
  return (
    data.kind === kind &&
    data.status === "approved" &&
    data.session_id === sessionId &&
    data.requester_user_id === userId
  );
}

async function queryRelevantSince(
  sinceTimestamp: number
): Promise<{ ok: boolean; requests: FriendRequest[] }> {
  try {
    const auth = await checkAuth();
    if (!auth.ok) return { ok: false, requests: [] };
    if (!auth.userId) return { ok: true, requests: [] };

    const sinceIso = new Date(sinceTimestamp).toISOString();
    const { data, error } = await supabase
      .from("friend_requests")
      .select(COLUMNS)
      .or(`requested_at.gt.${sinceIso},resolved_at.gt.${sinceIso}`)
      .order("requested_at", { ascending: true });
    if (error || !data) {
      console.error("Failed to fetch friend requests", error);
      return { ok: false, requests: [] };
    }
    return { ok: true, requests: data.map(toFriendRequest) };
  } catch (err) {
    console.error("Failed to fetch friend requests", err);
    return { ok: false, requests: [] };
  }
}

export async function fetchRelevantRequests(sinceTimestamp: number): Promise<FriendRequest[]> {
  const result = await queryRelevantSince(sinceTimestamp);
  return result.requests;
}

export async function pollRelevantRequests(
  sinceTimestamp: number
): Promise<{ ok: true; requests: FriendRequest[] } | { ok: false }> {
  const result = await queryRelevantSince(sinceTimestamp);
  return result.ok ? { ok: true, requests: result.requests } : { ok: false };
}
```

```typescript
    const now = Date.now();
    const since = (await getLastFriendRequestPollAt()) ?? now - FIRST_POLL_LOOKBACK_MS;
    const result = await pollRelevantRequests(since);
    if (!result.ok) return;
    for (const req of result.requests) {
```

```typescript
    .from("profiles")
    .upsert({ user_id: userId, password_set_at: new Date().toISOString() }, { onConflict: "user_id" });
  if (error) {
    throw new Error(error.message);

}
```

```typescript
// PASSWORD or PROFILE_SAVE_MINE) can be retried WITHOUT re-calling AUTH_VERIFY_OTP, which would
// either fail outright (an OTP code is single-use server-side) or, worse, require the user to
// request and enter an entirely new code for a failure that has nothing to do with the code
// itself. Distinct in purpose from the old (now-removed) pendingCreateSession, which existed to
// gate a manual next step the user drove themselves - this exists purely to make automatic
// completion retryable.
const [verifiedSession, setVerifiedSession] = useState<SignInFormSession | null>(null);

async function completeAccountCreation(session: SignInFormSession) {
  setAuthBusy(true);
  setAuthError(null);
  try {
    // No currentPassword - a brand-new account has none to prove, Task 6's messageRouter.ts
    // branch is a no-op when profiles.password_set_at is null.
    const passwordRes = await sendMessage<{ ok: boolean; error?: string }>({
      type: "AUTH_SET_PASSWORD",
      payload: { password },
    });
    if (!passwordRes.ok) {
      setAuthError(passwordRes.error ?? "Could not finish creating your account. Please try again.");
      return;
    }
    const profileRes = await sendMessage<{ ok: boolean; error?: string }>({
      type: "PROFILE_SAVE_MINE",
      payload: { humanName, bunnyName: bunnyName || undefined },
    });
    if (!profileRes.ok) {
      setAuthError(profileRes.error ?? "Could not finish creating your account. Please try again.");
      return;
    }
    setOtpCode("");
    setPassword("");
    setConfirmPassword("");
    setVerifiedSession(null);
    onSignedIn(session);
  } catch (err) {
    console.error("Failed to finish creating the account", err);
    setAuthError(err instanceof Error ? err.message : String(err));
  } finally {
    setAuthBusy(false);
  }
}

async function handleCreateVerifyOtp(e: FormEvent) {
  e.preventDefault();
  setAuthBusy(true);
  setAuthError(null);
  try {
    const verifyRes = await sendMessage<{ ok: boolean; session?: SignInFormSession; error?: string }>({
      type: "AUTH_VERIFY_OTP",
      payload: { email, token: otpCode },
    });
    if (!verifyRes.ok || !verifyRes.session) {
      setAuthError(verifyRes.error ?? "Incorrect or expired code.");
      return;
    }
    // The email is now proven - hand off to completeAccountCreation, which owns its own
    // authBusy/authError lifecycle from here (see the shared finally block there instead of
    // duplicating one here).
    setVerifiedSession(verifyRes.session);
    setAuthBusy(false);
    await completeAccountCreation(verifyRes.session);
    return;
  } catch (err) {
    console.error("Failed to verify sign-in code", err);
    setAuthError(err instanceof Error ? err.message : String(err));
    setAuthBusy(false);
  }
}
```
