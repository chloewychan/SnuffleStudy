# SnuffleStudy V3.3 Implementation Plan

**Goal:** Build every item in `docs/scope_summaries/V3.3_Scope_Summary.md` — the definite v3.3 scope, already decided against `docs/scope_summaries/V3.3_Feature_Feedback.md`'s reasoning. This plan turns that scope into buildable tasks: exact schema, exact message contracts, exact file changes, and a Definition of Done per task.

**Architecture:** No structural changes to the extension's layers (background/domain/infrastructure/presentation stays a four-layer split, message-passing-only between UI and background, same as every prior version). Additions: one new Postgres table with RLS (`study_room_invitees`), one new small table (`profiles`), one new table mirroring an existing one almost exactly (`session_end_requests`, modeled on `unlock_requests`), one Edge Function is retired (`redeem-temp-passcode`) and one is trimmed (`approve-temp-passcode` loses its code-generation half), and `temp_passcode_requests` loses four columns it no longer needs. Presentation-layer changes are heavier than usual this version — the sidepanel's Settings tab goes from two embedded panels to a real sub-navigated surface — but nothing here introduces a new architectural pattern the codebase doesn't already have an example of.

**Tech Stack:** Unchanged — Supabase/Postgres/LiveKit/Resend, WXT/React/TypeScript. `AUTH_SET_PASSWORD`/`AUTH_SIGN_IN_PASSWORD` (Task 14) are the one genuinely new third-party surface (Supabase Auth's password methods, alongside the already-used OTP methods on the same client).

Per `docs/Implementation_Plan_Guidelines.md`: full SQL/type detail is given for every task that touches RLS, a credential/access-control boundary, or a schema/message contract more than one task consumes (Tasks 8, 10, 11, 12, 13) — these are exactly the "security- or privacy-critical" and "shared contract" categories the guidelines call out, and this codebase's own migration history (cited throughout) shows what happens when this class of change is under-specified: a fix round, then often a second one. Medium detail is used for well-precedented UI work with no new access-control surface (Tasks 1, 3, 6, 7, 9). Task 14 gets a precise message contract but treats exact Supabase Auth call syntax the way the guidelines direct for any third-party API surface: confirm `signInWithPassword`/`updateUser`'s exact current signature against `supabase.com/docs` at implementation time rather than trusting this plan's remembered syntax.

## Global Constraints

Everything from `docs/V2_Implementation_Plan.md`'s and `docs/V3.2_Implementation_Plan.md`'s Global Constraints still applies unchanged: no API key ships client-side; friend-visible data stays field- or row-gated by RLS, never client-side filtering alone; UI components never import `infrastructure/backend/*` directly except the two already-documented exceptions in `studyRoomApi.ts` (`joinRoom`, `subscribeToPresence`) — every new capability in this plan reaches the UI through `messageRouter.ts`, no new direct-import exceptions are added.

New for V3.3:
- **Task 10 removes the temp-passcode-specific PBKDF2/salt/lockout machinery** (`code_hash`/`code_salt`/`failed_attempts`/`locked_until` on `temp_passcode_requests`, and both Edge Functions' copies of the hashing code). This is **not** a change to `src/domain/sites/hardBlockCredential.ts` or the *permanent* hard-block passcode it protects — that's a separate table (no `temp_passcode_requests` involvement at all), a separate credential store (`settingsRepo.getHardBlockCredential()`), and stays exactly as it is. Only the temp-passcode-specific duplicate of that hashing approach goes away, because the thing it was hashing (a human-relayed code) no longer exists in this design.
- **A background poll never triggers a disruptive UI action on its own.** `applyApprovedUnlockRequest` (existing) and the new `applyApprovedTempPasscodeRequest` (Task 10) are both "silently extend what the user is already allowed to do" — safe to run unattended from `alarmHandlers.ts`. Ending a session (Task 12) is disruptive — it stops what the user is doing — so an approved session-end request is never auto-applied from the background poll; it only produces a notification, and the actual `SESSION_END` call still requires the user to click a button.

## Decisions

Resolved here, once, rather than left for whichever task hits them first:

1. **`session_end_requests` (Task 12) reuses `unlock_requests`' exact RLS shape** (migration `20260815000008`'s policies, copied and retargeted at the new table) rather than inventing a new visibility model — same "no assigned friend, any pending-group-member can resolve, first-responder-wins" design, since the request in `docs/scope_summaries/V3.3_Scope_Summary.md` explicitly asks for a single button with no friend picker.
2. **Sequencing correction from the scope doc:** the scope doc's suggested order puts the temp-passcode message field (its Section 4, item 3) before the temp-passcode redesign (Section 4, item 1). This plan reverses that — **Task 10 (redesign) before Task 11 (message field)** — because both touch the same migration surface on `temp_passcode_requests`, and Task 10 drops four columns from that table. Landing the drop first, then adding `message` in its own clean follow-up migration, avoids a migration that both adds and removes columns on the same table in the wrong order, or a rebase headache if they're built out of sequence.
3. **`TEMP_PASSCODE_CLAIM_APPROVAL`'s handler always re-reads the request row itself, server-side, rather than trusting client-supplied hostname/expiry.** The requester's client already has a fresh copy of the row (it just fetched it), but the message only ever carries `{ requestId }` — see Task 10's Interfaces block. Cheap, and closes off a class of bug where a stale or crafted client payload could claim access to a hostname the server never actually approved.
4. **`profiles.human_name` has no uniqueness constraint.** It's a display label, not an identifier — every security/authorization check in this codebase keys off `auth.uid()`/`user_id`, never a name, and that stays true after Task 8.
5. **The Study Room invite backfill (Task 13) does not insert a row for a room's own owner.** The owner already has unconditional access via `study_rooms`' `owner_user_id = auth.uid()` clause — an invitee row for them would be redundant, not incorrect, so it's just skipped.
6. **`SignInForm.tsx`'s Create-account/Sign-in choice lives inside the component itself**, not as a prop the caller sets — every call site (`AccountPage.tsx`, `OnboardingWizard.tsx`, and Task 7's new sidepanel Account sub-view, which reuses `AccountPage.tsx` directly) gets both flows automatically, with no risk of one call site being wired to the wrong mode.

### Task 6: Archive study rooms (soft delete)

**Goal:** A room's owner can remove it from the joinable list without a hard delete — `producer_tag_sends.recipient_room_id` references `study_rooms.id`, so a real `DELETE` risks either an FK violation or silently erasing real Producer Tag history.

**Depends on:** nothing.

**Interfaces:**
- Consumes: nothing new.
- Produces:
  ```ts
  // studyRoomApi.ts
  export async function archiveRoom(roomId: string): Promise<void>;
  ```
  New message: `{ type: "STUDY_ROOM_ARCHIVE"; payload: { roomId: string } }` → `{ ok: boolean; error?: string }`.

**Deliverables:**
- New migration:
  ```sql
  alter table study_rooms add column archived_at timestamptz;

  create policy "owner can archive their own room"
    on study_rooms for update
    using (owner_user_id = auth.uid())
    with check (owner_user_id = auth.uid());
  ```
- `studyRoomApi.ts`: `listRooms()` adds `.is("archived_at", null)` to its existing query; new `archiveRoom(roomId)` does `requireUserId()` then `.update({ archived_at: new Date().toISOString() }).eq("id", roomId).eq("owner_user_id", userId)`, throwing on a Postgres error (same convention as `createRoom`/`leaveRoom`).
- `messageRouter.ts`: new `STUDY_ROOM_ARCHIVE` case, thin pass-through, same convention as `STUDY_ROOM_LEAVE`.
- `StudyRoomPanel.tsx`: an "Archive this room" button next to a room in the list, shown only when `room.ownerUserId === selfUserId`, calling `STUDY_ROOM_ARCHIVE` and removing it from the local `rooms` list on success.

**Definition of done:** a room's owner archives it — it disappears from `STUDY_ROOM_LIST` for every user, including the owner; a non-owner attempting `STUDY_ROOM_ARCHIVE` on someone else's room is denied (RLS `using` clause matches zero rows, surfaced as a Postgres/PostgREST error, turned into `{ ok: false }` by the outer `handleMessage` catch — verify this negative case directly, not just the happy path); any Producer Tag history referencing the archived room (`producer_tag_sends.recipient_room_id`) is untouched and still queryable.

### Task 8: Profiles backend (bunny name / human name)

**Goal:** `BunnyTab.tsx`'s `bunnyName`/`humanName` fields are pure local stub state today — wire them to a real backend, and show `human_name` everywhere a raw user id is shown today.

**Depends on:** nothing.

**Interfaces:**
- Consumes: `users_share_a_group(uuid, uuid)` (existing helper, migration `20260815000012`).
- Produces:
  ```sql
  create table profiles (
    user_id     uuid primary key references auth.users(id),
    human_name  text,
    bunny_name  text,
    updated_at  timestamptz not null default now()
  );

  alter table profiles enable row level security;

  create policy "self or group-mate can read a profile"
    on profiles for select
    using (
      user_id = auth.uid()
      or users_share_a_group(user_id, auth.uid())
    );

  create policy "self can insert own profile"
    on profiles for insert
    with check (user_id = auth.uid());

  create policy "self can update own profile"
    on profiles for update
    using (user_id = auth.uid())
    with check (user_id = auth.uid());

  grant select, insert, update on profiles to authenticated;
  ```
  ```ts
  // infrastructure/backend/profileApi.ts
  export interface Profile {
    userId: string;
    humanName: string | null;
    bunnyName: string | null;
    updatedAt: string;
  }
  export async function getMyProfile(): Promise<Profile | null>;
  export async function saveMyProfile(patch: { humanName?: string; bunnyName?: string }): Promise<Profile>;
  export async function fetchProfilesByIds(userIds: string[]): Promise<Profile[]>; // never throws — degrades to [], same convention as fetchIncomingNudges etc.
  ```
  New messages:

### Task 14: Password auth — separate account-creation and sign-in flows

**Goal:** Creating an account requires verifying an email code *and* setting a matching password before the account is usable. Signing into an existing account offers a password or a fresh code as equal options — a regular sign-up/log-in shape, not OTP-with-an-optional-password-bolted-on.

**Depends on:** nothing (independent of every other task; do Task 2's copy fix as part of this task's rewrite if not already done separately).

**Interfaces:**
- Consumes: Supabase Auth's `signInWithOtp`/`verifyOtp` (existing, unchanged) and `signInWithPassword`/`updateUser` (new to this codebase — **confirm exact current call signatures against `supabase.com/docs` at implementation time**, per this plan's light-detail rule for third-party auth APIs; the shapes below are this plan's best-effort contract, not guaranteed-current syntax).
- Produces:
  ```ts
  // shared/messages.ts, new:
  | { type: "AUTH_SET_PASSWORD"; payload: { password: string } }
  | { type: "AUTH_SIGN_IN_PASSWORD"; payload: { email: string; password: string } }
  ```
  Response shapes: `AUTH_SET_PASSWORD` → `{ ok: boolean; error?: string }`; `AUTH_SIGN_IN_PASSWORD` → `{ ok: boolean; session?: AuthSession; error?: string }` (same `AuthSession` shape `AUTH_VERIFY_OTP` already returns).

**Deliverables:**
- `messageRouter.ts`: two new cases —
  ```ts
  case "AUTH_SET_PASSWORD": {
    const { error } = await supabase.auth.updateUser({ password: message.payload.password });
    if (error) return { ok: false, error: error.message };
    return { ok: true };
  }
  case "AUTH_SIGN_IN_PASSWORD": {
    const { data, error } = await supabase.auth.signInWithPassword({
      email: message.payload.email,
      password: message.payload.password,
    });
    if (error) return { ok: false, error: error.message };
    return { ok: true, session: data.session };
  }
  ```
  (Confirm `updateUser`/`signInWithPassword`'s exact option/return shape against current Supabase docs before implementing — same caveat as this task's Interfaces block.)
- `SignInForm.tsx`, restructured with an internal top-level choice (per Decision 6 — this lives in the component, not a caller-supplied prop):
  - **Entry state:** "Create account" / "Sign in" buttons.
  - **Create-account branch:** email → `AUTH_REQUEST_OTP` → code entry → `AUTH_VERIFY_OTP` → **on success, do not call `onSignedIn` yet** — instead show a required two-field password step ("Password" / "Confirm password"), submit disabled until they match; on submit, call `AUTH_SET_PASSWORD`; only on *that* success does `onSignedIn` fire. `onSkip` (present only in the onboarding context) remains available at every step in this branch, exactly as it is today for the OTP step — skipping mid-signup behaves exactly like skipping today's single-step flow (no partial-account cleanup needed; an unverified or password-less account is simply left as-is, matching this codebase's existing "no resume-mid-verification" stance).
  - **Sign-in branch:** two peer options, not fallback-primary — "Sign in with a password" (email + password fields, `AUTH_SIGN_IN_PASSWORD`) and "Email me a code" (today's `AUTH_REQUEST_OTP`/`AUTH_VERIFY_OTP` round trip, unchanged, calling `onSignedIn` directly on success — **no** password step tacked onto this path, since the account already exists).
- `AccountPage.tsx`: keep a "set/change your password" action for an already-signed-in user (`AUTH_SET_PASSWORD`, same message Task 14's signup step uses) — this is the recovery path for any account created before this feature shipped (no password yet), and the normal way to change a password later; no longer the primary way a password gets set (that's now mandatory at signup).
- Forgot-password: no new UI beyond what's already described — "Email me a code" on the Sign-in branch gets a user back in via OTP, and `AccountPage.tsx`'s existing "set/change your password" section is where they'd then set a new one.
- `OnboardingWizard.tsx`'s account step renders `SignInForm` unchanged at the call-site level — it inherits the Create-account/Sign-in split and the mandatory password step automatically; `onSkip` behavior is unchanged.

**Definition of done:** a brand-new email cannot complete "Create account" without both a verified code and two matching passwords — verify the submit button is genuinely disabled (not just visually) until both conditions hold. An existing account can sign in with either its password or a fresh code — verify both paths independently reach a real session (`AUTH_GET_SESSION` confirms it after each). An account created before this feature shipped (no password set) can still sign in via "Email me a code," and can set a password afterward from `AccountPage.tsx`. "Skip for now" in onboarding still fully skips, at any point in either branch, with no partial state blocking a later attempt.
