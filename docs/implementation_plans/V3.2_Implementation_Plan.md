**Goal:** Harden what `docs/V3.1_Scope_Summary.md`'s one-session hackathon rush deliberately left rough, and build everything else `docs/V3_Scope_Summary.md` scoped as must-ship that V3.1 skipped outright. Per `docs/Implementation_Plan_Guidelines.md`, detail level below varies by task the same way v1/v2's plans did: full detail (exact SQL/types) for the two backend fixes, since they're privacy- and security-adjacent and touch a shared contract other code already reads; medium detail for the onboarding cleanup and the panel split, since the patterns are already established elsewhere in this codebase; light, goal-and-contract-only detail for deployment readiness, since its privacy-policy content is a legal/product judgment call, not something to write exact copy for here.

## Decisions

1. **Merge direction:** `v3.1` → `main`, per the discovery above — corrected from this plan's first draft, which assumed a three-way `v3.1`/`frontend`/`main` reconciliation before checking that `main` and `frontend` are already the same commit. Only `v3.1`'s two commits are actually unmerged. See Task 0a.
2. **Digest privacy fix scope, corrected from `docs/V3.2_Scope_Summary.md`'s framing:** that document's Section 2, item 2 says to add negative tests "especially [for] distraction attempts and goal text." Reading `daily_digests`' actual schema (`supabase/migrations/20260815000010_v2_daily_digests.sql`) shows it has no goal-text column at all — it's four aggregate numbers (`completed_sessions`, `abandoned_sessions`, `distraction_count`, `recovery_rate`), never per-session detail. Of those four, exactly one — `distraction_count` — has a corresponding Task 10 per-field toggle (`shareDistractionAttempts`) that isn't currently consulted. This plan fixes that one, real, concrete gap (Task 5 below) rather than a broader "goal text" gap that doesn't exist in this table. Flagging the correction here rather than silently redefining what the scope doc said.
3. **How the digest fix is implemented:** `daily_digests` stores one row per `(subject_user_id, digest_date)`, not per `(subject, viewer, date)` — so "hide `distraction_count` from viewer B but show it to viewer A" can't be a stored-row property. Task 5 adds a view that computes per-viewer visibility at read time (using `auth.uid()`), rather than fanning out storage into a row per friendship. Cheaper to compute, and it's the same pattern this codebase already uses for row-level visibility (SECURITY DEFINER helper functions consulted inside a policy/view) — just applied to a column instead of a whole row.
4. **Study Room "active participant," source of truth:** on inspection, `generate-livekit-token`'s Edge Function already filters on `left_at is null` when deciding whether to mint a token — it doesn't currently disagree with `studyRoomApi.leaveRoom()`. The actual risk isn't a live disagreement today; it's that the same "is this user an active participant" check is independently hand-written in at least two places (the Edge Function's inline query, and `studyRoomApi.ts`'s own `.is("left_at", null)` filters used for presence/participant listing) with nothing forcing them to agree if either one changes later. Task 6 below centralizes the check into one Postgres function both can call, closing that risk rather than a bug that's already fired.

### Task 5: Daily-digest privacy enforcement

**Goal:** `distraction_count` in the daily digest currently ignores `friendship_settings.share_distraction_attempts` — a subject who hasn't shared distraction attempts with a specific friend still has that count exposed to them via the digest, because `compute_daily_digests()` aggregates unconditionally and `digestApi.ts` reads the raw table directly. See Decisions 2–3 above for why this is narrower, and shaped differently, than `docs/V3.2_Scope_Summary.md`'s original phrasing.

**Depends on:** nothing (independent of Section 1).

**Interfaces:**
- Consumes: `daily_digests` (unchanged schema — `supabase/migrations/20260815000010_v2_daily_digests.sql`), `friendship_settings.share_distraction_attempts` (Task 10, v2).
- Produces: a new view `daily_digests_visible`, and `digestApi.ts`'s `queryDigestsForDate`/`pollNewDigests` now select from it instead of `daily_digests` directly. `DigestSummary`/`FriendDigest`'s TypeScript shape is unchanged — `distractionCount` just comes back as `0` instead of the real count when the subject hasn't shared it with the querying viewer, rather than a new field or a nullable type, so no downstream consumer (`FriendGroupPanel`'s `DigestCard`) needs to change.

**Deliverables:**
- New migration creating:

  ```sql
  create or replace view public.daily_digests_visible as
  select
    d.subject_user_id,
    d.digest_date,
    d.completed_sessions,
    d.abandoned_sessions,
    case
      when d.subject_user_id = auth.uid() then d.distraction_count
      when exists (
        select 1 from friendship_settings fs
        where fs.user_id = d.subject_user_id
          and fs.friend_user_id = auth.uid()
          and fs.share_distraction_attempts = true
      ) then d.distraction_count
      else 0
    end as distraction_count,
    d.recovery_rate,
    d.computed_at
  from public.daily_digests d;

  grant select on public.daily_digests_visible to authenticated;
  ```

  A `security_invoker` view (Postgres's default) runs with the querying user's own permissions, so `daily_digests`' existing RLS policy (`"subject or digest-opted-in friend can read a daily digest"`) still gates *row* access exactly as it does today — this view only changes what's exposed in the `distraction_count` *column* for a row the viewer can already see, mirroring the field-level toggles `session_status_events`' RLS already enforces at the row level, applied here at the column level instead.
  - `distraction_count` folds to `0` for a viewer who hasn't been granted `share_distraction_attempts`, matching `compute_daily_digests()`'s own existing zero-distraction convention (documented in that migration) rather than introducing a new "hidden" sentinel value.
  - `completed_sessions`, `abandoned_sessions`, and `recovery_rate` are passed through unchanged — none of them has a corresponding Task 10 toggle, so there's nothing to gate yet; if one gets added later, this view is exactly where it'd be added the same way.
- `digestApi.ts`: change the two `.from("daily_digests")` calls to `.from("daily_digests_visible")`. No other change to this file.

### Task 6: Unify Study Room "active participant" rules

**Goal:** Centralize "is this user an active participant in this room" into one Postgres function, so `generate-livekit-token`'s Edge Function and `studyRoomApi.ts`'s presence/listing queries can't independently drift out of agreement, even though they currently agree (see Decision 4).

**Depends on:** nothing.

**Interfaces:**
- Consumes: `study_room_participants` (unchanged schema).
- Produces:

  ```sql
  create or replace function public.is_active_room_participant(
    p_room_id uuid,
    p_user_id uuid
  )
  returns boolean
  language sql
  stable
  security definer
  set search_path = public
  as $$
    select exists (
      select 1 from study_room_participants
      where room_id = p_room_id
        and user_id = p_user_id
        and left_at is null
    );
  $$;

  revoke all on function public.is_active_room_participant(uuid, uuid) from public;
  grant execute on function public.is_active_room_participant(uuid, uuid) to authenticated, service_role;
  ```

  `generate-livekit-token/index.ts` calls this via RPC instead of its current inline `.select().eq(...).eq(...).is("left_at", null)` query.

**Deliverables:**
- New migration adding `is_active_room_participant` as above.
- `generate-livekit-token/index.ts`: replace the inline participant-row query (lines ~118–124 as of this plan) with `adminClient.rpc("is_active_room_participant", { p_room_id: roomId, p_user_id: callerId })`, keeping the same 403 response when it returns `false`.
- `studyRoomApi.ts`: leave its client-side `.is("left_at", null)` filters as they are for now — they run through RLS as the authenticated user, not the service-role client the Edge Function uses, so they can't call a `security definer` function the same way without a matching RPC wrapper exposed to `authenticated`. Documented here as a deliberate half-step: the Edge Function (the actual security boundary) is unified; making `studyRoomApi.ts`'s read-side queries call the same function via RPC instead of a repeated filter is a follow-up worth doing but isn't required to close the actual drift risk, since a client-side listing query being wrong only affects what a legitimate participant sees in their own UI, not who can obtain a valid video token.

**Definition of done:** `generate-livekit-token` calls `is_active_room_participant` instead of hand-rolling the query; a user who has left a room (`left_at` set) is still correctly refused a token; `scripts/verify-study-rooms.mjs` passes unchanged (it tests the observable behavior, which doesn't change).
