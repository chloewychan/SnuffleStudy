# SnuffleStudy V4.1 Implementation Plan — Sidebar Reformat

**Source scope document:** `docs/scope_summaries/V4.1_Scope_Summary.md`. This plan maps that document's General/Footer/Bunny/Study/Friends/Settings/Other-Pages sections into buildable tasks, ordered so that the two genuinely new pieces of shared infrastructure — the Nudge Vault backend and the persistent app-shell footer — land before anything that consumes them.

## Goal

Reformat the existing sidebar to its v4.1 shape: trim onboarding to one screen plus sign-in with fixed defaults baked in; remove the popup entirely; replace scattered per-section Refresh buttons with one in the Header; split the Bunny tab's save action and drop its toggle/status box; give the Task Vault a checkbox instead of delete, sorted so completed tasks sink to the bottom and the first uncompleted one becomes a new session's default goal; split Study Rooms into a Study-tab list/create/manage-access box and a persistent, tab-surviving joined-room footer; replace the old "Friend activity" panel with a multi-select Friends box (bulk nudge, bulk add-to-room, per-friend options, add/invite a friend) and a new Nudge Vault box (the user's own saved audio and written nudges); relocate incoming nudges and friend requests into a second persistent footer; and collapse the Settings tab's four-way sub-nav into stacked boxes. No new visual design — this release is restructuring and defaulting, not a redesign.

## Architecture

Unchanged from V3.4: WXT-based Chrome MV3 extension. Background service worker (`background/messageRouter.ts`'s single `switch (message.type)`) is the sole entry point for UI→backend communication, with the existing documented direct-call exceptions (`studyRoomApi.joinRoom`/`subscribeToPresence`, `producerTagApi.subscribeToRoomProducerTags`/`downloadTagAudio`/`blobToBase64`) unchanged. Domain layer stays free of browser/Supabase APIs. `infrastructure/backend/*Api.ts` wraps every Supabase call; Postgres RLS is the real security boundary everywhere.

New this version: two pieces of app-shell-level shared state, both provided once in `SidePanelApp.tsx` so they survive tab switches instead of living inside a conditionally-mounted tab component —

- **Study Room session state** (join/leave, video tiles, participants, camera/mic, selected-tile ids), via a new `StudyRoomSessionProvider`/`useStudyRoomSession()` context.
- **Incoming activity** (undismissed nudges, pending friend requests), via a new `useIncomingActivity()` hook, consumed by the new `AppFooter`.

A third piece of shared infrastructure, a **refresh registry**, replaces every panel's own Refresh button: any mounted panel that owns a fetch registers a callback; the Header's one Refresh button calls every currently-registered callback.

## Tech Stack

Unchanged: WXT, React, TypeScript, Supabase (Postgres + RLS + Edge Functions + Realtime + Storage), `idb` for local task/session storage, LiveKit for Study Room video/audio.

## Global Constraints

- Every UI→backend call goes through `sendMessage()`/`messageRouter.ts`'s switch, except the pre-existing documented direct-call exceptions above — unchanged this version, and nothing added by this plan needs a new exception.
- RLS is the real security boundary. Every new policy below is reasoned about as if a malicious client calls the underlying REST/RPC surface directly with arbitrary input, not just through the shipped UI.
- Migrations in `supabase/migrations/` are strictly cumulative/additive — never edit a shipped migration file.
- The Options page (`OptionsApp.tsx`) is not touched by this plan. It keeps its own Settings/History/Account/Friends/Privacy navigation, and keeps composing `AccountPage.tsx`/`FriendsPage.tsx`/`SettingsPage.tsx` directly. Several tasks below edit those three shared files — those edits apply to the Options page automatically, which is the intended, accepted consequence (friend management becomes sidebar-only once Task 9 moves it out of `AccountPage.tsx`), not a gap to patch.
- `LockedPage.tsx` (a separate route, not part of `SidePanelApp.tsx`'s own tree) is out of scope for the new footer — see Decision 4.

## Decisions

Judgment calls made once here, up front, so no task improvises one independently. Each is flagged **(overridable)** — say so and it changes.

1. **A vault-authored written nudge is copied into the `nudges` row at send time (`custom_body`), never a live reference to `nudge_vault_texts`.** A sent nudge must keep displaying correctly for its recipient even after the sender later deletes that vault text — a live foreign key would either block the delete or require `ON DELETE SET NULL`, silently blanking a message a friend already received. Copying avoids both. The catalog-based path (`message_id`) is untouched and kept alongside it (see Decision 5). **(overridable)**

2. **Deleting an audio Nudge Vault item is a soft delete** (`producer_tags.deleted_at`), not a row delete. `producer_tag_sends.tag_id` references `producer_tags(id)` with no cascade — a hard delete would fail outright the moment a tag has ever been sent to anyone, which is exactly the case a "delete this from my vault" button needs to support. The existing "owner can manage their own producer tags" policy already covers the UPDATE this needs; the existing immutable-columns trigger only pins `user_id`/`audio_url`/`duration_ms`/`created_at`, so a new `deleted_at` column is unrestricted by it. Every "my vault" list query filters `deleted_at is null`; the recipient-side playback path (`producer_tag_sends` → `producer_tags` join) is untouched and unaffected. **(overridable)**

3. **Nudge dismissal moves from a single watermark timestamp to a persisted set of dismissed nudge ids.** Today's `nudgeDismissalState.ts` stores one `dismissedThroughSentAt` cursor because only the single oldest undismissed nudge was ever shown at once. The new footer shows every undismissed nudge simultaneously, each with its own Dismiss button — a design where dismissing nudge B while nudge A (older) is still visible is a normal, expected action, which a single watermark cannot represent (advancing it past B would also hide A). This is a required correctness fix for the new UI, not a style choice. **(not meaningfully overridable — flag if you want a different persistence shape, e.g. per-nudge dismissed-at timestamps instead of a bare id set, but the watermark model cannot support the new footer at all)**

4. **`ActiveSessionView.tsx`'s existing "Study Room" section (participant list + one Nudge button per member, gated on `session.accountabilityGroupId`) is removed as part of Task 7.** It's already confirmed dead code — `accountabilityGroupId` has no producer anywhere in the codebase, so this branch never renders today. Leaving it in place alongside the new, real, persistent Study Room footer would mean two different "Study Room during a session" implementations sitting in the same file, one of them permanently unreachable — confusing for anyone reading this file later. Not named in the scope doc explicitly; added here because it duplicates exactly what Task 7 makes real. **(overridable — leave it in place, dead, if you'd rather this plan not touch a file the scope doc didn't name)**

5. **The new `AppFooter` mounts only inside `SidePanelApp.tsx`'s own render branches** — the no-session tab view, the active-session view, and the COMPLETED/ABANDONED screens (per your confirmation that footers should render "everywhere except onboarding"). `LockedPage.tsx` is a separate route this plan doesn't touch; if a hard-blocked site's own page should also show the footer, that's a follow-up, not part of this plan. **(overridable)**

6. **`NUDGE_SEND`'s existing catalog path (`messageId` against the fixed `NUDGE_MESSAGES` list) is kept, not replaced.** The scope doc explicitly defers removing `NUDGE_MESSAGES` to v4.2. Rather than repoint the one existing message type at a new, incompatible payload shape, `NUDGE_SEND`'s payload becomes a union — `{ friendUserId } & ({ messageId } | { vaultTextId })` — so the old path keeps working unchanged for any caller that still uses it, and the new vault path is purely additive. **(overridable)**

7. **Every "pick a vault nudge, send it to N selected targets" action (Friends box; Study Room footer) fires one existing per-target message per selection — `NUDGE_SEND` or `PRODUCER_TAG_SEND_TO_FRIEND` once per selected friend, called in a loop from the frontend.** No new bulk-send message is added. This matches how every other multi-target action in this codebase already works (e.g. `ManageAccessSection`'s per-friend `STUDY_ROOM_INVITEE_ADD`/`REMOVE` calls) and keeps the server-side cooldown/permission gate (`can_send_nudge()`) evaluated per-recipient, which a batched endpoint would have to reimplement anyway. **(overridable)**

8. **The Study Room footer's Nudge button targets selected participant tiles individually** (`NUDGE_SEND`/`PRODUCER_TAG_SEND_TO_FRIEND` per selected participant's `userId`), not the existing room-wide `PRODUCER_TAG_SEND_TO_ROOM` broadcast. The spec asks for "sends a nudge to all the friends that were selected" — a subset of the room, not everyone in it — which only the per-target messages can express. A participant who isn't actually a friend of the sender will have their send rejected server-side by `can_send_nudge()`/`producer_tag_sends`' RLS, surfaced as the same inline error the Friends box already shows for that case — a pre-existing constraint, not something this plan introduces or needs to work around. **(overridable)**

9. **The room-wide producer-tag broadcast mechanism (`PRODUCER_TAG_SEND_TO_ROOM`, `RoomProducerTagBroadcast`, `subscribeToRoomProducerTags`) is left in place, unused by any UI after this version**, rather than deleted. It becomes dead code the moment Task 7 removes in-room recording, exactly the kind of cleanup the scope doc defers to v4.2 (its optional item for this footer). Removing it now would mean deleting and potentially re-adding backend surface within one release for no functional reason. **(overridable — pull it into this plan's scope if you'd rather not carry it as v4.2 debt)**

## Task 1 — Nudge Vault schema + API

### Goal

Give every user a personal, deletable library of audio and written nudges — the source both for the new Nudge Vault box's own lists and for every "pick a nudge to send" dropdown elsewhere (Friends box, Study Room footer). Reuse `producer_tags` for the audio half (it already is exactly "an audio clip I recorded," just missing a "list mine" query and a safe delete); add one small new table for the written half.

### Depends on

Nothing. Do first.

### Scope

**In:** the schema/API/message changes below. **Out:** any UI (Tasks 7–9 build the boxes/dropdowns that consume this). Out: removing `NUDGE_MESSAGES` or its send path (Decision 6, v4.2).

### Interfaces

**Produces (SQL — `supabase/migrations/20260815000045_v4.1_nudge_vault.sql`):**

```sql
-- === nudge_vault_texts: the written half of the Nudge Vault. Audio reuses producer_tags
-- directly (see below) - no parallel table needed there, just list/soft-delete it doesn't have yet.
create table nudge_vault_texts (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id),
  body        text not null check (char_length(body) between 1 and 500),
  created_at  timestamptz not null default now()
);

alter table nudge_vault_texts enable row level security;

create policy "owner can manage their own vault texts"
  on nudge_vault_texts for all
  using (user_id = auth.uid())
  with check (user_id = auth.uid());

grant select, insert, update, delete on nudge_vault_texts to authenticated;
grant select, insert, update, delete on nudge_vault_texts to service_role;

-- === producer_tags: soft-delete (Decision 2). The existing "owner can manage their own producer
-- tags" FOR ALL policy (20260815000002) already covers this UPDATE; the existing immutable-
-- columns trigger (20260815000021) only pins user_id/audio_url/duration_ms/created_at, so this
-- new column is unrestricted by it - no trigger/policy change needed, only the column itself.
alter table producer_tags add column deleted_at timestamptz;

-- === nudges: a vault-authored written nudge is copied into custom_body at send time (Decision
-- 1) rather than referencing nudge_vault_texts live. message_id becomes nullable; exactly one of
-- the two is set per row.
alter table nudges alter column message_id drop not null;
alter table nudges add column custom_body text;
alter table nudges add constraint nudges_exactly_one_body check (
  (message_id is not null) <> (custom_body is not null)
);
```

**Produces (TypeScript — `infrastructure/backend/nudgeVaultApi.ts`, new):**
```typescript
import { supabase } from "./supabaseClient";
import { requireUserId } from "./authHelpers";

export interface NudgeVaultText {
  id: string;
  body: string;
  createdAt: number;
}

interface NudgeVaultTextRow {
  id: string;
  body: string;
  created_at: string;
}

function toNudgeVaultText(row: NudgeVaultTextRow): NudgeVaultText {
  return { id: row.id, body: row.body, createdAt: new Date(row.created_at).getTime() };
}

export async function createVaultText(body: string): Promise<NudgeVaultText> {
  const userId = await requireUserId();
  const { data, error } = await supabase
    .from("nudge_vault_texts")
    .insert({ user_id: userId, body })
    .select()
    .single();
  if (error || !data) throw new Error(error?.message ?? "Could not save this nudge.");
  return toNudgeVaultText(data);
}

export async function listMyVaultTexts(): Promise<NudgeVaultText[]> {
  await requireUserId();
  const { data, error } = await supabase
    .from("nudge_vault_texts")
    .select()
    .order("created_at", { ascending: false });
  if (error) throw new Error(error.message);
  return (data ?? []).map(toNudgeVaultText);
}

export async function deleteVaultText(id: string): Promise<void> {
  const { error, data } = await supabase.from("nudge_vault_texts").delete().eq("id", id).select();
  if (error) throw new Error(error.message);
  if (!data || data.length === 0) throw new Error("That nudge is already gone.");
}
```

**Produces (`infrastructure/backend/producerTagApi.ts` additions):**
```typescript
// "My vault" list - the owner's own non-deleted tags, newest first. Distinct from
// PRODUCER_TAG_SENDS_FETCH (incoming, from friends) and the room-broadcast path - this is
// specifically "audio I've recorded and kept," per Task 9's Nudge Vault box.
export async function listMine(): Promise<ProducerTag[]> {
  const userId = await requireUserId();
  const { data, error } = await supabase
    .from("producer_tags")
    .select()
    .eq("user_id", userId)
    .is("deleted_at", null)
    .order("created_at", { ascending: false });
  if (error) throw new Error(error.message);
  return (data as ProducerTagRow[]).map(toProducerTag);
}

// Soft delete (Decision 2) - a past send referencing this tag keeps playing for its recipient;
// this only removes it from the owner's own vault list and from future send dropdowns.
export async function softDelete(tagId: string): Promise<void> {
  const { error, data } = await supabase
    .from("producer_tags")
    .update({ deleted_at: new Date().toISOString() })
    .eq("id", tagId)
    .select();
  if (error) throw new Error(error.message);
  if (!data || data.length === 0) throw new Error("That nudge is already gone.");
}
```

**Produces (`infrastructure/backend/nudgeApi.ts` changes):**
```typescript
export interface FriendNudge {
  id: string;
  senderUserId: string;
  recipientUserId: string;
  messageId: string | null;   // CHANGED: nullable — exactly one of messageId/customBody is set
  customBody: string | null;  // NEW
  sentAt: number;
}

export type NudgeSource =
  | { kind: "catalog"; messageId: string }
  | { kind: "vault"; vaultTextId: string };

export async function sendNudge(
  friendUserId: string,
  source: NudgeSource
): Promise<{ ok: boolean; error?: string }> {
  const auth = await checkAuth();
  if (!auth.ok) return { ok: false, error: "Could not verify your sign-in status." };
  if (!auth.userId) return { ok: false, error: "Not signed in." };

  let insertPayload: { sender_user_id: string; recipient_user_id: string; message_id?: string; custom_body?: string };

  if (source.kind === "catalog") {
    if (!isValidNudgeMessageId(source.messageId)) {
      return { ok: false, error: "Not a recognized nudge message." };
    }
    insertPayload = { sender_user_id: auth.userId, recipient_user_id: friendUserId, message_id: source.messageId };
  } else {
    // The vault text must belong to the sender - a plain select under RLS already enforces this;
    // a missing/foreign id returns no row rather than another user's text.
    const { data: vaultText, error: vaultError } = await supabase
      .from("nudge_vault_texts")
      .select("body")
      .eq("id", source.vaultTextId)
      .single();
    if (vaultError || !vaultText) {
      return { ok: false, error: "This nudge no longer exists in your vault." };
    }
    insertPayload = { sender_user_id: auth.userId, recipient_user_id: friendUserId, custom_body: vaultText.body };
  }

  const { error } = await supabase.from("nudges").insert(insertPayload);
  if (error) {
    console.error("Failed to send nudge", error);
    return { ok: false, error: "Couldn't send that nudge — this friend may have nudges turned off, or you're on cooldown." };
  }
  return { ok: true };
}
```
`toFriendNudge()`'s row mapper gains `messageId: row.message_id` (now possibly `null`) and `customBody: row.custom_body`. Every other function in this file (`fetchIncomingNudges`, `pollIncomingNudges`, `queryNudgesSince`) is unchanged — only the row shape they return grows one field.

```typescript
import { createContext, useContext, useEffect, useRef, useCallback } from "react";

interface RefreshRegistryValue {
  register(fn: () => void): () => void; // returns an unregister function
  refreshAll(): void;
}

const RefreshRegistryContext = createContext<RefreshRegistryValue | null>(null);

export function RefreshRegistryProvider({ children }: { children: React.ReactNode }) {
  const refreshersRef = useRef(new Set<() => void>());

  const register = useCallback((fn: () => void) => {
    refreshersRef.current.add(fn);
    return () => refreshersRef.current.delete(fn);
  }, []);

  const refreshAll = useCallback(() => {
    for (const fn of refreshersRef.current) fn();
  }, []);

  return (
    <RefreshRegistryContext.Provider value={{ register, refreshAll }}>
      {children}
    </RefreshRegistryContext.Provider>
  );
}

// Registers `fn` for as long as the calling component is mounted - only currently-visible
// panels are ever in the set, so refreshAll() never touches an unmounted tab's stale closure.
// `fn` itself should be stable (useCallback) in the caller, same contract useEffect deps already
// expect - an unstable fn just means slightly more churn in the registered set, not a bug.
export function useRegisterRefresh(fn: () => void): void {
  const ctx = useContext(RefreshRegistryContext);
  useEffect(() => {
    if (!ctx) return;
    return ctx.register(fn);
  }, [ctx, fn]);
}

export function useRefreshAll(): () => void {
  const ctx = useContext(RefreshRegistryContext);
  if (!ctx) throw new Error("useRefreshAll must be used within a RefreshRegistryProvider");
  return ctx.refreshAll;
}
```

```typescript
export function sortTasksForDisplay(tasks: Task[]): Task[] {
```
