## Judgment calls

1. **`selectedFriendId`/`effectiveFriendId` live in the container, not in the hook or either section.** The plan describes the hook as wrapping "the five `load*` functions ... and their state" — `selectedFriendId` isn't loaded from anywhere, it's local picker-selection UI state, so putting it in the hook would have been scope creep beyond what the plan asked the hook to own. It can't live inside `NudgeSendForm` either (the only place the `<select>` renders it), because `ProducerTagSection` also needs to read the same `effectiveFriendId` as its send target — exactly the pre-split behavior, where both features deliberately share one friend-picker selection (see the original file's own comment, carried into `ProducerTagSection.tsx`). The container is the one place both siblings can read it, so it stays there.
2. **`NudgeSendForm` and `ProducerTagSection` own their own send-busy/error/success state and send handlers internally, rather than the hook owning them.** The plan's literal wording scopes the hook to the five `load*` functions; `handleSendNudge`/`handleSendProducerTag` and their busy/error/success flags aren't `load*` functions, and nothing outside each section ever reads that state. Keeping them local: (a) matches the plan's literal hook scope instead of expanding it, (b) keeps the hook a pure "fetch state" concern, and (c) means the container doesn't need to thread five extra props to each section merely to relay state nothing else touches. `effectiveFriendId` (needed by both) is the one thing that does cross the boundary, and it's passed as a prop precisely because it's shared.
3. **`dismissNudge`/`dismissedNudgeIds` and the two derived values (`visibleNudge`, `friendDigests`) went into the hook, not the container**, even though they're not literally `load*` functions either. Judged this differently from judgment call 2 because these are pure derivations/mutations of the hook's own fetch state (nudges, digests) that nothing besides "what does the loaded nudge/digest data currently look like" needs — computing them next to the state they're derived from avoids exporting raw `incomingNudges`/`digests`/`dismissedNudgeIds` out of the hook just so the container could recompute the same thing. This is the plan's "and their state" clause read to include state that's a direct function of the loaded data, not just the loading flags/errors themselves.
4. **`DigestCard` and `IncomingProducerTagCard` stay as local (non-exported) sub-components inside `DigestSection.tsx`/`ProducerTagSection.tsx` respectively**, rather than getting their own files. The plan's file structure names exactly five files plus the hook — it does not list either of these as separate extractions, and each is only ever used by its one parent section, so nesting them (matching how they already lived directly above their section in the original file) is the more literal reading of "mechanical extraction."
5. **`FriendEventFeed` takes one `onRefresh` callback, not four individual `load*` props.** The Refresh button has never triggered just one fetch — bundling four calls behind one button is existing, tested behavior (`FriendGroupPanel.test.tsx`'s "also refetches incoming nudges... when the Refresh button is clicked" test), so the container composes that bundle (`handleRefresh`) and hands the child a single action, keeping `FriendEventFeed` from needing to know which other sections exist.
