## What I built

- **`supabase/migrations/20260815000031_v3.2_active_room_participant.sql`** (new): creates `public.is_active_room_participant(p_room_id uuid, p_user_id uuid) returns boolean`, `language sql stable security definer set search_path = public`, body `select exists (select 1 from study_room_participants where room_id = p_room_id and user_id = p_user_id and left_at is null)` — the plan's SQL used **verbatim** (only the header comment is new prose). Updated the header comment block to describe the new authorization model and to note the deliberate non-change to `studyRoomApi.ts`. No other line in this file changed — the LiveKit token-minting logic below the check is untouched.
- **`snufflestudy/src/infrastructure/backend/studyRoomApi.ts`**: **not touched**, per the plan's explicit scope (documented as a deliberate half-step, not a gap — the client-side listing queries run through RLS as the `authenticated` role, not the service-role client this Edge Function uses, so they can't call this SECURITY DEFINER function the same way without a separate RPC wrapper exposed to `authenticated`, which is a real follow-up but not required to close the actual drift risk in the security boundary).

## Judgment calls

1. **Named the new function `is_active_room_participant` rather than overloading or renaming the pre-existing `is_room_participant`.** The plan specifies this name directly, and my own check confirmed the two functions answer genuinely different questions (any-time participant, used for RLS discovery, vs. currently-active participant, used for token minting) — so a new, distinctly-named function is correct, not an accidental duplicate. Documented the distinction explicitly in the migration's header comment to prevent future confusion between the two.
2. **Kept the RPC call's error handling shape identical to the original query's** (`participantError` → 500 "Server error"; falsy result → 403 "Not a participant of this room") rather than introducing new status codes or messages, since the task's Definition of Done requires "keeping the same 403 response when it returns `false`" and the plan gives no reason to change the 500 path either.
3. **Did not add a client-facing RPC wrapper for `authenticated`** to let `studyRoomApi.ts` call this function later, beyond granting `authenticated` execute (matching this schema's existing convention of granting both roles on every helper of this shape) — actually wiring `studyRoomApi.ts` to use it is explicitly out of scope per the plan's "Explicitly out of scope" section, and I did not touch that file.
