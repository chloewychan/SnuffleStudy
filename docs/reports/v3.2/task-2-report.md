## Judgment calls / deviations from the plan, and why

1. **Added a `selfLoaded` boolean to three panels, beyond the plan's literal "gains the same `selfUserId` state shape the other three panels already have."** This was necessary, not cosmetic, for two concrete reasons I verified by running the tests, not just reasoning about it:
   - Without it, gating a *whole-branch UI swap* (StudyRoomPanel's entire body, or a section's entire content) on bare `selfUserId === null` means a **signed-in** user would see the sign-in prompt flash on every mount, for the brief window before `AUTH_GET_SESSION` resolves (since `selfUserId` starts at its initial value of `null`).
   - For `UnlockRequestPanel.tsx` specifically, this isn't hypothetical: the existing test *"never shows the viewer's own pending request in the friend-approval list, even if the requests fetch resolves before the self-identity fetch"* deliberately holds `AUTH_GET_SESSION` unresolved and asserts `"No pending unlock requests from friends."` renders during that window. A bare `selfUserId === null` gate would have shown my new sign-in prompt instead at that exact assertion, breaking this regression test outright. I ran the suite, saw this fail, and fixed it with `selfLoaded` rather than weakening the existing test.
   - `FriendGroupPanel.tsx` didn't need a new flag because it already has an equivalent signal: `loadFriends()` sets `selfUserId` synchronously before it ever sets `friendIds`, so gating on `friendIds` (already non-null only once resolved) is a free, already-present "self-identity is known" proxy. Reused it instead of adding a redundant field to a file Task 7 is about to split anyway.

2. **Added `&& !selfError` to the three `selfLoaded` gates (`StudyRoomPanel`, `TempPasscodePanel`, `UnlockRequestPanel`) — not in my first draft.** I caught this via the actual test run, not by inspection: `FriendsTab.test.tsx`'s `"does not crash when the friends/rooms fetches fail"` test rejects every `sendMessage` call (including `AUTH_GET_SESSION`) with `new Error("network down")`. Before this fix, a rejected `AUTH_GET_SESSION` left `selfUserId` at its initial `null` (the `.catch()` only sets `selfError`, never touches `selfUserId`), which my gate misread as "confirmed signed out" and rendered the sign-in prompt instead of the pre-existing `"Could not load rooms: network down"` error text the test expects. A failed *check* is not the same fact as a confirmed *no session*, and asserting "sign in" when the real problem is "couldn't verify" would be actively wrong. Fixed by requiring `!selfError` too, so an auth-check failure falls through to each panel's own pre-existing error handling (which already surfaces the same underlying failure via `loadRooms()`/etc.), rather than asserting a sign-in state we don't actually know.
   - `FriendGroupPanel.tsx` didn't need this guard either, for the same reason as judgment call #1: a failed `AUTH_GET_SESSION` there sets `friendsError` and explicitly returns before `friendIds` is ever set, so `friendIds` stays `null` and my `friendIds && ...`-gated branches never fire in that case — already correct by construction.
3. **`FriendGroupPanel.tsx`'s Producer Tags section is untouched, deliberately.** The plan's Deliverables for this file name exactly two sections to check/fix — "nudge-send section, digest section" — not Producer Tags. Signed out, Producer Tags' send button is simply disabled (`sendDisabled={!effectiveFriendId}`) with no explanation of its own, but the now-fixed nudge-send section directly above it already surfaces the actual reason ("Sign in to nudge friends...") before the user ever reaches the Producer Tags section, so there's no dead end reached without an explanation first. Left as the plan scoped it rather than expanding scope into a section it didn't name (also: Task 7 splits this file next, so minimizing my footprint here is worth it).
4. **`StudyRoomPanel`'s Producer Tags/participant sections needed no separate gate.** They only render inside the `if (joinedRoom)` branch, and `joinedRoom` can only become non-null via `handleJoinRoom`, which calls `studyRoomApi.joinRoom` — itself gated by `requireUserId()`. A signed-out user can never reach that branch, so the top-level `selfUserId === null` gate on the base view is sufficient.
