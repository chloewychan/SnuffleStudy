## Judgment calls

1. **Used the plan's literal inline `exists(...)` check rather than the pre-existing `friend_has_granted_distraction_visibility(subject, viewer)` helper**, even though that helper already implements almost the identical check (plus an extra group-membership floor) and is used for the structurally analogous `session_status_events` DISTRACTION_ATTEMPT gate. I considered swapping it in for consistency/defense-in-depth, but the task brief was explicit — use the plan's given SQL verbatim, adjusting only for real column/type mismatches, which the live-schema check found none of. Functionally the two are equivalent today: `daily_digests_visible` is a `security_invoker` view, so `daily_digests`' own base-table RLS (`"subject or digest-opted-in group-mate can read a daily digest"`, `20260815000011`) already requires shared group membership before a row reaches this view's `CASE` expression at all — the helper's extra group check would be redundant, not corrective, in this specific call site. Flagged here rather than silently substituted, per this session's own working style.
2. **Did not revoke `authenticated`'s existing `select` grant on the raw `daily_digests` table.** This is a real, worth-flagging residual gap, not an oversight: a `security_invoker` view requires the invoking role to retain its own privileges (including base-table grants) for RLS to apply through the view at all — the plan's own Decision 3 says as much ("runs with the querying user's own permissions"). That means the raw table remains directly `SELECT`-able by any `authenticated` client — including a technically-savvy user hitting the Supabase REST API directly with their own session JWT, bypassing `digestApi.ts`'s code path (and thus the view) entirely, and seeing the real, unredacted `distraction_count`. Closing this fully would require a different mechanism (e.g., a non-invoker/definer-style view combined with `FORCE ROW LEVEL SECURITY` and revoking the base table grant), which is a materially bigger, riskier change than "point the client at a view" — out of scope for what this task asked for and not something I made unilaterally. **Flagging as open** (see below) rather than silently accepting or silently fixing.
3. **Extended `digestApi.test.ts`'s two table-name assertions** even though the task said "no other change to that file" (`digestApi.ts`, not its test file). Necessary: the assertions pin the literal `.from(...)` argument, which changed as a direct, intended consequence of the one sanctioned edit. Leaving them unchanged would have made `npx vitest run` fail, which the task explicitly asked me to confirm passes clean.
4. **`snufflestudy/scripts/_tmp-check-schema.mjs`/`_tmp-apply-migration.mjs`** were created transiently to query the live schema and attempt to apply the migration, then deleted — not part of the deliverable, not committed (confirmed via `git status` before committing).
