## Judgment calls

1. **Auto-generated group name.** Used `` `Friends of ${session?.user.email ?? "me"}` `` (the plan's own first suggested option) rather than the plain `"Friends"` alternative, since it's marginally more traceable in a database admin view without costing anything — the plan is explicit this string is cosmetic and never rendered, so either is correct.
2. **Collapsing the two-step flow into one function vs. two.** The plan's deliverable text describes one "Invite a friend" action calling both `GROUP_CREATE` then `GROUP_GENERATE_INVITE_CODE` in sequence. I implemented this as a single `handleInviteAFriend()` async function (rather than keeping `handleCreateGroup`/`handleGenerateInvite` as two functions called back-to-back) since there's now only one button and one code path — no state where a group exists without also having (or having failed to get) an invite code in flight. `groupBusy`/`inviteBusy` are both still tracked separately internally (so a mid-flight failure at either step surfaces the right error), but the button only shows one combined busy label.
3. **`Delete account`'s "friend groups" → "friend connections", not "friendships."** Chose "connections" specifically to avoid implying the real pairwise-`friendships` table rebuild that Scope explicitly marks out-of-scope for this version — "friend connections" is accurate description of what's deleted without naming a schema concept the codebase doesn't have yet.
4. **"Group ID" → "Friend list ID", "Leave group" → "Leave."** The plan's Deliverables text only explicitly calls out the section heading ("Group members" → "Your friends"), but the DoD requires zero "group" strings anywhere in the sidepanel/options pages, and this section's field label, button, confirm dialog, and success/error copy all said "group" too. Relabeled all of them consistently with the new "Your friends" framing rather than leaving a "Your friends" heading sitting above a "Group ID" field.
5. **Two borderline "study group"/"study room" strings, resolved in favor of literal DoD compliance.** `StudyRoomPanel.tsx`'s `"Rooms in your groups"` heading is genuinely about the friend-group visibility concept (in scope, changed without hesitation). Its `placeholder="e.g. Thursday study group"` is different in kind — an example room name using the ordinary English phrase "study group" (a group of people studying together), unrelated to the app's Friend Group backend entity, and not part of any file or string the plan names for this task. I changed it anyway (to `"e.g. Thursday study session"`) purely because the DoD's literal wording ("no visible UI string says 'group' anywhere in the sidepanel") would otherwise fail on inspection, and the swap costs nothing semantically. Flagging this explicitly since it's the one change in this diff that isn't really about the friend-group cosmetic rename — a reviewer who disagrees can revert just this one line safely, it has zero interaction with anything else in this task.
6. **Server-mocked error strings in tests left alone.** `FriendsPage.test.tsx` has a test mocking `FRIENDSHIP_SETTINGS_UPDATE` returning `{ ok: false, error: "no shared group" }` and asserting that opaque string renders — this is testing that arbitrary server error text passes through untouched, not asserting any hardcoded UI copy this task owns, so it was left as-is.
