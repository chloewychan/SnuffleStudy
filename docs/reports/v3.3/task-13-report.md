## Three real gaps found by actually running this against the live DB — not by reading the plan's SQL alone

This continues the pattern this run has already hit three times (`20260815000035` for `profiles`, `20260815000038` for `session_end_requests`). This task found three distinct issues, one of which is more serious than anything found so far this run:

1. **Missing `service_role` grant** (same category as the two precedents). The plan's literal SQL grants only `authenticated`. Reproduced live: a service-role insert/delete against `study_room_invitees` failed with "permission denied for table study_room_invitees". Fixed with the same asymmetric `authenticated`+`service_role` grant split every other table in this schema uses.

2. **`delete_account_data()` never taught about `study_room_invitees`** (same category). Reproduced live by mirroring the *real* `delete-account` Edge Function's exact sequence (`adminClient.rpc("delete_account_data", ...)` then `adminClient.auth.admin.deleteUser()`) for both a user who was only an invitee on someone else's room, and a user who owned a room with an active invitee — both failed with "Database error deleting user" until fixed. Fixed by adding two statements: delete invitee rows for rooms the caller owns (before the existing room cascade), and delete the caller's own invitee rows on rooms they don't own. `invited_by` needs no separate cleanup statement — it's always the room's owner (the table's only INSERT path enforces `sr.owner_user_id = auth.uid()`), so every such row is already covered by the owned-room cleanup.

3. **Infinite RLS recursion — a new mutual A/B cycle between `study_rooms` and `study_room_invitees`** (a different, more serious category — this one isn't a missing-grant/missing-cleanup gap, it's a correctness bug in the plan's given SQL that breaks the feature outright). The plan's literal `"owner can manage invitees for their own room"` policy is a raw subquery into `study_rooms`. Combined with this task's own new `study_rooms` SELECT policy raw-subquerying into `study_room_invitees`, this recreates exactly the bug class `20260815000003_v2_fix_grants_and_rls_recursion.sql` already fixed once for `study_rooms`/`study_room_participants` — a mutual A-queries-B/B-queries-A cycle. Reproduced live: creating a study room (`studyRoomApi.createRoom`'s exact `.insert(...).select().single()` call) failed outright with `"infinite recursion detected in policy for relation \"study_rooms\""`, applied against the plan's literal SQL, verbatim. Fixed the same way `20260815000003` fixed the original cycle: routed `study_room_invitees`' policy through `is_room_owner(room_id, auth.uid())` — the existing `SECURITY DEFINER` helper from that migration, already reused by `study_room_participants`' own SELECT policy for the same purpose — instead of a raw subquery. This was the minimal fix: only that one policy needed to change; `study_rooms`' new SELECT policy still raw-subqueries into `study_room_invitees` exactly as the plan wrote it, and that direction remains safe because `study_room_invitees`' policies no longer subquery back into `study_rooms`.

**A fourth, related finding on the same policy** (not a missing-grant/cleanup bug, a behavioral gap against the DoD's own text): the plan's literal `study_room_participants` OR-clause in the new `study_rooms` SELECT policy — copied verbatim from the pre-existing policy — doesn't filter on `left_at is null`, so it matches *any* historical participant row, not just a currently-active one. Before this task that was harmless (group-sharing was the real gate, this clause only ever widened an already-visible set); this task removes group-sharing as a basis entirely, turning the same unscoped clause into a standing loophole — someone who joined a room once, left, and had their invite explicitly revoked would retain read access forever, directly contradicting the DoD's own text: *"Account A removes the invite — Account B, if not currently in the room, loses visibility to it again."* Reproduced live (the negative-case test failed with this clause unscoped); fixed by adding `and srp.left_at is null` to that clause. Confirmed no other code path depends on the unscoped form (grepped every `.from("study_rooms")` call site — `createRoom`/`listRooms`/`archiveRoom` in `studyRoomApi.ts` only).

All four fixes are documented at length in `supabase/migrations/20260815000039_v3.3_study_room_invitees.sql`'s own header comments, following the exact precedent `20260815000035`/`20260815000038` already set.

## Judgment calls

- **Picker UI shape**: `ManageAccessSection` re-fetches `AUTH_GET_SESSION` independently rather than accepting `selfUserId` as a prop from `StudyRoomPanel` — this mirrors `LockedPage.tsx`'s own pattern (re-deriving self rather than assuming which id in `GROUP_LIST_MEMBERS`' results is "self") and keeps the component self-contained, at the cost of one extra round trip per expand. Not a correctness issue (the room-list view already gates on `room.ownerUserId === selfUserId` before this component ever mounts).
- **One expanded room at a time**: chosen to mirror `HistoryPage.tsx`'s existing `expandedSessionId` convention rather than a per-room boolean map — there's no product requirement for multiple simultaneously-expanded "Manage access" sections.
