### Two real bugs found by live verification, fixed via a follow-up migration

Running the mandated live negative-case script (not just inspecting the policy SQL) surfaced two genuine defects the plan's literal SQL text didn't anticipate — both fixed in **`supabase/migrations/20260815000035_v3.3_profiles_grants_and_account_deletion.sql`**:

1. **Missing `service_role` grant.** The plan's own SQL block only grants `authenticated`. Every other core table in this schema (`friend_groups`, `unlock_requests`, `nudges`, etc. — see `20260815000003_v2_fix_grants_and_rls_recursion.sql`'s "Bug 1") grants both `authenticated` **and** `service_role` at the table level — Postgres GRANTs are separate from RLS and from `service_role`'s RLS-bypass. A `service_role`-keyed client got `permission denied for table profiles` on every direct query. Fixed with `grant select, insert, update, delete on profiles to service_role;` (asymmetric with `authenticated`'s `select, insert, update`, mirroring `daily_digests`' existing asymmetric-grant precedent — there's no client-facing delete policy on `profiles`, so granting `authenticated` DELETE would be a no-op RLS blocks anyway).
2. **Account deletion regression.** `delete_account_data()` (`20260815000032_v3.2_account_deletion.sql`, v3.2 Task 8) predates `profiles` and never deletes a caller's `profiles` row. Since `profiles.user_id references auth.users(id)` with no `ON DELETE CASCADE` (this schema has none, anywhere), **any real user who ever saves a bunny/human name would fail to delete their account** — `supabase/functions/delete-account/index.ts`'s Step 3 (`adminClient.auth.admin.deleteUser`) would hit a live FK violation after Step 1 (`delete_account_data`) silently left the `profiles` row behind. I reproduced this exact failure live (see Verification below) before fixing it. Fixed by re-declaring `delete_account_data` (`create or replace function`, same technique `20260815000029` uses to amend an existing SECURITY DEFINER function) with one added `delete from profiles where user_id = p_user_id;` statement, grouped with the other simple single-owner-column deletes; every other line is copied verbatim from `20260815000032`.

This second fix is a deliberate scope decision beyond the plan's literal Deliverables text (which only says "Migration as above" for the `profiles` table itself), made because: it's a real, live-reproduced defect: it's squarely a security/privacy-critical concern (account deletion is a data-removal guarantee this exact codebase has already had to get right once, in v3.2 Task 8); and this task's own instructions explicitly call for treating Task 8's negative case seriously rather than as an afterthought.
