**A real gap found, not in the plan's prose but in its literal SQL block.** The plan's given migration is a bare `alter table ... drop column code_hash, code_salt, failed_attempts, locked_until; drop function ...`. Checking every migration that touches these four columns (not just the ones the plan cited) surfaced that `20260815000026_v2_temp_passcode_group_floor.sql` — the table's *current* INSERT policy ("users can create their own genuinely-pending temp passcode requests") — has a `WITH CHECK` clause that directly references `code_hash is null and code_salt is null and failed_attempts = 0 and locked_until is null`. Postgres tracks a policy's reference to a column as a real dependency; a bare `DROP COLUMN` against a column an active policy's `USING`/`WITH CHECK` expression reads fails outright ("cannot drop column ... because other objects depend on it"), it does not silently cascade. Applying the plan's literal SQL as written would have failed at `apply-migrations.mjs` time. Fixed by having the migration drop + recreate that policy *first*, with only the four code-specific predicates removed — `requester_user_id = auth.uid()`, `status = 'pending'`, `expires_at is null`, the self-assignment guard, and the `users_share_a_group` floor are all preserved verbatim. This is documented at length in the migration's own header comment. Confirmed this was the *only* blocking dependency — grepped every migration for these four column names; the only other references are `20260815000016`'s original column adds/column-level grants (which Postgres auto-drops with the column, no dependency error) and `20260815000017`'s now-dropped RPC (already handled by the plan's `drop function if exists`).

No other claims in the plan's Task 10 block needed correction — the message contract, `claimApproval`'s given implementation, and every file-level change matched what actually needed to happen.

### A real, expected limitation found by actually running the live scripts

Both live scripts surfaced the same thing: the **deployed** `approve-temp-passcode` Edge Function on the live project is still the pre-Task-10 version. Per this codebase's established convention (`docs/qa/V3.2_Two_Account_QA_Script.md`'s "Deploy/redeploy the two changed Edge Functions" section) and this task's own explicit instruction, Edge Function deployment happens once, at the Task 15 two-account QA gate — not per implementation task. The *currently live* function still tries to write `code_hash`/`code_salt`/`failed_attempts`/`locked_until`, which this task's migration just dropped, so calling it right now returns HTTP 500 ("Failed to approve request"). This is not a defect in this task's work — the repo's `approve-temp-passcode/index.ts` is correct (matches the plan, unit-tested) — it's a deliberate, temporary gap between the live schema and the not-yet-redeployed function, exactly as the deployment-deferral convention predicts. Both scripts log this live call's real result as an informational note (not scored as a failure) and then simulate what the redeployed function will do — a service-role update to `status='approved'`/`expires_at`/`resolved_at` only, since there's nothing else left to set — to still prove, live and today, everything Task 10 actually controls: the RLS boundary, the schema, and `claimApproval`'s own query.
