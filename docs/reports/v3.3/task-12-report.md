## A real gap found, the same way Tasks 8 and 10 found theirs

The plan's literal migration SQL for this task grants only `authenticated`. Every other table in this schema that references `auth.users(id)` grants **both** `authenticated` and `service_role` at the table level (established in `20260815000003`, `20260815000007`, `20260815000010`, `20260815000014`, and — twice already this same run — `20260815000035` for `profiles`). Confirmed live: a service-role cleanup call against `session_end_requests` failed with "permission denied for table session_end_requests" until the missing grant was added.

**A second, more serious gap, same category:** `delete_account_data()` (last amended by `20260815000035` for `profiles`) predates `session_end_requests` entirely and never cleaned it up. Since `session_end_requests.requester_user_id`/`resolved_by` both reference `auth.users(id)` with no `ON DELETE CASCADE` (true of every table in this schema), any real user who ever requested or resolved a temporary end-session pass would hit "Database error deleting user" on "Delete account" — reproduced live, directly, before being fixed.

Both fixes are in `supabase/migrations/20260815000038_v3.3_session_end_requests.sql`'s own header comment at length, following the identical pattern and reasoning `20260815000035` already established for `profiles` (this migration says so explicitly, and cites it).

## What was built

- **Migration** `supabase/migrations/20260815000038_v3.3_session_end_requests.sql`: creates `session_end_requests` and its three RLS policies exactly per the plan (mirroring `unlock_requests`' shape, retargeted at ending a session instead of unlocking a hostname), plus the `service_role` grant and `delete_account_data()` amendment described above.
- **`domain/accountability/sessionEndRequest.ts`** (new): the `SessionEndRequest` interface, exactly per the plan.
- **`infrastructure/backend/sessionEndRequestApi.ts`** (new): `createRequest`/`resolveRequest`/`fetchRelevantSessionEndRequests`/`pollRelevantSessionEndRequests` mirror `unlockRequestApi.ts`'s shape exactly (same `requireUserId()`+throw and `checkAuth()`-gated `queryRelevantSince` split, same "first responder wins" `.select().single()`-forces-an-error technique on resolve). **`isApprovedForSelf(requestId, sessionId)`** — the function that closes this task's negative case — does its own fresh server-side read (never trusts a client-supplied field) and returns `true` only when all three hold: `status === "approved"`, `session_id` matches, **and** `requester_user_id` matches the caller's own freshly-verified id. That third check is the one doing real work: RLS's `resolved_by = auth.uid()` clause legitimately lets the resolving friend read the row too (so they can see the outcome of their own decision), but read access is not authorization to use the request as their own pass — without this explicit comparison, a friend who approved someone else's request could reuse that same `requestId` to end their own session early.
- **`friendPollState.ts`**: new `getLastSessionEndPollAt`/`setLastSessionEndPollAt`, mirroring the unlock-poll cursor pair exactly.
- **`messageRouter.ts`** / **`shared/messages.ts`**: `SESSION_END_REQUEST_CREATE`/`SESSION_END_REQUEST_RESOLVE`/`SESSION_END_REQUESTS_FETCH` thin pass-throughs. `SESSION_END`'s hard-mode branch gains an `endRequestId` path: when present, calls `isApprovedForSelf` and either falls through to the existing `abandonSession` logic (on `true`) or returns a clear `{ ok: false, error: "..." }` (on `false`) — the permanent-passcode branch is completely unchanged when `endRequestId` is absent, confirmed by reading the current handler (see excerpt below).
- **`alarmHandlers.ts`**: new `pollSessionEndRequestUpdates(userId)`, added to `handleFriendPollAlarm` alongside the other poll functions — **notification-only**, mirroring `pollUnlockRequestUpdates`'s notification halves, with deliberately **no** `applyApproved*`-style auto-apply call. This matches the plan's own Global Constraints note: ending a session is disruptive, so an approved request never auto-ends anything from the background poll — only a user's own "End session now" click does.
- **New `sidepanel/components/SessionEndRequestPanel.tsx`**, composed into `FriendsTab.tsx` below the panels Task 1 moved in: shows pending session-end requests from friends with Approve/Deny, mirroring `UnlockRequestPanel.tsx`'s shape.
- **`EndSessionControl.tsx`**: alongside the unchanged passcode form — a "Request a temporary pass from a friend" button, a status block with a "Check status" poll, and (once approved) an "End session now" button that sends `SESSION_END` with `endRequestId` instead of `passcode`.

**Judgment call (from the original subagent, reviewed and left as-is):** `SessionEndRequestPanel.tsx` shows the requesting friend's session-end request without resolving their display name through Task 8's `useDisplayNames` — the plan's own Task 8 call-site list does not name this (not-yet-existing) panel, and this task's own Deliverables text doesn't ask for it either. Left as a plain "a friend" framing rather than reaching for a resolver the plan never wired this panel into. Not a blocker; a one-line addition later if desired.
