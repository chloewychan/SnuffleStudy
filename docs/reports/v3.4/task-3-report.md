## Live verification against the Definition of Done — and a real bug found

Wrote `snufflestudy/scripts/verify-friend-requests.mjs` (new, kept committed, matching this repo's unbroken keep-every-verify-script precedent — pattern-matched against `verify-friendships.mjs`/`verify-temp-passcode.mjs`/`verify-unlock-requests.mjs`). Four ephemeral test accounts (A = requester, B = A's friend used as the assigned `friend_user_id` on kind-specific requests, D = A's *other* friend, C = an unconnected stranger), friendships seeded directly via the service-role client, `pg`-based direct-SQL debugging used only to root-cause the bug below (not part of the committed script).

**First run: 1 of 33 checks FAILED.** Case 1 ("D, A's friend but not specifically assigned, CAN resolve A's group-wide `site_unlock` request") failed with `new row violates row-level security policy for table "friend_requests"` — a real, live-database-reproducible rejection, not a script bug. This is exactly the DoD's central "any of the requester's friends" claim, and it didn't hold.

**Root cause**, confirmed via a from-scratch minimal reproduction against a throwaway scratch table (not `friend_requests` itself, to isolate the mechanism from anything project-specific): PostgreSQL's RLS enforcement for `UPDATE` re-checks the `UPDATE` policy's own `USING` clause against the *resulting* row, in addition to `WITH CHECK` — confirmed even with an unconditional `with check (true)`, which still failed identically. `WITH CHECK` can only narrow what `USING` already permits, never widen it. Concretely: `20260815000041`'s `USING` clause has three OR-branches (requester, assigned friend, or `friend_user_id is null and status='pending' and are_friends(...)`); a friend resolving via the third branch necessarily flips `status` away from `'pending'`, so on the new row that branch goes false, and since they're neither the requester nor an assigned friend (there is no assignment on a null-`friend_user_id` row), *no* branch holds post-update — Postgres rejects the write outright, independent of `WITH CHECK`. This is why the requester's own self-resolve (Decision 4) and an *assigned* friend's resolve both worked (their qualifying branch doesn't depend on `status`), and only the "any friend, first-responder-wins" path was broken.

This is a genuine spec-level gap, not an implementation deviation — the shipped migration matches the plan's own Interfaces-section SQL verbatim. The old, now-dropped `unlock_requests` table's SELECT policy (`20260815000008_v2_unlock_request_group_visibility.sql`) already had a `resolved_by = auth.uid()` branch for exactly this "the resolver keeps their own access after resolving" reason (that migration's own comment: *"Once resolved, visibility collapses back down to just the requester and whoever resolved it"*) — the branch was dropped when three tables' policies were consolidated into one, and only a live, actually-exercised third-party-resolver test caught it.

**Fix:** `supabase/migrations/20260815000042_v3.4_friend_requests_resolver_visibility_fix.sql` — adds `resolved_by = auth.uid()` as an additional OR-branch to both the SELECT and UPDATE policies' `USING` clauses (kept identical to each other, as before). Applied to the live dev project via `node scripts/apply-migrations.mjs`. `WITH CHECK` is unchanged — Decision 3's `site_temp_pass` exclusion and Decision 4's preserved self-resolve quirk are untouched.

## Judgment calls

- **Fixed the RLS bug via a new migration (`20260815000042`), not by editing `20260815000041` in place.** Task 2's own report set a precedent of editing a migration file directly for a same-task fix, reasoning it was still being actively authored. This is different: `20260815000041` was fully committed by a *different, already-finished* prior session before I started, and the fix is a `drop policy`/`create policy` pair, which isn't idempotent the way `create or replace function` is (re-running a `create policy` against a database that already has it errors). The plan's own Global Constraints text is explicit and literal on exactly this case: "A later migration can `drop policy`/`create or replace function`/`alter table` to change an earlier one's effective behavior." Followed that.
- **Kept `verify-friend-requests.mjs` committed** — same unbroken precedent as every other `verify-*.mjs` script in this repo.
- **Shortened the new migration's policy names below Postgres's 63-byte identifier limit** — the two policy names it replaces were already silently truncated by Postgres at creation time (confirmed directly via `pg_policies` before picking new ones), an accepted-if-unfortunate existing pattern; picked shorter, non-truncated names for the replacements rather than perpetuating the truncation.
- **Case 3's Edge Function invocation is informational only, not scored pass/fail** — mirrors `verify-temp-passcode.mjs`'s own established precedent for the same reason (deployment lag between a task landing and the QA-gate redeploy step is expected, not a defect in this task's work).
