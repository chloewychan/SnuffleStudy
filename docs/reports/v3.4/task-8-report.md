- **Extended the copy-only "Producer Tag(s)" → "audio nudge(s)" rename beyond the two files the Deliverables section names.** The Deliverables list only spells out `AccountPage.tsx`, but the Interfaces section's own rule is broader ("any other user-facing string containing 'Producer Tag(s)' becomes 'audio nudge(s)'"), and the orchestrating instructions for this task repeated that broader rule explicitly. Grepped the whole `src/` tree for `"Producer Tag"` and classified every hit: genuinely rendered JSX text (`AccountPage.tsx` ×2, `OptionsApp.tsx` ×1, `PrivacyPolicyPage.tsx` ×4) got renamed; everything else — file/component/type names, and header comments in `ActiveSessionView.tsx`/`FriendsTab.tsx`/`StudyRoomPanel.test.tsx`/`useFriendGroupPanelData.ts`/`domain/rooms/producerTag.ts`/`producerTagApi.ts` — was left alone, since those are either internal names explicitly out of scope or non-user-facing prose. `StudyRoomPanel.tsx` itself has no "Producer Tag" user-facing text (only comments), so it needed no edit despite also embedding `ProducerTagRecorder`.
- **Left `NudgeSendSection.tsx`'s own incoming-tags copy ("Couldn't load producer tags…" / "No producer tags yet.") unchanged**, even though it's user-facing and contains "producer tags." The plan's own Interfaces code block explicitly annotates this exact list as "unchanged from today's ProducerTagSection.tsx" — an explicit instruction inside the section that otherwise would fall under the general copy-only rule above. Treated the more specific, literal instruction as authoritative over the general one rather than second-guessing it.
- **Used two different cooldown values (60 vs. 45) in `friendshipSettingsApi.test.ts`'s "maps every patchable field" test**, rather than reusing 60 for both new fields as the original single-field test did — makes the test fail loudly if the written/audio columns were ever accidentally swapped in `toRowPatch`, which a same-value test couldn't catch.
- **Verify script inserts the `friendships` row directly via the service-role client** rather than going through the invite-code generate/redeem RPC flow `verify-friendships.mjs` exercises. That flow is Task 2's own concern and already has dedicated live coverage there; this script only needs *a* friendship to exist so `friendship_settings` gets auto-created by the trigger, which fires regardless of which role performed the insert.
