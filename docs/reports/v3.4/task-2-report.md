### Assessment of the leftover draft migration

Read it in full and independently verified its claims rather than trusting it. It turned out to be **substantially correct and unusually well-grounded** — its own header comments describe three deviations from the plan's literal SQL, each with a stated reason, and I verified all three directly:

1. **Statement ordering** (drop the `invite_codes` policy before the column it references, not after) — confirmed correct by checking that the plan's literal order fails with "cannot drop column … because other objects depend on it."
2. **`redeem_invite_code()`'s return-type change** requires `drop function` before `create function` (`create or replace` can't change a return type) — confirmed correct.
3. **Seven additional call sites of `users_share_a_group()`** the plan's own Interfaces section never mentioned (`unlock_requests`' SELECT/UPDATE, `daily_digests`' SELECT, `session_status_events`' SELECT + `fetch_friend_event_details()`, `session_end_requests`' SELECT/UPDATE) — I independently re-derived this exact same list by grepping every migration for non-comment `users_share_a_group(` calls and cross-referencing which migration last redefined each object; the draft's list was complete and its policy-name targets were exact matches for what's actually live.

I also found and fixed a **pre-existing, unrelated bug** the draft had already partially addressed: `20260815000039`'s `delete_account_data()` claims in its own header comment to be "every other line … copied verbatim from 20260815000038," but its actual body silently drops the `unlock_requests`/`temp_passcode_requests` cleanup blocks that `20260815000038` had — a live FK-violation bug (`Database error deleting user`) for any account that ever created or resolved either kind of request. The draft had already restored those two blocks from `20260815000038` in its own rewrite (correctly, though its comment described this as "AS-IS" carryover, which wasn't quite accurate — I corrected the comment to describe what actually happened and why).

**What I fixed beyond the draft:** the draft had never actually been *run* successfully — the previous attempt terminated before applying it. Running it for real against the live project surfaced two further ordering bugs Postgres's dependency resolution requires and the draft hadn't hit yet:
- `drop table group_memberships` failed because `friend_groups`' own SELECT policy (`"members can read their groups"`, from `20260815000002`) has a raw, non-function subquery into `group_memberships` — this predates `users_share_a_group()` entirely, so it wasn't caught by the "swap every caller" sweep.
- `drop function is_group_member(...)` (and `is_group_owner`/`has_redeemed_invite_code`) failed because `group_memberships`' own three policies (`SELECT`/`INSERT`/`DELETE`) call those `language sql` functions directly — the opposite dependency direction from the first failure.

Fixed by explicitly dropping every blocking policy (the one cross-table policy on `friend_groups`, plus `group_memberships`' own three) before any function or table drop. Verified live, no further errors.

**One more bug found only by exercising it end-to-end** (via my own verification script, described below): `delete_account_data()`'s rewrite never cleaned up `invite_codes` rows referencing the deleted user (`created_by`/`used_by`, no `ON DELETE CASCADE`) — the pre-v3.4 version only cleaned these up as an incidental part of its now-gone `friend_groups`-deletion branch, and that user-scoped cleanup needed to survive independently under the pairwise model. `admin.auth.admin.deleteUser()` failed with the same "Database error deleting user" bug class until I added it back. Applied directly to the live DB via a one-off `create or replace function` (idempotent, safe to re-run) since the migration file was already recorded as applied in `_migrations` by that point — the checked-in file and the live DB now match.
