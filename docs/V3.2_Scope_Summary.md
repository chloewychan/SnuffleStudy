# SnuffleStudy V3.2 Scope Summary — Post-Hackathon Cleanup + Remaining V3 Work

**Purpose of this document:** two kinds of work, bundled because they land in the same follow-up pass. First, harden whatever `docs/V3.1_Scope_Summary.md`'s one-session hackathon rush deliberately left rough. Second, build everything else `docs/V3_Scope_Summary.md` already scoped as must-ship that V3.1 skipped entirely because it wasn't demo-relevant or wasn't safe to rush. Once V3.2 is done, the project is genuinely at the bar V3 originally defined: fully usable, deployment-ready, no gaps — this is where that bar actually gets met, V3.1 having only aimed at "demoable."

---

## Section 1 — Clean up V3.1's shortcuts

Each of these has a specific, named counterpart in `docs/V3.1_Scope_Summary.md` — not general polish, but closing a gap that document flagged on purpose rather than hid.

1. **Extract the shared sign-in component.** V3.1 duplicated OTP form logic between the new onboarding step and `AccountPage.tsx` to save session budget. Factor it into one `<SignInForm />` (or equivalent) both surfaces render, so there's one implementation of `AUTH_REQUEST_OTP`/`AUTH_VERIFY_OTP` instead of two.
2. **Finish wiring the later sign-in gate at every social entry point.** V3.1 only gated the Friends section in Settings. Add the same prompt to: sending or receiving a nudge, joining a Study Room, requesting a temporary hard-mode passcode, and viewing the daily digest — every place a signed-out user could otherwise hit a dead end or a silent no-op instead of a clear "sign in to do this."
3. **Add real automated test coverage for the onboarding auth step.** Every other `OnboardingWizard` step already has one; bring this one in line with that existing convention.
4. **Harden the onboarding copy's edge cases** that V3.1 explicitly didn't handle: a wrong or expired OTP code, requesting a new code, and any state where the user needs feedback beyond "Skip for now."
5. **Fold the onboarding auth flow into the two-account QA script** (Section 2, item 1 below) instead of relying on the single manual click-through V3.1 used to call itself demo-ready.

## Section 2 — Everything else already in the current V3 scope

These are unchanged from `docs/V3_Scope_Summary.md` — restated briefly here for a standalone read; that document remains the source of truth for full detail, so it isn't duplicated in full below.

1. **Manual two-account QA and a canonical QA script** — release gate, not backlog. Friend live status, nudges, unlock approval, digest visibility (verify *after* item 2 below lands, so the check also proves the privacy fix), Study Room audio/video, and Producer Tag delivery, all between two real accounts. Write it up once as a reusable script rather than re-deriving it per release.
2. **Daily-digest privacy enforcement** — centralize the visibility logic so `session_status_events`' RLS and the digest aggregation (`compute_daily_digests()` / `digestApi.fetchDigestForDate`) share one source of truth instead of two independently-written checks, and add negative tests for every hidden field, especially distraction attempts and goal text.
3. **Study Room "active participant" unification** — one Postgres function/view backing both the RLS policy and the `generate-livekit-token` Edge Function's `left_at` check, so the two can't drift the way they can today.
4. **Split `FriendGroupPanel.tsx`** — extract the friend-event feed, nudge send/receive, digest cards, and Producer Tag section into their own files/components, plus a `useFriendGroupPanelData()` hook for the five `load*` functions. Mechanical, not a design change.
5. **Deployment readiness work** — a published privacy policy naming every real data destination (Supabase, Anthropic via Edge Function, Resend, LiveKit, on-device storage), an account-and-data-deletion path, and a manifest permission audit. Required before any real Chrome Web Store submission — Chrome's user-data disclosure policy has been in force since August 1, 2026.

## Suggested execution order

1. **Split `FriendGroupPanel.tsx`** (Section 2.4) — do this first, same reasoning as in V3: smaller surface for everything that touches this file next.
2. **Daily-digest privacy fix** (Section 2.2) — a real privacy gap; close it early.
3. **Study Room active-participant unification** (Section 2.3) — independent, can run in parallel with the above.
4. **Section 1's auth cleanup** (shared component, full gating, tests, copy hardening) — finishes what V3.1 intentionally left rough.
5. **Deployment readiness work** (Section 2.5) — do this once the auth flow is actually final, since the privacy policy needs to describe the real, shipped experience.
6. **Manual two-account QA, last** (Section 2.1) — the release gate, now validating the complete, hardened V3 feature set rather than V3.1's rushed happy path.

## Definition of done for V3.2

Identical to `docs/V3_Scope_Summary.md`'s original bar, since this document is how that bar actually gets reached: every social feature is proven with two real accounts; the digest respects every privacy toggle, with test coverage; Study Room active-participant status has one source of truth; `FriendGroupPanel.tsx` is split with no behavior change; onboarding's sign-in step is fully gated, tested, and shares its implementation with `AccountPage.tsx`; a published privacy policy is live and matches actual data flows; account-and-data deletion works end to end; manifest permissions are audited and justified.
