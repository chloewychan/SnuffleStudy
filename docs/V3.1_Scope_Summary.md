# SnuffleStudy V3.1 Scope Summary — Hackathon Submission Pass

**Purpose of this document:** define the smallest slice of `docs/V3_Scope_Summary.md`'s six must-ship items that is both genuinely worth demoing and safely buildable in one implementation session, for hackathon submission. This is **not** the deployment-ready bar V3 defines — it's a deliberately reduced-rigor pass. `docs/V3.2_Scope_Summary.md` picks up everything this document skips, including hardening whatever this pass leaves rough.

**What "not worrying about safety and nitpicky testing" means here, concretely:** no new automated tests for what gets built in this pass, no live two-account verification, no shared-component extraction where a little duplication is faster. A feature that works when clicked through once, by hand, is the bar for V3.1 — not this project's usual standard (unit tests on every prior onboarding step, 11 live `verify-*.mjs` scripts, multiple review-and-fix rounds per task). That standard comes back in V3.2.

---

## Decisions: why V3.1 is almost entirely one item

Of V3's six must-ship items, only one is both visible in a demo and safe to rush. The other five are excluded for a specific reason each, not by omission:

- **Item 1 (manual two-account QA + canonical script)** — this *is* the "nitpicky testing" the prompt says to skip. It also can't be compressed into "one session" in any meaningful sense — it needs two real people, at minimum. Deferred whole to V3.2.
- **Item 2 (daily-digest privacy enforcement)** — a backend RLS correctness gap that only surfaces if someone specifically pokes at privacy-toggle edge cases. Invisible in a normal demo path. Deferred to V3.2.
- **Item 3 (Study Room active-participant unification)** — same shape as item 2: a backend drift-risk between two code paths, not something a demo click-through would ever surface. Deferred to V3.2.
- **Item 4 (split `FriendGroupPanel.tsx`)** — pure refactor, zero user-visible value, and touching the app's most complex component under deadline pressure is a real way to *introduce* a demo-breaking bug rather than prevent one. Deliberately not attempted before a submission deadline. Deferred to V3.2.
- **Item 6 (deployment readiness: privacy policy, account deletion, permission audit)** — Chrome Web Store compliance has nothing to do with a hackathon submission. Deferred to V3.2 (or whenever this project actually heads toward a real store listing).
- **Item 5 (auth in onboarding, skippable sign-in)** is the one item that's genuinely demo-relevant: it's what lets you actually walk a judge through signing in and using the social/accountability loop as a real flow, not a backend fact you have to explain. It's also reasonably scoped — Supabase Auth already works end-to-end in `AccountPage.tsx`, so this is wiring, not new infrastructure. **This is V3.1's scope**, cut down further below to fit one session.

## What's in V3.1

### Auth in onboarding: skippable sign-in (demo-scoped)

Same product decision as V3's item 5, unchanged: add a sign-in step immediately after the Welcome screen, with the copy **"Sign in to use friends, rooms, nudges, approvals, and synced accountability features,"** a **"Skip for now"** option that routes into local sessions exactly as onboarding already does today, and — for at least one entry point — a later prompt if a user skipped and then goes looking for a social feature.

**Cut down to fit one session, explicitly:**

- **No shared `<SignInForm />` extraction.** Call the existing `AUTH_REQUEST_OTP` / `AUTH_VERIFY_OTP` messages directly from the new onboarding step, duplicating the small amount of form logic `AccountPage.tsx` already has rather than spending session budget on a refactor first. This is a known, flagged shortcut — V3.2 dedupes it.
- **Gate exactly one entry point for the later prompt: opening the Friends section in Settings.** Leave nudge-send, room-join, digest view, and temp-passcode-request ungated for this pass — they'll work fine for an already-signed-in user and simply won't proactively prompt a signed-out one yet. This is a known gap, written down here so it isn't rediscovered as a surprise — V3.2 finishes the rest.
- **No new automated tests.** Every other onboarding step in this codebase has one; this one won't, for now. Flagged, not hidden.
- **No live/scripted verification.** Manually click through both paths once — a real sign-in with a real OTP email, and separately the skip path — before calling this demo-ready. That single manual pass is the actual bar for this document, not a stand-in for real QA.
- **No new "resume after closing the tab mid-verification" handling.** "Skip for now" already covers a user who doesn't want to wait on an email; that's sufficient for a demo.

**Definition of done for V3.1:** a fresh install shows Welcome → the new sign-in step (with the stated copy) → either "Skip for now" or a real, working email-OTP sign-in → the rest of onboarding continues unchanged either way → the app is usable both signed in and signed out → opening Friends in Settings while signed out prompts sign-in. Nothing else about `docs/V3_Scope_Summary.md` changes in this pass — everything else on that list is untouched, on purpose.

## One thing worth naming, outside this document's scope

If there's session budget left after the above and more visual demo polish is wanted, the draggable-bunny item in `docs/V4_Scope_Summary.md` is small, self-contained, and has real demo value (an always-visible companion reads a lot better on stage than one that only appears when something's already gone wrong). It's excluded here on purpose because it isn't part of "the current V3 scope" this document is scoped against — flagged only so it isn't forgotten as a cheap follow-up, not smuggled into this scope.
